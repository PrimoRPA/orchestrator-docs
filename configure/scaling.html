Масштабирование и отказоустойчивость

Применимо: 1.26.9WindowsLinuxDocker

Что в коде 1.26.9 есть для работы нескольких экземпляров служб: узлы WebApi, балансировка через nginx, прямые адреса между службами, кластер RabbitMQ, Redis, привязка лицензий к нескольким серверам, helm-чарты.

Несколько экземпляров WebApi

Экземпляры WebApi работают с общими БД и общим RabbitMQ. Каждый экземпляр — узел со своим номером. Узлы раз в несколько секунд отмечаются в БД; по этим отметкам Оркестратор видит состав кластера и пишет события «Добавился узел» (90500) и «Потерян узел» (90501). Часть очередей RabbitMQ создаётся на каждый узел отдельно — имя очереди дополняется номером узла (события для веб-сокетов, KeepAlive роботов, сброс кэшей).

ПараметрНазначениеПо умолчанию
InstanceInfo:IdНомер узла. У каждого экземпляра — свой. Отрицательное значение — номер генерируется сам и сохраняется в файл InstanceInfoId в рабочей папке службы0 (в Docker 0)
InstanceInfo:RunInBackgroundContextThreadSleepПериод отметки узла, мс. Узел считается потерянным, если не отмечался дольше периода + 2 с2000
InstanceInfo:DisableUpdateStatusОтключить отслеживание узловfalse
InstanceInfo:NodesDesynchronizationTimeoutСколько секунд ждать, пока все узлы подтвердят наличие файла дистрибутива робота. Потом — событие «Рассинхронизация дистрибутива робота на узлах» (1204)60
InstanceInfo:MaxSequentialSwitchingСколько переключений подтверждения подряд считать «мерцанием» (событие 1205)10
Assignment:LockTimeout, ReleaseLockTimeoutPeriodБлокировка заданий между узлами: через сколько секунд снимается зависшая блокировка и как часто это проверяется5, 60
MinWorkerThreads, MinCompletionPortThreadsМинимум потоков пула .NET; значение ≤ 0 — системное-1

В Docker-образе WebApi InstanceInfo__Id=0. При нескольких репликах переопределите его — уникальным числом или отрицательным значением, — иначе узлы будут делить одни и те же очереди.

Дистрибутивы робота и агента без S3 лежат в папке каждого узла, и каждый узел проверяет их у себя. Для нескольких узлов удобнее S3 (см. Хранилища).

Балансировка и nginx

В поставочных nginx/nginx.*.conf каждая служба описана блоком upstream с одним сервером (app_server — WebApi, robotlogs, queues, licenses, rdpstream и др.). Чтобы балансировать, добавьте серверы в нужный upstream. Веб-сокеты UI4 идут через /events/ к WebApi; вместо веб-сокетов можно включить long polling: WS:LongPolling=true (путь — WS:Path, по умолчанию /events).

Проверка живости для балансировщика — /health, /health/readiness, /health/liveness у каждой службы.

Прямые адреса между службами

По умолчанию службы обращаются друг к другу через внешний адрес Оркестратора (nginx). Можно задать внутренние адреса — так удобнее в Kubernetes.

WebApi → RobotLogsRobotLogs:BaseUrl (к нему добавляется /api)RobotDeployment:RobotLogsBaseUrl или RobotDeployment:OrchBaseUrl + /logs
RobotLogs, States, Analytic, RDP2 → WebApiOrchestrator:BaseUrlStates берёт адрес из полученных событий
WebApi → MachineInfoLicense:MachineInfoUrlсведения о «железе» для лицензии читаются SQL-запросом на сервере БД

Redis

Redis не обязателен. Без него отозванные токены хранятся в БД ltoolsidentity (таблица RevokedTokens) с кэшем в памяти на минуту, а кэши — в памяти каждого узла. С Redis токены и часть кэшей становятся общими для узлов.

RDP2

Несколько экземпляров RDP2 делят машины роботов через AddressFilter, WebApi сопоставляет их по RDP:RdpBaseUrls — см. Запуск роботов и RDP-сессии.

Kubernetes (helm)

В k8s/helm есть чарты webapi, robotlogs, queues, licenses, machineinfo, nuget2, ui. Чарт создаёт Deployment и Service: порт 8080 (http, сервис — 80) и 10052 (метрики), пробы /health, /health/liveness, /health/readiness. Параметры службы передаются переменными окружения из values.yaml (env:).

Пример: второй узел WebApi

"InstanceInfo": { "Id": 2 },
"RobotLogs": { "BaseUrl": "http://robotlogs" },
"RabbitMQ": { "Hosts": [ "rabbit1", "rabbit2", "rabbit3" ], "VirtualHost": "orch-prod" },
"UseRedis": true,
"Redis": { "ConnectionString": "redis:6379", "Password": "<зашифрованный>" },
"License": { "MachineInfoUrls": [ "http://app1:<порт>", "http://app2:<порт>" ] }

Как проверить

  1. Запустите второй узел. В «События оркестратора» есть «Добавился узел».
  2. Остановите один узел. Через несколько секунд — «Потерян узел»; UI4 и роботы продолжают работать через оставшийся.
  3. Загрузите дистрибутив робота. Нет события 1204 «Рассинхронизация дистрибутива робота на узлах».
