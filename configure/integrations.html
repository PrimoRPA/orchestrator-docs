Интеграции

Применимо: 1.26.9WindowsLinuxDocker

Передача событий Оркестратора во внешние системы (вебхуки через службу LogEventsWebhook), аналитическая БД и служба Analytic, выгрузки в интеграционные таблицы, доступ к REST API.

Вебхуки на события Оркестратора

Каждое событие журнала Оркестратора WebApi публикует в обменник RabbitMQ типа fanout. Служба LogEventsWebhook читает свою очередь из этого обменника и отправляет событие POST-запросом в JSON на адрес внешней системы. Внешних систем может быть несколько: на каждую — свой экземпляр LogEventsWebhook со своим именем очереди.

WebApi

ПараметрНазначениеПо умолчанию
Integration:EventWebhook:EnabledПубликовать события для вебхуковне задан (в Docker False)
RabbitMQ:EventWebhookExchangeNameОбменник (fanout)eventswebhook

Задайте Integration:EventWebhook:Enabled явно (true или false). Код обращается к подсекции EventWebhook без проверки на отсутствие.

LogEventsWebhook

ПараметрНазначениеПо умолчанию
HttpEndPoint:UrlАдрес приёма событий во внешней системе (POST, JSON, таймаут 10 с)—
HttpEndPoint:LoginUrlНеобязательный адрес авторизации. Служба шлёт туда {"UserName", "Password"}, ждёт ответ {"token": "…"} и передаёт токен в заголовке Authorization: Bearer. При ответе 401 повторяет один разпусто — без авторизации
HttpEndPoint:UserName, PasswordУчётка для LoginUrl, пароль зашифрован—
RabbitMQ:EventWebhookQueueNameОчередь этого экземпляра. Для второй внешней системы — другое имяeventswebhook
RabbitMQ:EventWebhookExchangeNameОбменник, должен совпадать с WebApieventswebhook
RabbitMQ:Host, Port, VirtualHost, UserName, PasswordПодключение к RabbitMQ—

Поля события в теле запроса: Id, Event (код события), EventType, EntityId, EntityData, UserId, TenantId, IP, Text, OrchTimestampUtc, SendedAt, OperationKey, WorkerAdminName, Signature, OrchBaseUrl. Коды событий — на странице События и их коды.

Пример приёмника в поставке — служба ArcSight: принимает события от LogEventsWebhook, переводит их в формат CEF и пишет текстовыми файлами в папку (Files:Path, MaxCountEvents=20, MaxCountFiles=60).

Аналитическая БД: служба Analytic

Analytic читает события Оркестратора из очереди RabbitMQ dbevents2, агрегирует их в БД ltoolsanalytic и периодически обновляет материализованные представления.

ПараметрНазначениеПо умолчанию
DbConnection:Items:Analytic:*Подключение к БД аналитики: Hostname, Port, DbName, UserName, Password и др.DbName в Docker — ltoolsanalytic
Orchestrator:BaseUrlАдрес WebApi—
Schedules:RefreshMaterializedViews:<представление>:CronStringРасписание обновления (Quartz cron). Ключи: mv_WorkersUsage, mv_RobotsUsage, mv_DpaEventsне задано — не обновляются
Schedules:RefreshMaterializedViews:<представление>:CommandTimeoutInSecondsТаймаут команды обновления, с; 0 — без ограничения600
Integration:Unloading, Observability:UnloadingВыгрузки в интеграционные таблицы (Enabled, Items с CronString, ObjectFlow, LeaveIterations)выключены

В Docker-образе Analytic расписания заданы ключами DpaEvents, RobotsUsage, WorkersUsage — без префикса mv_. Код узнаёт только ключи с mv_, поэтому с такими настройками задания запускаются, но представления не обновляются. Переопределите переменные с правильными ключами.

Выгрузки WebApi в интеграционные таблицы

WebApi по расписанию копирует справочники в таблицы IntegrationExchange* БД ltools, откуда их забирает внешняя система.

ПараметрНазначениеПо умолчанию
Integration:Unloading:EnabledВключить выгрузкиfalse
Integration:Unloading:Items:<поток>Потоки: Assignments, ExchangeQueues, Robots, RpaProjects, Workers, Folders. В каждом — CronString и ObjectFlowпусто
Integration:Unloading:OnlyAllSuccessПакет успешен, только если успешны все его частиtrue

Доступ к REST API

Отдельного механизма API-ключей в 1.26.9 нет. Внешняя система входит как обычный пользователь: POST /api/Account с телом {"UserName": "…", "Password": "…"} (для тенанта — заголовок tenantId) и получает в ответе поле token. Дальше — заголовок Authorization: Bearer <token>. Права определяются ролями пользователя, срок токена — Security:Jwt:SessionLifetimeMin.

Описание API: Swagger UI по адресу /api/doc, спецификация — /api/v1/swagger.json. Подробнее — API.

Пример (LogEventsWebhook)

"HttpEndPoint": {
  "Url": "https://siem-gw.example.local/api/OrchEvents",
  "LoginUrl": "https://siem-gw.example.local/api/account",
  "UserName": "orch",
  "Password": "<зашифрованный пароль>"
},
"RabbitMQ": {
  "Host": "rabbit.example.local", "Port": 5672,
  "UserName": "orch", "Password": "<зашифрованный пароль>",
  "EventWebhookQueueName": "eventswebhook-siem"
}

В WebApi: "Integration": { "EventWebhook": { "Enabled": true } }. В Analytic:

"Schedules": { "RefreshMaterializedViews": {
  "mv_WorkersUsage": { "CronString": "0 0/5 * * * ?" },
  "mv_RobotsUsage":  { "CronString": "0 0/5 * * * ?" },
  "mv_DpaEvents":    { "CronString": "0 0/5 * * * ?" }
} }

Как проверить

  1. Включите вебхуки, перезапустите WebApi и LogEventsWebhook, войдите в UI4. В RabbitMQ у обменника eventswebhook есть очередь экземпляра; во внешней системе появилось событие входа.
  2. Сравните несколько записей журнала «События оркестратора» с принятыми событиями. Совпадают по Id и времени.
  3. Через 5–10 минут после старта Analytic выполните в БД ltoolsanalytic запрос к mv_RobotsUsage. Данные свежие; в журнале Analytic нет ошибок обновления представлений.
