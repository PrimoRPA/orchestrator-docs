Очередь проектов

Применимо: 1.26.9WindowsLinuxDocker

На странице описаны выбор робота для проекта из очереди, стратегии очереди и защита системы от всплесков: замедление очереди при перегрузке машин, лимит длины очереди, сглаживание потока событий от триггеров. В конце приведены параметры очередей обмена данными.

Как работает очередь

Проект на запуск попадает в очередь проектов. Выполняется поиск свободного подходящего робота. Если робот найден, проект запускается. Если нет — проект переходит в очередь ожидания и через несколько секунд возвращается. Длительность ожидания зависит от поля «Приоритет» проекта.

ПараметрНазначениеПо умолчанию
RobotStart:UseRabbitMQtrue — очередь на RabbitMQ (циклическая, порядок не гарантирован); false — очередь на таблице БД с гарантированным порядком по приоритетуtrue
RabbitMQ:DeferredQueue1:ExpirationSecОжидание проекта с «Приоритетом» P1 (значение 0), с3 (в Docker 2)
RabbitMQ:DeferredQueue2:ExpirationSecОжидание с P2 (1), с7 (в Docker 5)
RabbitMQ:DeferredQueue3:ExpirationSecОжидание с P3 (2), с20
RabbitMQ:PriorityExpirationMillisecondsЗадержка, за которую проекты, поставленные почти одновременно, упорядочиваются по приоритету, мс1000
RabbitMQ:MaxLengthМаксимальная длина основной очереди в RabbitMQ1000
RobotStart:ProjectEventBusServiceАлгоритм подбора робота: 0 — прежний, 1 — без блокировок, 2 — без блокировок с кэшем (параметры кэша — RobotStart:LockFreeWithCache: LockAgentTTL, LockTTL, QueryRobotsTTL, по 500 мс)0 (в Docker 2)
RobotStart:BatchSizeТолько для UseRabbitMQ=false: сколько новых проектов берётся за один проход10 (в Docker 5)
RobotStart:ThreadSleepТолько для UseRabbitMQ=false: пауза между проходами, мс2000 (в Docker 5000)
ProjectQueue:CleaningDepthЗаписи таблицы очереди старше этого числа дней удаляются1

Чем дольше ожидание, тем выше вероятность, что освободившегося робота займёт другой проект. Чем короче — тем выше нагрузка на БД из-за постоянного поиска робота.

Стратегия очереди

Стратегия определяет, какие роботы допускаются к выполнению проекта:

  • «Проект могут выполнять Роботы, не привязанные ни к какому проекту» (значение 1);
  • «Проект могут выполнять только Роботы, привязанные к проекту» (значение 2);
  • оба варианта одновременно (3).

Глобальная стратегия (она же для тенанта по умолчанию) задаётся в UI4: Настройки → Система → Стратегия очереди проектов (вкладка видна только в тенанте по умолчанию). Для отдельного тенанта её можно переопределить в конфиге WebApi:

ПараметрНазначениеПо умолчанию
Tenants:Items[].RpaProjectQueueProcessingTypeСтратегия для тенанта. Работает при Tenants:FromAppsettings=true; иначе берётся из записи тенанта в БДне задан → глобальная

Замедление очереди при перегрузке машин

Если машина робота перегружена, проект не запускается на ней, а возвращается в очередь, пока нагрузка не снизится. Требуется фоновый сбор метрик машин; он работает только с новым алгоритмом опроса машин.

ПараметрНазначениеПо умолчанию
Worker:CollectWorkerStatusServiceАлгоритм опроса машин: 0 — прежний, 1 — новый. Для замедления требуется 10
Worker:CollectBackgroundPerformanceСобирать метрики машин в фоне вместе с проверкой доступностиfalse
Worker:PerformanceDeltaPrcntШаг шкалы нагрузки 0–100 %25
Worker:PerformanceDelta100PrcntНа сколько процентов метрика может быть ниже 100 %, чтобы машина считалась перегруженной2
ProjectQueue:WorkerPerformanceHighDurationСколько секунд машина должна быть в зоне высокой нагрузки, чтобы проект вернулся в очередь. 0 — замедление выключено60 (в Docker 0)
ProjectQueue:WorkerPerformanceHighCPUOnlyОпределять перегрузку только по CPUtrue
ProjectQueue:WorkerPerformanceHighResolverКак определять высокую нагрузку: 0 — порог AbsoluteWorkerPerformanceHigh, 1 — последний интервал шкалы (100 % − PerformanceDeltaPrcnt)0
ProjectQueue:AbsoluteWorkerPerformanceHighПорог высокой нагрузки, %95

Сглаживание потока событий от триггеров: Assignment

При всплеске событий (расписания, почта, запуски из роботов) их можно пропускать через промежуточную очередь и разбирать с постоянной скоростью — одно событие за интервал.

ПараметрНазначениеПо умолчанию
Assignment:ChainLimiterTriggerEventTimeИнтервал разбора промежуточной очереди, мс. 0 — сглаживание выключенов классе 500; без ключа в конфиге служба не включается (в Docker 500)
Assignment:ChainLimiterTriggerEventSchedule / Email / FromRobotДля каких триггеров включить сглаживание. Если все false — выключеноfalse (в Docker True)
Assignment:MaxTriggerQueueLengthРазмер промежуточной очереди. При переполнении события теряются10000
Assignment:EnableIntegralIntensityWidgetВиджет нагрузки на главной страницеfalse (в Docker True)
Assignment:MaxLastEventsIntervalЗа сколько минут виджет показывает последние события очереди5

Заполнение промежуточной очереди видно по событиям журнала: 9016 — очередь растёт, 9017 — уменьшается, 9018 — «Переполнение очереди событий от триггеров». Поле EntityId у 9016/9017: 1 — 25 %, 2 — 50 %, 3 — 75 % от MaxTriggerQueueLength. Если событий 9018 нет, а рост не превышает 25 %, увеличивать очередь не требуется; при запасе мощности допускается уменьшить интервал.

Как проверить

  1. Поставьте проект в очередь при занятых роботах. В «Очередь проектов» проект ожидает и запускается, когда робот освобождается.
  2. После смены стратегии для тенанта войдите в тенант и откройте проект. Подсказки у роботов и проектов («Робот не привязан к проектам» и т. п.) соответствуют выбранной стратегии.
  3. При включённом сглаживании создайте нагрузку триггерами и проверьте журнал. Есть события 9016/9017, нет 9018.
