Обслуживание БД

Применимо: 1.26.9WindowsLinuxDocker

Какие фоновые задачи Оркестратора сами чистят и переносят данные, какими параметрами они управляются и что администратору БД нужно делать вручную.

Что растёт быстрее всего

Больше всего данных в БД журналов ltoolslogs: таблицы Logs (журнал робота), OrchEvents (журнал Оркестратора), RobotLogMessages, RobotCustomLogMessages, RobotScreenFiles. Сам Оркестратор старые записи журналов не удаляет — для этого секционирование и ручная очистка секций или всего журнала.

В оперативной БД ltools растут запуски проектов, очередь проектов и элементы очередей обмена данными. Для них есть фоновые задачи WebApi.

Перенос старых запусков в БД журналов

Служба WebApi периодически переносит завершённые запуски проектов (завершены успешно, с ошибкой, принудительно или по таймауту) старше Period из ltools в ltoolslogs вместе со значениями аргументов. При нескольких узлах WebApi каждая пачка помечается узлом, чтобы узлы не переносили одно и то же. Результат пишется в журнал Оркестратора: 90300 — успешно, 90301 — ошибка.

ПараметрНазначениеПо умолчанию
RpaProjectLaunch:EnableLogsTransferВключить перенос. Читается при старте службы.true
RpaProjectLaunch:PeriodЧерез сколько минут после завершения запуск считается старым.20160 (2 недели)
RpaProjectLaunch:MaxBatchСколько запусков переносится за один проход.2000
RpaProjectLaunch:LogsThreadSleepПауза между проходами, секунды.300
"RpaProjectLaunch": {
  "EnableLogsTransfer": true,
  "Period": 20160,
  "MaxBatch": 2000,
  "LogsThreadSleep": 300
}

В Docker-образе WebApi (k8s/web-api.Dockerfile) перенос выключен: RpaProjectLaunch__EnableLogsTransfer=False, а MaxBatch=500, Period=80640. Если оставить так, таблица запусков в ltools будет только расти. Проверьте значение в своей установке.

Как проверить: в журнале Оркестратора появляются события 90300 «Перенос старых запусков в БД с логами: успешно»; число запусков старше Period в ltools не растёт.

Очистка очереди проектов

Записи очереди проектов (таблица RpaProjectQueue) сначала помечаются, а затем удаляются физически, если они старше ProjectQueue:CleaningDepth дней. Удаление выполняет служба обработки очереди проектов при работе.

ПараметрНазначениеПо умолчанию
ProjectQueue:CleaningDepthВозраст записей очереди проектов (дней), после которого они удаляются.1

Очереди обмена данными

Две фоновые задачи WebApi:

  • Удаление просроченных элементов — по TTL, сроку (deadline) и таймауту обработки, каждые DeleteExpiredInterval мс.
  • Автоочистка и архивация старых элементов — по правилу, заданному в карточке очереди в UI4: поле «Автоматическая очистка/архивация для старых элементов очереди» со значениями «Очистка / архивация не выполняется», «Очистка при превышении возраста элемента (в днях)», «Очистка при превышении кол-ва элементов в очереди», «Архивация при превышении возраста элемента (в днях)», «Архивация при превышении кол-ва элементов в очереди». Архив — таблицы *Archive в той же БД ltools.
ПараметрНазначениеПо умолчанию
ExchangeQueue:DeleteExpiredIntervalИнтервал удаления просроченных элементов, мс.4000
ExchangeQueue:AllowDeleteLockedItemsУдалять просроченные элементы, заблокированные роботом.false
ExchangeQueue:ExchangeQueueValuesAutoDeleteIntervalИнтервал автоочистки/архивации, минуты. Меньше 5 не бывает.60
ExchangeQueue:ExchangeQueueValuesAutoDeleteChunkSizeРазмер пачки при автоочистке, записей (1–10000).100
ExchangeQueue:MinExchangeQueueValuesDeleteLimitDaysМинимально допустимый порог «возраст в днях» в правиле очереди.30

Результат автоочистки — события 3030 (успешно) и 3031 (ошибка) в журнале Оркестратора.

Журналы: секции, дамп, полная очистка

Только для PostgreSQL. В UI4 в настройках есть вкладка «Журналы» (видна, если СУБД — PostgreSQL). Там список секций таблиц Logs и OrchEvents БД ltoolslogs с размером, фильтром по году и архивным секциям, кнопками «Сделать дамп» и «Удалить».

  • Список секций строится по наследованию таблиц в PostgreSQL (pg_inherits). Год берётся из имени секции: четыре символа после первого _ (например, Logs_2026…); секции с arch в этом месте считаются архивными.
  • Сами секции Оркестратор не создаёт — секционирование настраивает администратор БД.
  • Полная очистка журналов выполняет TRUNCATE таблиц OrchEvents, RobotCustomLogMessages, RobotLogMessages, Logs, RobotScreenFiles и пишет событие 20000 «Очистка логов» (класс «Инцидент безопасности»). Если идёт выгрузка журналов, очистка отклоняется.
ПараметрНазначениеПо умолчанию
LogsDump:PathПапка для дампов. WebApi создаёт её при старте, если её нет.не задано
LogsDump:ArchPathПодпапка (относительно Path) для файла выгрузки LogsDump.zip, который отдаётся на скачивание.не задано
LogsDump:PageSizeРазмер страницы выгрузки, записей. В 1.26.9 используется только отключённой службой выгрузки.20000
LogsDump:MaxPageCountМаксимум страниц в выгрузке. В 1.26.9 используется только отключённой службой выгрузки.100

Удаление секции — это DROP TABLE секции: данные удаляются безвозвратно. Перед удалением сделайте резервную копию.

Дамп и удаление секций в 1.26.9 не работают по коду. Кнопки UI4 отправляют команду в WebApi, но обработчики DumpLogsSectionCommandHandler и DeleteLogsSectionCommandHandler закомментированы, а фоновая служба LogsDumpService отключена в Startup.cs. Команда, скорее всего, завершится ошибкой в журнале WebApi «Ошибка обработки события административной команды для БД с логами». Проверить на стенде и уточнить у разработки; до этого секции удалять средствами СУБД.

Секционирование. Процедура настройки (помесячные секции Logs/OrchEvents, PostgreSQL и MS SQL) в коде отсутствует — есть только статьи на сайте («Секционирование … для PostgreSQL 11+», «… для SQL Server»). Перенести их сюда после сверки со схемой БД 1.26.9.

Рекомендации по параметрам переноса запусков. В руководстве 1.25.7 рекомендованы MaxBatch=500 и Period=80640; в коде по умолчанию 2000 и 20160. Решить, что рекомендовать.

Аналитическая БД. Процедуры очистки ltoolsanalytic (analytics_purge_old_rows) в коде 1.26.9 нет; по сайту она появится в миграциях с 1.26.11. Для выгрузок Analytic есть параметр LeaveIterations — см. Интеграции.

Версии проектов. Фоновой очистки старых версий проектов в коде не найдено. Есть только RpaProject:RemoveOrphans — удалять ли все версии при удалении v0-версии проекта.

Регламент СУБД (VACUUM, перестроение индексов, статистика) в коде не описан — нужна методика от команды.
