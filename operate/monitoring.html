Мониторинг и метрики

Применимо: 1.26.9WindowsLinuxDocker

Каждая служба Оркестратора может предоставлять метрики для Prometheus или Zabbix. На странице описано, как включить сбор, какой адрес указать в системе мониторинга и какие метрики доступны.

Перед началомпройдена Проверка установки
Результатслужбы отдают метрики, Prometheus или Zabbix получает их по заданному адресу

Как устроен сбор метрик

Служба не отправляет метрики самостоятельно. Она открывает отдельный порт и отвечает на запросы Prometheus (HTTP, путь /metrics) или сервера Zabbix (пассивная проверка по протоколу агента Zabbix). Провайдер выбирается в секции Monitoring конфига каждой службы. По умолчанию провайдер не задан — мониторинг выключен, в журнал службы пишется предупреждение Monitoring service is disabled.

Секция Monitoring есть у служб: WebApi, RobotLogs, States, Queues, Notifications, MachineInfo, Analytic, Licenses, LogEventsWebhook, ArcSight, RDP2, а также у Агента на машинах роботов.

Параметры

Секция Monitoring задаётся в конфиге той службы, метрики которой собираются: appsettings.ProdLinux.json (Linux) или appsettings.ProdWin.json (Windows). В поставочных конфигах Linux секции нет — добавьте её. Параметры читаются при запуске: после изменения перезапустите службу.

ПараметрНазначениеПо умолчанию
Monitoring:ProviderPrometheus, Zabbix или пустая строка (выключено). Другое значение — ошибка в журнале службы, мониторинг выключен.""
Monitoring:PortПорт, на котором служба отвечает системе мониторинга. Значение вне 0–65535 — ошибка, мониторинг выключен.10052
Monitoring:DotNetMonitoringEnabledМетрики процесса .NET: память, сборки мусора, потоки, CPU.false
Monitoring:KestrelMonitoringEnabledМетрики встроенного веб-сервера Kestrel: подключения, очереди, TLS.false
Monitoring:NpgsqlMonitoringEnabledМетрики подключений к PostgreSQL, с меткой DbName. Для служб, которые не обращаются к БД (RDP2, MachineInfo), включение не требуется.false
Monitoring:IdleDurationMillisТолько WebApi: как часто (мс) пересчитывать метрики primo_orch_*, которые считаются запросами к БД. Между пересчётами отдаются прежние значения. Минимальное значение — 1000.2000

Пример секции для конфига любой службы:

"Monitoring": {
  "Provider": "Prometheus",
  "Port": 10052,
  "DotNetMonitoringEnabled": true,
  "KestrelMonitoringEnabled": true,
  "NpgsqlMonitoringEnabled": true,
  "IdleDurationMillis": 10000
}

В Docker-образах поставки мониторинг уже включён переменными окружения: Monitoring__Provider=Prometheus, Monitoring__Port=10052, метрики .NET и Kestrel включены, Monitoring__IdleDurationMillis=10000. Порт 10052 объявлен в образе, но в поставочном compose-файле наружу не опубликован: Prometheus должен работать в той же сети Docker либо порт нужно опубликовать в compose-файле.

Если несколько служб установлены на одном сервере, задайте каждой отдельный Monitoring:Port — по умолчанию у всех 10052, и вторая служба не сможет открыть порт.

Подключение Prometheus

  1. В конфиге службы задайте Monitoring:Provider = Prometheus и свободный Monitoring:Port, затем перезапустите службу. в журнале службы нет сообщения Monitoring service is disabled
  2. На сервере службы запросите метрики: curl http://localhost:<Monitoring:Port>/metrics. в ответе есть строки # HELP и primo_…
  3. На сервере Prometheus добавьте в scrape_configs файла prometheus.yml задание — по одному job_name на службу — и перезагрузите конфигурацию Prometheus. на странице целей Prometheus (Status → Targets) задание в состоянии UP

Пример заданий для WebApi и RobotLogs; хосты и порты замените фактическими:

scrape_configs:
  - job_name: "webapi"
    static_configs:
      - targets: ["<хост WebApi>:10052"]
  - job_name: "robotlogs"
    static_configs:
      - targets: ["<хост RobotLogs>:10053"]

Путь /metrics и протокол HTTP — значения Prometheus по умолчанию, задавать их в задании не требуется.

Подключение Zabbix

При Provider: "Zabbix" служба работает как пассивный агент Zabbix на порту Monitoring:Port. На сервере Zabbix создайте узел с интерфейсом агента на этот адрес и порт.

  • Ключ элемента данных — имя метрики, например primo_rl_queue_length.
  • Для метрики с меткой значение метки пишется в квадратных скобках: db_client_connections_usage[ltoolslogs]. Ключ без скобок возвращает значение метрики без метки.
  • Ключ agent.ping всегда возвращает 1 — подходит для проверки доступности.
  • Неизвестный ключ возвращает ZBX_NOTSUPPORTED.

Значение метки в ключе Zabbix должно состоять из латинских букв, цифр и _ и не начинаться с цифры. Метрики WebApi размечены именем тенанта (TenantName): для тенанта с кириллицей, пробелом или дефисом в имени ключ не пройдёт проверку, Zabbix получит ZBX_NOTSUPPORTED.

Метрики служб

У каждой метрики есть описание на русском — строка # HELP в ответе /metrics. Ниже — сводка по службам.

СлужбаПрефиксЧто показывает
WebApiprimo_orch_Срез по тенантам (метка TenantName, у тенанта по умолчанию метки нет): роботы (всего, развёрнутые, выполняющие), машины, проекты и версии, ассеты, шаблоны, задания по статусам, лицензии Студии и робота (всего и занятые по редакциям Enterprise/Standard/Desktop, для оркестраторных и аттендед-роботов). Счётчик primo_orch_failed_uploads — неудачные выгрузки в аналитику (метка TableName).

Analyticprimo_analytic_Полученные и сохранённые события, обновления материализованных представлений, неудачные выгрузки во внешние системы (метка TableName).

Общие метрики (если включены): dotnet_* и process_*, kestrel_*, db_client_*.

Метрики primo_orch_* считаются запросами к БД при каждом обращении Prometheus или Zabbix, но не чаще, чем раз в IdleDurationMillis. При частом опросе увеличьте этот параметр.

Grafana

Отчёты Grafana открываются в UI4 на странице Аналитика → Grafana. Список отчётов задаётся в конфиге WebApi, в секции Grafana:ReportItems: разделы (Name) и отчёты в них (Name, Url, Description).

В шаблонах nginx из поставки Grafana проксируется по пути /grafana/ на 127.0.0.1:3000.
