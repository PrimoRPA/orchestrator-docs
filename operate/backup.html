Резервное копирование и восстановление

Применимо: 1.26.9WindowsLinuxDocker

В резервную копию Оркестратора входят базы данных, файлы, конфиги и секреты. Встроенных средств резервного копирования в Оркестраторе нет — копии создаются средствами СУБД, S3 и ОС.

Перед началомпройдена Проверка установки
Результатсоздана резервная копия баз данных, файлов и конфигов; порядок восстановления из неё известен

Базы данных

Каждая БД задаётся элементом секции DbConnection:Items конфига службы. Имена БД ниже — из Docker-образов поставки; в конкретной установке они могут отличаться, проверьте DbConnection:Items:<имя>:DbName.

ltools, ltoolsidentity и ltoolslicense связаны между собой (идентификаторы тенантов, пользователей, лицензий), поэтому создавайте их копии в одном окне и восстанавливайте вместе.

Конфиги, сертификаты, секреты

  • Конфиги каждой службы: appsettings.json и appsettings.<окружение>.json. Окружение задаёт ASPNETCORE_ENVIRONMENT: в unit-файлах Linux и образах — ProdLinux, на Windows — ProdWin. На Linux службы находятся в /opt/Primo/<Служба>.
  • Unit-файлы systemd Primo.Orchestrator.*.service (Linux) или параметры служб Windows.
  • Конфиг nginx и сертификат с ключом, на которые он ссылается (ssl_certificate, ssl_certificate_key).
  • Переменные окружения PRIMOSALT (соль шифрования паролей в конфигах) и PRIMOSIGNINGKEY (ключ подписи токенов). Без той же соли зашифрованные пароли в конфигах не расшифруются.
  • Если секреты во внешнем хранилище (Secrets:External) — резервная копия Vault или БД секретов.

Копии конфигов и переменных окружения содержат секреты. Храните их с теми же мерами защиты, что и пароли.

Порядок копирования и восстановления

Проверенный порядок для установки службами на Linux с PostgreSQL на том же сервере. Команды выполняются от имени пользователя с правом sudo; команды systemctl --user — под пользователем служб (orch-user). Для других СУБД и вариантов установки порядок тот же, отличаются команды копирования.

Создание копии

  1. Остановите службы Оркестратора, чтобы копии баз и файлов были согласованы между собой: 
    for u in Nginx RDP2 NuGet LogEventsWebhook Licenses Queues States Notifications Analytic RobotLogs WebApi MachineInfo; do
  systemctl --user stop Primo.Orchestrator.$u
done
  2. Создайте копию каждой базы. Каталог копии должен быть доступен пользователю postgres на запись: 
    for d in ltools ltoolsidentity ltoolslicense ltoolsltwrepo ltoolslogs ltoolsanalytic ltoolsnuget; do
  sudo -u postgres pg_dump -Fc -f <каталог копии>/$d.dump $d
done
  3. Создайте копию файлов: каталог данных, конфиги служб, юниты, конфиг и сертификат nginx: 
    cd /
sudo tar -czf <каталог копии>/files.tgz opt/Primo/Data opt/Primo/*/appsettings*.json \
  opt/Primo/nginx/nginx.conf opt/Primo/nginx/cert1.crt opt/Primo/nginx/cert1.rsa \
  home/orch-user/.config/systemd/user
sudo chmod 600 <каталог копии>/files.tgz
  4. Запустите службы и перенесите копию за пределы сервера. /health служб отвечает Healthy

Состояние RabbitMQ копировать не требуется: очереди создаются службами заново при запуске. Сообщения, которые находились в очередях в момент сбоя, при этом теряются, поэтому копию создавайте при остановленных службах.

Восстановление

  1. Остановите службы, если они запущены. Убедитесь, что в RabbitMQ существует пользователь служб с правами на виртуальный хост, а в PostgreSQL — роль служб.
  2. Создайте пустые базы с владельцем — ролью служб и восстановите в них копии: 
    for d in ltools ltoolsidentity ltoolslicense ltoolsltwrepo ltoolslogs ltoolsanalytic ltoolsnuget; do
  sudo -u postgres createdb -O <роль служб> $d
  sudo -u postgres pg_restore -d $d <каталог копии>/$d.dump
done
    pg_restore завершается без сообщений об ошибках
  3. Восстановите файлы. Чтобы восстановить только каталог данных, укажите его в конце команды: 
    sudo tar -xzf <каталог копии>/files.tgz -C / opt/Primo/Data
    владелец /opt/Primo/Data — пользователь служб
  4. Запустите MachineInfo, затем WebApi и дождитесь ответа Healthy на http://localhost:5001/health. После этого запустите остальные службы.
  5. Проверьте результат: вход в интерфейс, раздел лицензий, список роботов, запуск проекта на роботе. лицензии действительны, проект выполняется, история запусков сохранена

При восстановлении на том же сервере лицензии остаются действительными, повторная загрузка не требуется.

Установка в Docker

Проверенный порядок для установки одним compose-файлом. Команды выполняются от имени root в каталоге с compose-файлом. Копируются дамп всех баз, тома с файлами (webapidata, nugetdata) и файлы каталога установки. Том RabbitMQ копировать не требуется.

  1. Остановите службы Оркестратора, кроме PostgreSQL, и создайте дамп баз: 
    cd /opt/Docker
docker compose stop $(docker compose config --services | grep -v '^0postgres-db$')
docker compose exec -T 0postgres-db pg_dumpall -U postgres | gzip > <каталог копии>/all.sql.gz
  2. Остановите PostgreSQL и создайте копию томов и файлов установки. Имена томов выводит docker volume ls: 
    docker compose stop
for v in orch-docker_webapidata orch-docker_nugetdata; do
  tar -czf <каталог копии>/$v.tgz -C /var/lib/docker/volumes/$v/_data .
done
cp docker-compose.yml nginx.conf cert1.crt cert1.rsa <каталог копии>/
  3. Запустите службы: docker compose start. docker compose ps — все службы healthy

Восстановление на сервере с установленным Docker:

  1. Верните в каталог установки docker-compose.yml, nginx.conf и файлы сертификата из копии. Создайте контейнеры и тома без запуска и распакуйте в тома файлы: 
    cd /opt/Docker
docker compose up --no-start
for v in orch-docker_webapidata orch-docker_nugetdata; do
  tar -xzf <каталог копии>/$v.tgz -C /var/lib/docker/volumes/$v/_data
done
  2. Запустите только PostgreSQL, дождитесь состояния healthy и восстановите базы. Сообщение о том, что роль postgres уже существует, ошибкой не является: 
    docker compose up -d 0postgres-db
gunzip -c <каталог копии>/all.sql.gz | docker compose exec -T 0postgres-db psql -U postgres -q -d postgres
  3. Запустите остальные службы: docker compose up -d. все службы healthy; лицензии действительны, проект на роботе выполняется

Ключ primo-machine-key в compose-файле должен остаться прежним: к нему привязаны лицензии.

Восстановление: на что обратить внимание

  • После восстановления конфигов служба при старте сравнит их с хэшем в БД и, если файл отличается, запишет событие 2 «Конфигурационный файл изменен» (класс «Инцидент безопасности»). Это штатное поведение.
  • Лицензии привязываются к серверу через службу MachineInfo (License:MachineInfoUrl, License:MachineInfoUrls). При восстановлении на другом оборудовании лицензии могут стать недействительными.
