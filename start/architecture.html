Как устроен Оркестратор

Применимо: 1.26.9WindowsLinuxDocker

Из каких служб состоит Оркестратор, какие базы данных и внешние компоненты ему нужны и как команда «запустить робота» доходит до машины робота.

Серверные службы

Все службы собираются одной версией (в 1.26.9 — 1.26.9) и публикуются под Windows (win-x64) и Linux (linux-x64). Имя исполняемого файла — Primo.Orchestrator.<Служба>.

Имена БД — значения по умолчанию из Dockerfile-ов; при установке их можно поменять. Подробный справочник — Компоненты и службы.

На машине робота

  • Агент — служба Primo.Orchestrator.Agent (Windows-служба или systemd-юнит на Linux). Слушает HTTP(S)-запросы от WebApi и отвечает обратными вызовами на /api/AgentCallback/….
  • Agent.Runner — входит в Linux-дистрибутив агента, запускает робота в графической сессии.
  • AgentUpdater — утилита автообновления агента. Агент скачивает её из WebApi перед обновлением; см. Порядок обновления.
  • Робот — Primo.Robot, развёрнутый агентом из дистрибутива.

Потоки трафика

Браузер ──HTTPS──► UI (Nginx) ──► WebApi / RobotLogs / Licenses / Queues / NuGet
WebApi ──HTTP(S)──► Агент:  Deploy, Start, HardKill, Erase, Reboot, Update
Агент ──HTTP(S)──► WebApi: /api/AgentCallback/… (трекинг), скачивание проекта и дистрибутивов
Робот ──HTTP(S)──► WebApi (RobotDeployment:OrchBaseUrl) и RobotLogs (RobotDeployment:RobotLogsBaseUrl)
Службы ◄──► RabbitMQ;   WebApi ◄──REST──► RDP2;   WebApi ──► MachineInfo (License:MachineInfoUrl)
UI ◄── /events (WS:Path) ── WebApi: живые обновления в интерфейсе

Порты — на странице Порты.

Как запускается робот

  1. Запуск инициирован вручную или заданием. Проект попадает в очередь проектов (RabbitMQ, при строгом порядке — таблица БД). проект виден в RPA-проекты → Очередь проектов
  2. Для свободного робота WebApi вызывает у агента api/Robots/Start (или StartWithTracking). в карточке робота появляется трекинг запуска
  3. Агент проходит этапы и сообщает о каждом: остановка старого процесса робота, скачивание и сохранение архива проекта, генерация скрипта запуска, создание задачи запуска. этапы трекинга отмечены успешными
  4. Windows: агент пишет run.bat и создаёт задачу Планировщика заданий под учётной записью робота. Linux: агент пишет start-0-runner.sh → start-1-session.sh (поднимает графическую сессию) → start-2-robot.sh. Если в ~/.config/robot есть исполняемые pre-session.sh, post-session.sh, pre-robot.sh, post-robot.sh, они выполняются до и после соответствующего шага. процесс Primo.Robot запущен
  5. Робот получает свободную лицензию, переходит в состояние «Выполняет проект», шлёт логи в RobotLogs, работает с ресурсами и очередями через WebApi. статус робота — выполняет проект

Развёртывание идёт так же через агента (api/Robots/Deploy): агент скачивает дистрибутив робота, распаковывает его, на Windows правит Primo.Robot.exe.config (порт и сертификат) и резервирует URL робота.

Расхождение со старыми доками: в руководстве 1.25.7 Linux-робот запускается через robotTask.sh, в коде 1.26.9 — цепочка start-0-runner.sh / start-1-session.sh / start-2-robot.sh с хуками pre/post (хуки — с 1.26.6).

Старые доки: «Оркестратор открывает RDP-сессию под учётной записью робота, дожидается загрузки профиля» перед запуском Windows-робота. В коде есть вызовы агента RDPUserProfileLoaded и LinuxUserSessionReady, но кто и когда открывает сессию (WebApi, RDP2 или внешний клиент) — проверить и описать на странице Запуск роботов и RDP-сессии.

В Docker-поставке на Ubuntu есть ещё служба mcp (MCP-сервер, PrimoRpa.McpServer.Api). Её код не входит в решение Orchestrator.Backend.sln. Через неё ИИ-клиенты работают с Оркестратором по протоколу MCP — см. MCP Server. Включать ли её в общую схему — уточнить у разработки.
