Установка служб

Применимо: 1.26.9WindowsLinux

Оркестратор устанавливается на сервер набором служб: на Linux — юнитами systemd, на Windows — службами Windows, перед ними nginx с UI4. Выберите ОС сервера: на вкладке описан весь порядок установки.

Linux: службы работают без root

На Linux все службы Оркестратора и nginx работают от одного обычного пользователя через пользовательские юниты systemd. Такой вариант безопаснее; все порты поставки выше 1024, поэтому root не требуется. Инструкции на вкладках ниже составлены для этого варианта; вариант от root — в конце каждой вкладки.

Что нужно для работы без root
  • Пользователь служб. Один для всех служб и nginx. В образах Docker он называется orch-user (UID 1001); на сервере имя выбирается произвольно.
  • Linger. sudo loginctl enable-linger <пользователь>. Без него службы стартуют только после входа пользователя и останавливаются после выхода. Проверка: loginctl show-user <пользователь> --property=Linger — Linger=yes.
  • Владелец каталогов. /opt/Primo/<Служба> и /opt/Primo/nginx принадлежат пользователю служб. В /opt/Primo/nginx юнит при каждом старте создаёт logs (журналы и nginx.pid) и temp — требуется право записи.
  • Каталоги данных. Пользователю требуется право записи во все каталоги из конфигов служб: у WebApi — RobotDistrUpload:TargetFilePath, AgentDistrUpload:TargetFilePath, RpaProjectArchiveUpload:TargetFilePath, NuGet:UploadPackagePath, LogsDump:Path, LogsDump:ArchPath; у RobotLogs — ScreenFileUpload:ScreenFilePath; у NuGet2 — FileSystem:Path; у ArcSight — Files:Path; каталоги файловых журналов Serilog, если они заданы.
  • Файлы на чтение. Ключ сертификата nginx cert1.rsa — владелец пользователь служб, права 600. Keytab для входа через Kerberos (ActiveDirectory:MultyForest:<имя>:KerberosKeytabPath), если он хранится в файле.
  • Команды — от имени пользователя служб. Копируйте файлы и вызывайте systemctl --user в его сессии, не через sudo: иначе файлы получат владельца root и юнит не запустится.

Сессия пользователя открывается входом по SSH или из текущей сессии:

sudo su - <пользователь>
export XDG_RUNTIME_DIR=/run/user/$(id -u)

Без XDG_RUNTIME_DIR команда systemctl --user после su не находит менеджер пользователя.

Чем системный юнит отличается от пользовательского

Установка по ОС

Выбор вкладки запоминается, а ссылка с адресом вкладки (например, install-services.html#astra) открывает сразу нужную ОС.

Полная установка серверной части Оркестратора на Astra Linux: подготовка сервера, службы как пользовательские юниты systemd (без root), nginx с UI4, проверка и агент на машинах роботов. Разделы выполняются по порядку.Вариант от root — в конце страницы.

Что нужно

  • Архивы служб primo-rpa-orchestrator-<служба>-<версия>-linux.zip из таблицы выше и primo-rpa-orchestrator-passwordencryptor-<версия>-linux.zip. Архивы self-contained: установка .NET не требуется. В каждом архиве есть appsettings.ProdLinux.json и два юнита: *.service (от root) и *.user.service (без root).
  • Архив UI4, конфиг nginx.linux.conf, юниты Primo.Orchestrator.Nginx.user.service и Primo.Orchestrator.Nginx.service.
  • Сертификат и ключ на внешнее имя Оркестратора — файлы cert1.crt и cert1.rsa.
  • PostgreSQL и RabbitMQ — на этом или отдельном сервере.
  • Учётная запись с sudo на сервере.
  • Внешний адрес Оркестратора (DNS-имя или IP), ниже — <адрес>.

Ресурсы сервера — см. Требования к железу.

1. Подготовка сервера

  1. Установите пакеты: 
    sudo apt update
sudo apt install nginx unzip curl libicu72
    От пакета nginx нужны только /usr/sbin/nginx и /etc/nginx/mime.types. libicu72 — библиотека ICU для .NET, она же устанавливается в образ Docker на Astra 1.8. nginx -v выводит версию, файл /etc/nginx/mime.types существует
  2. Отключите стандартный юнит nginx, иначе он запустит второй nginx со своим конфигом: 
    sudo systemctl disable --now nginx
    systemctl is-enabled nginx — disabled, systemctl is-active nginx — inactive
  3. Для MachineInfo установите cpuid: 
    sudo apt install cpuid
    MachineInfo собирает параметры машины для лицензии командами hostname, cpuid и lsblk --nodeps -no serial <Devices:HDD>. Если cpuid не установлен, вместо серийного номера процессора служба возвращает000000000000. cpuid | grep 'processor serial number' выводит строку
  4. Создайте пользователя служб и разрешите его юнитам работать без входа в систему: 
    sudo useradd -m -s /bin/bash orch-user
sudo loginctl enable-linger orch-user
    Без linger службы стартуют только после входа пользователя и останавливаются после выхода. loginctl show-user orch-user --property=Linger — Linger=yes
  5. Создайте каталоги и назначьте их владельцем пользователя служб: 
    sudo mkdir -p /opt/Primo/{MachineInfo,WebApi,RobotLogs,Analytic,Notifications,States,Queues,Licenses,LogEventsWebhook,NuGet2,RDP2,ArcSight,nginx,Data}
sudo chown -R orch-user:orch-user /opt/Primo/{MachineInfo,WebApi,RobotLogs,Analytic,Notifications,States,Queues,Licenses,LogEventsWebhook,NuGet2,RDP2,ArcSight,nginx,Data}
    В каталоге /opt/Primo/Data службы хранят загруженные дистрибутивы, архивы проектов и пакеты. Владелец меняется только у перечисленных каталогов: если на этом же сервере установлен агент, каталоги /opt/Primo/Agent и /opt/Primo/AgentData должны остаться за пользователем агента. ls -l /opt/Primo — владелец перечисленных каталогов orch-user
  6. Скопируйте архивы и файлы nginx в каталог пользователя служб, например в /home/orch-user/dist: 
    sudo mkdir -p /home/orch-user/dist
sudo cp <каталог с файлами поставки>/linux/*.zip <каталог с файлами поставки>/ui/*.zip <каталог с файлами поставки>/data/NGINX/* /home/orch-user/dist/
sudo chown -R orch-user:orch-user /home/orch-user/dist
    Домашний каталог пользователя служб закрыт для других учётных записей, поэтому копирование выполняется через sudo. Файлы nginx — nginx.linux.conf и Primo.Orchestrator.Nginx.user.service — находятся в папке версии orchestrator/data/NGINX/, архив UI4 — в orchestrator/ui/. sudo ls /home/orch-user/dist показывает архивы служб, архив UI4, nginx.linux.conf и юнит nginx
  7. Откройте на файерволе входящий 44392/tcp, если файервол включён. Для ufw: sudo ufw allow 44392/tcp. С сервера должны быть доступны СУБД (5432 для PostgreSQL) и RabbitMQ (5672); при установке на этот же сервер дополнительных действий не требуется.

Параметры, которые возвращает MachineInfo (имя хоста, серийные номера процессора и диска), используются для лицензии. Установитеcpuid, задайте Devices:HDD и имя хоста до запроса лицензии и не изменяйте их после этого.

2. СУБД и RabbitMQ

Установите их по инструкции поставщика или используйте существующие. Для Оркестратора требуются:

  • Базы PostgreSQL: ltools, ltoolsidentity, ltoolslicense, ltoolsltwrepo (WebApi), ltoolslogs (RobotLogs), ltoolsanalytic (Analytic), ltoolsnuget (NuGet2). Licenses работает с ltools.
  • Для каждой БД — рабочий пользователь и пользователь миграций (допускается один и тот же). WebApi применяет миграции при каждом старте, поэтому пользователю миграций нужны права на создание объектов, а если базы не созданы заранее — и на создание БД.
  • Пользователь RabbitMQ для служб, порт 5672.

Пример для случая, когда СУБД и RabbitMQ устанавливаются на этот же сервер. Пакеты PostgreSQL и RabbitMQ установите из репозитория ОС или по инструкции поставщика.

  1. Создайте в PostgreSQL пользователя и базы. Пароль задайте собственный, без пробелов: 
    sudo -u postgres psql -c "CREATE ROLE orch LOGIN PASSWORD '<пароль БД>';"
for d in ltools ltoolsidentity ltoolslicense ltoolsltwrepo ltoolslogs ltoolsanalytic ltoolsnuget; do
  sudo -u postgres createdb -O orch $d
done
    команда psql -h localhost -U orch -d ltools -c "select 1" запрашивает пароль и выводит 1
  2. Создайте пользователя RabbitMQ и выдайте ему права: 
    sudo rabbitmqctl add_user orch '<пароль RabbitMQ>'
sudo rabbitmqctl set_permissions -p / orch ".*" ".*" ".*"
    sudo rabbitmqctl list_users показывает пользователя orch

В примере базы принадлежат пользователю orch, поэтому он же применяет миграции. Имя пользователя и пароли указываются в конфигах служб на шаге 4.

3. Пароли для конфигов

Пароли СУБД и RabbitMQ в конфигах указываются зашифрованными. Зашифруйте два пароля, заданные в разделе 2: пароль пользователя БД и пароль пользователя RabbitMQ. Утилиту запускают дважды, по разу на каждый пароль; обе полученные строки понадобятся в разделе 4. Для шифрования используется утилита из архива PasswordEncryptor-linux.

  1. Распакуйте и запустите утилиту: 
    unzip primo-rpa-orchestrator-passwordencryptor-*-linux.zip -d ~/encryptor
chmod +x ~/encryptor/Primo.Orchestrator.PasswordEncryptor
~/encryptor/Primo.Orchestrator.PasswordEncryptor
  2. Утилита ничего не выводит и ожидает ввода строки. Введите пароль и нажмите Enter. Если используется собственная сольPRIMOSALT, введите через пробел: <пароль> <соль>. утилита выводит Copy following string: и зашифрованную строку; эта строка вставляется в конфиг. Для выхода нажмите любую клавишу

Пароль не должен содержать пробелов: утилита делит строку по пробелу. Если PRIMOSALT задан, он должен быть одинаковым на всех службах и агентах; в пользовательских юнитах для него есть закомментированная строка #Environment=PRIMOSALT=.

4. Службы Оркестратора

Все шаги этого раздела выполняйте под orch-user, не через sudo: иначе файлы получат владельца root и юниты не запустятся.

  1. Откройте оболочку пользователя служб — войдите по SSH под orch-user или из текущей сессии: 
    sudo su - orch-user
export XDG_RUNTIME_DIR=/run/user/$(id -u)
    whoami — orch-user; systemctl --user status отвечает без ошибки подключения к шине
  2. Распакуйте архивы и сделайте файлы исполняемыми: 
    cd ~/dist
for s in MachineInfo WebApi RobotLogs Analytic Notifications States Queues Licenses LogEventsWebhook RDP2 ArcSight; do
  unzip -q -o primo-rpa-orchestrator-"${s,,}"-*-linux.zip -d /opt/Primo/$s
  chmod +x /opt/Primo/$s/Primo.Orchestrator.$s
done
unzip -q -o primo-rpa-orchestrator-nuget2-*-linux.zip -d /opt/Primo/NuGet2
chmod +x /opt/Primo/NuGet2/BaGet
    Если RDP2 и ArcSight не требуются, исключите их из списка. в каждом каталоге есть исполняемый файл, appsettings.ProdLinux.json и юниты *.service, *.user.service
  3. Настройте appsettings.ProdLinux.json каждой службы — см. «Минимальные изменения для запуска» ниже. Вместо изменения файла допускается добавить в юнит строки Environment=: секция и ключ через двойное подчёркивание, например Environment=RabbitMQ__Host=db01. Переменные окружения перекрывают файл.
  4. Установите пользовательские юниты: 
    mkdir -p ~/.config/systemd/user
for s in MachineInfo WebApi RobotLogs Analytic Notifications States Queues Licenses LogEventsWebhook RDP2 ArcSight; do
  cp /opt/Primo/$s/Primo.Orchestrator.$s.user.service ~/.config/systemd/user/Primo.Orchestrator.$s.service
done
cp /opt/Primo/NuGet2/Primo.Orchestrator.NuGet.user.service ~/.config/systemd/user/Primo.Orchestrator.NuGet.service
systemctl --user daemon-reload
    Файл копируется без .user в имени — по этому имени выполняется управление службой. systemctl --user list-unit-files 'Primo.Orchestrator.*' показывает все юниты
  5. Запустите MachineInfo: 
    systemctl --user enable --now Primo.Orchestrator.MachineInfo
curl -k https://localhost:5051/health
    В поставочном конфиге MachineInfo слушает порт 5051 по HTTPS со встроенным сертификатом, поэтому проверка выполняется с ключом -k. ответ Healthy
  6. Запустите WebApi. При первом запуске служба создаёт таблицы в базах, это занимает около минуты: 
    systemctl --user enable --now Primo.Orchestrator.WebApi
curl http://localhost:5001/health
    При первом запуске в журнале службы есть ошибки «Failed executing DbCommand» с запросом к таблице __EFMigrationsHistory: таблиц ещё нет, после создания ошибки прекращаются. /health отвечает Healthy; в журнале (journalctl --user -u Primo.Orchestrator.WebApi) есть строка Now listening on: http://[::]:5001
  7. Запустите остальные службы: 
    for u in RobotLogs Analytic Notifications States Queues Licenses LogEventsWebhook NuGet; do
  systemctl --user enable --now Primo.Orchestrator.$u
done
    При необходимости так же запустите Primo.Orchestrator.RDP2 и Primo.Orchestrator.ArcSight. Проверка всех служб одной командой: 
    for p in 56748 56749 56751 56750 5088 5089 56770; do echo "$p $(curl -s http://localhost:$p/health)"; done
    /health отвечает Healthy на портах 56748, 56749, 56751, 56750, 5088, 5089, 56770; curl http://localhost:8081/ отвечает без ошибки; RDP2 — curl -k https://localhost:5102/health

Если States отвечает Unhealthy, в её конфиге не задан Orchestrator:BaseUrl — см. таблицу ниже.

Минимальные изменения для запуска

Набор изменений, с которым Оркестратор запускается на одном сервере. Файл каждой службы — /opt/Primo/<служба>/appsettings.ProdLinux.json, редактируется под orch-user, например nano /opt/Primo/WebApi/appsettings.ProdLinux.json. Параметры, не названные в списке, оставьте как в файле: почта, приёмник событий, ключ NuGet, каталоги данных для запуска изменять не требуется.

  1. Подключение к RabbitMQ — файлы WebApi, RobotLogs, Analytic, Notifications, States, Queues, Licenses, LogEventsWebhook. В секции RabbitMQ задайте три строки: 
    "Host": "127.0.0.1",
"UserName": "orch",
"Password": "<зашифрованный пароль RabbitMQ>",
  2. Подключение к базам — файлы WebApi (четыре строки), RobotLogs, Analytic, Licenses, NuGet2 (по одной). В каждой строке, которая начинается с PORT=5432;, замените имя пользователя и пароль в конце строки. Было: 
    …;HOST=127.0.0.1;USER ID=postgres;SearchPath=public;PASSWORD=<пример>"
    Стало: 
    …;HOST=127.0.0.1;USER ID=orch;SearchPath=public;PASSWORD=<зашифрованный пароль БД>"
    Строку с базой ltoolssecrets не изменяйте.
  3. Внешний адрес — файл WebApi. Замените адрес из примера в четырёх параметрах: 
    "OrchBaseUrl": "https://<адрес>:44392",
"RobotLogsBaseUrl": "https://<адрес>:44392",
"RdpBaseUrl": "https://<адрес>:44392/rdpstream",
"NuGetBaseUrl": "https://<адрес>:44392",
  4. Адрес WebApi для служб — файлы RobotLogs, Licenses, Queues, RDP2. В секции Orchestrator задайте "BaseUrl": "http://localhost:5001". В файле LogEventsWebhook задайте "LoginUrl": "http://localhost:5001/api/account".
  5. Секция, которой нет в файле — файлы States и Analytic. Добавьте секцию сразу после первой открывающей скобки файла; запятая после закрывающей скобки секции обязательна: 
    {
  "Orchestrator": {
    "BaseUrl": "http://localhost:5001"
  },
  …остальное содержимое файла без изменений
  6. Диск для лицензии — файл MachineInfo. В параметре "HDD" укажите диск сервера с путём, например "/dev/vda". Имя диска выводит команда lsblk --nodeps -no name,serial.

Службы RDP2 и ArcSight для запуска не требуются. RDP2 нужна, только если роботы работают на Windows.

Что задать в конфигах

Полная таблица параметров — для справки и для установки на несколько серверов. Значения для случая, когда все компоненты установлены на одном сервере. Адреса служб между собой — localhost; внешний адрес — https://<адрес>:44392. В поставочных файлах уже записаны примеры: адреса вида 192.168.0.x, пользователь postgres, пользователь RabbitMQ admin. 7. Машины роботов на Astra Linux

На каждую машину роботов устанавливается агент. Он всегда работает от пользователя Agent:UserName (по умолчанию agent), общая группа агента и роботов — Agent:GroupName (по умолчанию primo-rpa). Основной вариант — пользовательский юнит: обновление агента из Оркестратора управляет им командой systemctl --user.

Что нужно: архив primo-rpa-orchestrator-agent-<версия>-linux.zip (в нём агент, LTools.Orchestrator.Agent.Runner, appsettings.Runner.json, launch-as-user.expect и юниты), sudo на машине.

  1. Установите пакеты: 
    sudo apt install expect unzip xvfb xauth x11-utils dbus-x11
    Пакет x11-utils содержит утилиту xprop: без неё запуск роботов завершается без сообщения в интерфейсе. У пользователя робота должен существовать каталог ~/.local/share — подробности на странице Машины роботов и агент. Также требуются: X-сервер — /usr/bin/Xvnc (позволяет просматривать сеанс робота и управлять им) или /usr/bin/Xvfb (без просмотра), /usr/bin/xauth, для Xvnc — /usr/bin/vncpasswd; графическая оболочка Fly (/usr/bin/fly-wm). На Astra 1.8 — ещё /usr/bin/dbus-launch: агент вызывает его перед запуском сеанса робота. ls /usr/bin/expect /usr/bin/fly-wm /usr/bin/xauth и ls /usr/bin/Xvnc (или /usr/bin/Xvfb) находят файлы
  2. Создайте группу и пользователя агента, добавьте в группу пользователей роботов: 
    sudo groupadd primo-rpa
sudo useradd -g primo-rpa -m -s /bin/bash agent
sudo usermod -aG primo-rpa <пользователь робота>
    Другие имена — укажите в Agent:UserName и Agent:GroupName. id agent показывает группу primo-rpa
  3. Разрешите агенту запуск роботов и перезагрузку без пароля — файл в /etc/sudoers.d/ (редактируйте через sudo visudo -f /etc/sudoers.d/primo-agent): 
    agent ALL=(root) NOPASSWD: /usr/bin/systemd-run -G --uid=agent --gid=primo-rpa --property=EnvironmentFile=/dev/shm/agent-*-env /opt/Primo/Agent/launch-as-user.expect
agent ALL=(root) NOPASSWD: /usr/bin/systemd-run -G --unit=primo-robot-* --uid=agent --gid=primo-rpa --property=EnvironmentFile=/dev/shm/agent-*-env /opt/Primo/Agent/launch-as-user.expect
agent ALL=(root) NOPASSWD: /usr/bin/systemctl stop primo-robot-*.service
agent ALL=(root) NOPASSWD: /usr/sbin/reboot
    sudo -l -U agent показывает четыре команды
  4. Включите linger и подготовьте каталоги: 
    sudo loginctl enable-linger agent
sudo mkdir -p /opt/Primo/Agent <каталог данных агента> <каталог роботов>
sudo chown agent:primo-rpa /opt/Primo/Agent <каталог данных агента> <каталог роботов>
sudo chmod 775 <каталог роботов>
    Агент работает с UMask=0002, чтобы он и роботы могли удалять файлы друг друга в каталоге проекта.
  5. Откройте входящий 5002/tcp — на этот порт обращается WebApi.
  6. Под пользователем агента распакуйте архив и настройте конфиг: 
    sudo su - agent
export XDG_RUNTIME_DIR=/run/user/$(id -u)
unzip -q -o primo-rpa-orchestrator-agent-*-linux.zip -d /opt/Primo/Agent
cd /opt/Primo/Agent
chmod +x Primo.Orchestrator.Agent LTools.Orchestrator.Agent.Runner launch-as-user.expect
    В appsettings.ProdLinux.json задайте Agent:DataPath и DeployRobot:RobotsPath (по умолчанию C:\LTools — для Linux не подходит). AgentCommands:Session на Astra допускается не задавать: если параметр пуст, агент использует/usr/bin/fly-wm --execOnly {} (ОС определяется по NAME в /etc/os-release).
  7. Установите и запустите юнит (также под agent): 
    mkdir -p ~/.config/systemd/user
cp /opt/Primo/Agent/Primo.Orchestrator.Agent.user.service ~/.config/systemd/user/Primo.Orchestrator.Agent.service
systemctl --user daemon-reload
systemctl --user enable --now Primo.Orchestrator.Agent
    curl -k https://localhost:5002/api/Version возвращает версию агента; в journalctl --user -u Primo.Orchestrator.Agent нет предупреждений «the launch of robots is impossible»
  8. Зарегистрируйте машину: в UI4 Настройки → Система → Машины роботов, Добавить машину, заполните Наименование и IP/DNS, включите Linux (после сохранения не меняется) и сохраните. в списке машин в колонке Версия агента появилась версия

При старте агент проверяет: доступен ли sudo, есть ли expect, исполняемы ли launch-as-user.expect и команда сеанса, разрешён ли в sudoers вызов systemd-run, существуют ли пользователь и группа. Каждая проблема — отдельное предупреждение в журнале. Подробнее об агенте — Машины роботов и агент.

Вариант от root: если nginx должен слушать порт ниже 1024

Службы работают от root через системные юниты. Вариант используется, если nginx должен слушать порт ниже 1024 (например, 443). Чем отличаются варианты — в начале страницы, в блоке «Linux: службы работают без root»; как перейти с root — Переход с root на работу без root.

  1. Выполните разделы 1–3 без шагов про пользователя orch-user, linger и chown.
  2. Распакуйте архивы командами из раздела 4 через sudo, настройте конфиги.
  3. Установите системные юниты — файлы без .user: 
    for s in MachineInfo WebApi RobotLogs Analytic Notifications States Queues Licenses LogEventsWebhook RDP2 ArcSight; do
  sudo cp /opt/Primo/$s/Primo.Orchestrator.$s.service /etc/systemd/system/
done
sudo cp /opt/Primo/NuGet2/Primo.Orchestrator.NuGet.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now Primo.Orchestrator.MachineInfo
sudo systemctl enable --now Primo.Orchestrator.WebApi
    затем остальные службы в том же порядке, что в разделе 4. systemctl status Primo.Orchestrator.WebApi — active (running)
  4. nginx: файлы — как в разделе 5, но через sudo; юнит Primo.Orchestrator.Nginx.service в /etc/systemd/system/. Главный процесс nginx работает от root, рабочие — от пользователя сборки nginx (на Astra обычно nobody), поэтому www должен быть доступен всем на чтение (755 / 644). systemctl status Primo.Orchestrator.Nginx — active (running)

В системных юнитах служб, кроме RDP2 и nginx, нет Restart=always: после сбоя служба автоматически не перезапускается. В пользовательских юнитах служб перезапуск через 5 секунд задан.

Полная установка серверной части Оркестратора на РЕД ОС: подготовка сервера, службы как пользовательские юниты systemd (без root), nginx с UI4, проверка и агент на машинах роботов. Разделы выполняются по порядку.Вариант от root — в конце страницы.

1. Подготовка сервера

  1. Установите пакеты: 
    sudo dnf install nginx unzip curl
    От пакета nginx нужны только /usr/sbin/nginx и /etc/nginx/mime.types. Службам также требуется библиотека ICU для .NET (в образы Docker на Astra и Ubuntu устанавливаетсяlibicu72 / libicu74) — проверьте, что она установлена. nginx -v выводит версию, файл /etc/nginx/mime.types существует
  2. Отключите стандартный юнит nginx, иначе он запустит второй nginx со своим конфигом: 
    sudo systemctl disable --now nginx
    systemctl is-enabled nginx — disabled, systemctl is-active nginx — inactive
  3. Для MachineInfo установите cpuid: 
    sudo dnf install cpuid
    MachineInfo собирает параметры машины для лицензии командами hostname, cpuid и lsblk --nodeps -no serial <Devices:HDD>. Если cpuid не установлен, вместо серийного номера процессора служба возвращает000000000000. cpuid | grep 'processor serial number' выводит строку
  4. Создайте пользователя служб и разрешите его юнитам работать без входа в систему: 
    sudo useradd -m -s /bin/bash orch-user
sudo loginctl enable-linger orch-user
    Без linger службы стартуют только после входа пользователя и останавливаются после выхода. loginctl show-user orch-user --property=Linger — Linger=yes
  5. Создайте каталоги и назначьте их владельцем пользователя служб: 
    sudo mkdir -p /opt/Primo/{MachineInfo,WebApi,RobotLogs,Analytic,Notifications,States,Queues,Licenses,LogEventsWebhook,NuGet2,RDP2,ArcSight,nginx,Data}
sudo chown -R orch-user:orch-user /opt/Primo/{MachineInfo,WebApi,RobotLogs,Analytic,Notifications,States,Queues,Licenses,LogEventsWebhook,NuGet2,RDP2,ArcSight,nginx,Data}
    В каталоге /opt/Primo/Data службы хранят загруженные дистрибутивы, архивы проектов и пакеты. Владелец меняется только у перечисленных каталогов: если на этом же сервере установлен агент, каталоги /opt/Primo/Agent и /opt/Primo/AgentData должны остаться за пользователем агента. ls -l /opt/Primo — владелец перечисленных каталогов orch-user
  6. Скопируйте архивы и файлы nginx в каталог пользователя служб, например в /home/orch-user/dist: 
    sudo mkdir -p /home/orch-user/dist
sudo cp <каталог с файлами поставки>/linux/*.zip <каталог с файлами поставки>/ui/*.zip <каталог с файлами поставки>/data/NGINX/* /home/orch-user/dist/
sudo chown -R orch-user:orch-user /home/orch-user/dist
    Домашний каталог пользователя служб закрыт для других учётных записей, поэтому копирование выполняется через sudo. Файлы nginx — nginx.linux.conf и Primo.Orchestrator.Nginx.user.service — находятся в папке версии orchestrator/data/NGINX/, архив UI4 — в orchestrator/ui/. sudo ls /home/orch-user/dist показывает архивы служб, архив UI4, nginx.linux.conf и юнит nginx

2. СУБД и RabbitMQ

Установите их по инструкции поставщика или используйте существующие. Для Оркестратора требуются:

  • Базы PostgreSQL: ltools, ltoolsidentity, ltoolslicense, ltoolsltwrepo (WebApi), ltoolslogs (RobotLogs), ltoolsanalytic (Analytic), ltoolsnuget (NuGet2). Licenses работает с ltools.
  • Для каждой БД — рабочий пользователь и пользователь миграций (допускается один и тот же). WebApi применяет миграции при каждом старте, поэтому пользователю миграций нужны права на создание объектов, а если базы не созданы заранее — и на создание БД.
  • Пользователь RabbitMQ для служб, порт 5672.

Пример для случая, когда СУБД и RabbitMQ устанавливаются на этот же сервер. Пакеты PostgreSQL и RabbitMQ установите из репозитория ОС или по инструкции поставщика.

  1. Создайте в PostgreSQL пользователя и базы. Пароль задайте собственный, без пробелов: 
    sudo -u postgres psql -c "CREATE ROLE orch LOGIN PASSWORD '<пароль БД>';"
for d in ltools ltoolsidentity ltoolslicense ltoolsltwrepo ltoolslogs ltoolsanalytic ltoolsnuget; do
  sudo -u postgres createdb -O orch $d
done
    команда psql -h localhost -U orch -d ltools -c "select 1" запрашивает пароль и выводит 1
  2. Создайте пользователя RabbitMQ и выдайте ему права: 
    sudo rabbitmqctl add_user orch '<пароль RabbitMQ>'
sudo rabbitmqctl set_permissions -p / orch ".*" ".*" ".*"
    sudo rabbitmqctl list_users показывает пользователя orch

В примере базы принадлежат пользователю orch, поэтому он же применяет миграции. Имя пользователя и пароли указываются в конфигах служб на шаге 4.

3. Пароли для конфигов

Пароли СУБД и RabbitMQ в конфигах указываются зашифрованными. Зашифруйте два пароля, заданные в разделе 2: пароль пользователя БД и пароль пользователя RabbitMQ. Утилиту запускают дважды, по разу на каждый пароль; обе полученные строки понадобятся в разделе 4. Для шифрования используется утилита из архива PasswordEncryptor-linux.

  1. Распакуйте и запустите утилиту:

Минимальные изменения для запуска

Набор изменений, с которым Оркестратор запускается на одном сервере. Файл каждой службы — /opt/Primo/<служба>/appsettings.ProdLinux.json, редактируется под orch-user, например nano /opt/Primo/WebApi/appsettings.ProdLinux.json. Параметры, не названные в списке, оставьте как в файле: почта, приёмник событий, ключ NuGet, каталоги данных для запуска изменять не требуется.

  1. Подключение к RabbitMQ — файлы WebApi, RobotLogs, Analytic, Notifications, States, Queues, Licenses, LogEventsWebhook. В секции RabbitMQ задайте три строки: 
    "Host": "127.0.0.1",
"UserName": "orch",
"Password": "<зашифрованный пароль RabbitMQ>",
  2. Подключение к базам — файлы WebApi (четыре строки), RobotLogs, Analytic, Licenses, NuGet2 (по одной). В каждой строке, которая начинается с PORT=5432;, замените имя пользователя и пароль в конце строки. Было: 
    …;HOST=127.0.0.1;USER ID=postgres;SearchPath=public;PASSWORD=<пример>"
    Стало: 
    …;HOST=127.0.0.1;USER ID=orch;SearchPath=public;PASSWORD=<зашифрованный пароль БД>"
    Строку с базой ltoolssecrets не изменяйте.
  3. Внешний адрес — файл WebApi. Замените адрес из примера в четырёх параметрах: 
    "OrchBaseUrl": "https://<адрес>:44392",
"RobotLogsBaseUrl": "https://<адрес>:44392",
"RdpBaseUrl": "https://<адрес>:44392/rdpstream",
"NuGetBaseUrl": "https://<адрес>:44392",
  4. Адрес WebApi для служб — файлы RobotLogs, Licenses, Queues, RDP2. В секции Orchestrator задайте "BaseUrl": "http://localhost:5001". В файле LogEventsWebhook задайте "LoginUrl": "http://localhost:5001/api/account".
  5. Секция, которой нет в файле — файлы States и Analytic. Добавьте секцию сразу после первой открывающей скобки файла; запятая после закрывающей скобки секции обязательна: 
    {
  "Orchestrator": {
    "BaseUrl": "http://localhost:5001"
  },
  …остальное содержимое файла без изменений
  6. Диск для лицензии — файл MachineInfo. В параметре "HDD" укажите диск сервера с путём, например "/dev/vda". Имя диска выводит команда lsblk --nodeps -no name,serial.

Службы RDP2 и ArcSight для запуска не требуются. RDP2 нужна, только если роботы работают на Windows.

5. nginx и UI4

Шаги также выполняются под orch-user.

  1. Скопируйте конфиг, сертификат и UI: 
    cd ~/dist
# только для стенда: самоподписанный сертификат на адрес сервера
openssl req -x509 -newkey rsa:2048 -nodes -days 365 -keyout cert1.rsa -out cert1.crt -subj "/CN=<адрес>" -addext "subjectAltName=DNS:<имя сервера>,IP:<IP сервера>"
mkdir -p /opt/Primo/nginx/www
cp nginx.linux.conf /opt/Primo/nginx/nginx.conf
cp cert1.crt cert1.rsa /opt/Primo/nginx/
chmod 600 /opt/Primo/nginx/cert1.rsa
unzip -q primo-rpa-orchestrator-ui-*.zip -d /opt/Primo/nginx/www
    Для промышленной установки команду openssl не выполняйте: сертификат на имя сервера выпускает удостоверяющий центр организации, его файлы копируются в ~/dist под именами cert1.crt и cert1.rsa; ключ должен быть без пароля. В subjectAltName укажите имеющиеся значения: только DNS:…, только IP:… или оба. Если у сервера нет DNS-имени, вместо <адрес> подставьте IP и оставьте в subjectAltName только IP:<IP сервера>. /opt/Primo/nginx/www/index.html существует (находится в корне www, а не во вложенной папке)
  2. Установите юнит и запустите nginx: 
    cp Primo.Orchestrator.Nginx.user.service ~/.config/systemd/user/Primo.Orchestrator.Nginx.service
systemctl --user daemon-reload
systemctl --user enable --now Primo.Orchestrator.Nginx
    Перед стартом юнит создаёт logs и temp в /opt/Primo/nginx и проверяет конфиг (nginx -t). Команды в юните записаны без абсолютных путей: mkdir и kill находятся на РЕД ОС и Debian/Astra в разных каталогах, systemd определяет путь автоматически. systemctl --user reload тоже сначала проверяет конфиг: при ошибке в конфиге nginx продолжает работать с прежним. systemctl --user status Primo.Orchestrator.Nginx — active (running); curl -k https://localhost:44392/ возвращает страницу UI

Журналы nginx: /opt/Primo/nginx/logs/nginx_error.log и nginx_access.log (JSON).

7. Машины роботов на РЕД ОС

На каждую машину роботов устанавливается агент. Он всегда работает от пользователя Agent:UserName (по умолчанию agent), общая группа агента и роботов — Agent:GroupName (по умолчанию primo-rpa). Основной вариант — пользовательский юнит: обновление агента из Оркестратора управляет им командой systemctl --user.

Что нужно: архив primo-rpa-orchestrator-agent-<версия>-linux.zip (в нём агент, LTools.Orchestrator.Agent.Runner, appsettings.Runner.json, launch-as-user.expect и юниты), sudo на машине.

  1. Установите пакеты: 
    sudo dnf install expect
    Также требуются: X-сервер — /usr/bin/Xvnc (позволяет просматривать сеанс робота и управлять им) или /usr/bin/Xvfb (без просмотра), /usr/bin/xauth, для Xvnc — /usr/bin/vncpasswd; окружение MATE (/usr/bin/mate-session). ls /usr/bin/expect /usr/bin/mate-session /usr/bin/xauth и ls /usr/bin/Xvnc (или /usr/bin/Xvfb) находят файлы
  2. Создайте группу и пользователя агента, добавьте в группу пользователей роботов: 
    sudo groupadd primo-rpa
sudo useradd -g primo-rpa -m -s /bin/bash agent
sudo usermod -aG primo-rpa <пользователь робота>
    Другие имена — укажите в Agent:UserName и Agent:GroupName. id agent показывает группу primo-rpa
  3. Разрешите агенту запуск роботов и перезагрузку без пароля — файл в /etc/sudoers.d/ (редактируйте через sudo visudo -f /etc/sudoers.d/primo-agent): 
    agent ALL=(root) NOPASSWD: /usr/bin/systemd-run -G --uid=agent --gid=primo-rpa --property=EnvironmentFile=/dev/shm/agent-*-env /opt/Primo/Agent/launch-as-user.expect
agent ALL=(root) NOPASSWD: /usr/bin/systemd-run -G --unit=primo-robot-* --uid=agent --gid=primo-rpa --property=EnvironmentFile=/dev/shm/agent-*-env /opt/Primo/Agent/launch-as-user.expect
agent ALL=(root) NOPASSWD: /usr/bin/systemctl stop primo-robot-*.service
agent ALL=(root) NOPASSWD: /usr/sbin/reboot
    sudo -l -U agent показывает четыре команды
  4. Включите linger и подготовьте каталоги: 
    sudo loginctl enable-linger agent
sudo mkdir -p /opt/Primo/Agent <каталог данных агента> <каталог роботов>
sudo chown agent:primo-rpa /opt/Primo/Agent <каталог данных агента> <каталог роботов>
sudo chmod 775 <каталог роботов>
    Агент работает с UMask=0002, чтобы он и роботы могли удалять файлы друг друга в каталоге проекта.
  5. Откройте входящий 5002/tcp — на этот порт обращается WebApi.
  6. Под пользователем агента распакуйте архив и настройте конфиг: 
    sudo su - agent
export XDG_RUNTIME_DIR=/run/user/$(id -u)
unzip -q -o primo-rpa-orchestrator-agent-*-linux.zip -d /opt/Primo/Agent
cd /opt/Primo/Agent
chmod +x Primo.Orchestrator.Agent LTools.Orchestrator.Agent.Runner launch-as-user.expect
    В appsettings.ProdLinux.json задайте Agent:DataPath и DeployRobot:RobotsPath (по умолчанию C:\LTools — для Linux не подходит). AgentCommands:Session на РЕД ОС допускается не задавать: если параметр пуст, агент использует/usr/bin/mate-session (ОС определяется по NAME в /etc/os-release, который должен начинаться с RED OS).

    Как агент использует команду: сеанс MATE запускается в фоне, через 5 секунд стартует робот, после него выполняется AgentCommands:StopSession (по умолчанию пусто).

  7. Установите и запустите юнит (также под agent): 
    mkdir -p ~/.config/systemd/user
cp /opt/Primo/Agent/Primo.Orchestrator.Agent.user.service ~/.config/systemd/user/Primo.Orchestrator.Agent.service
systemctl --user daemon-reload
systemctl --user enable --now Primo.Orchestrator.Agent
    curl -k https://localhost:5002/api/Version возвращает версию агента; в journalctl --user -u Primo.Orchestrator.Agent нет предупреждений «the launch of robots is impossible»
  8. Зарегистрируйте машину: в UI4 Настройки → Система → Машины роботов, Добавить машину, заполните Наименование и IP/DNS, включите Linux (после сохранения не меняется) и сохраните. в списке машин в колонке Версия агента появилась версия

При старте агент проверяет: доступен ли sudo, есть ли expect, исполняемы ли launch-as-user.expect и команда сеанса, разрешён ли в sudoers вызов systemd-run, существуют ли пользователь и группа. Каждая проблема — отдельное предупреждение в журнале. Подробнее об агенте — Машины роботов и агент.

Вариант от root: если nginx должен слушать порт ниже 1024

Службы работают от root через системные юниты. Вариант используется, если nginx должен слушать порт ниже 1024 (например, 443). Чем отличаются варианты — в начале страницы, в блоке «Linux: службы работают без root»; как перейти с root — Переход с root на работу без root.

  1. Выполните разделы 1–3 без шагов про пользователя orch-user, linger и chown.
  2. Распакуйте архивы командами из раздела 4 через sudo, настройте конфиги.
  3. Установите системные юниты — файлы без .user: 
    for s in MachineInfo WebApi RobotLogs Analytic Notifications States Queues Licenses LogEventsWebhook RDP2 ArcSight; do
  sudo cp /opt/Primo/$s/Primo.Orchestrator.$s.service /etc/systemd/system/
done
sudo cp /opt/Primo/NuGet2/Primo.Orchestrator.NuGet.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now Primo.Orchestrator.MachineInfo
sudo systemctl enable --now Primo.Orchestrator.WebApi
    затем остальные службы в том же порядке, что в разделе 4. systemctl status Primo.Orchestrator.WebApi — active (running)
  4. nginx: файлы — как в разделе 5, но через sudo; юнит Primo.Orchestrator.Nginx.service в /etc/systemd/system/. Главный процесс nginx работает от root, рабочие — от пользователя по умолчанию сборки nginx, поэтому www должен быть доступен всем на чтение (755 / 644). systemctl status Primo.Orchestrator.Nginx — active (running)

В системных юнитах служб, кроме RDP2 и nginx, нет Restart=always: после сбоя служба автоматически не перезапускается. В пользовательских юнитах служб перезапуск через 5 секунд задан.

1. Подготовка сервера

  1. Установите пакеты: 
    sudo apt update
sudo apt install nginx unzip curl libicu74
    От пакета nginx нужны только /usr/sbin/nginx и /etc/nginx/mime.types. libicu74 — библиотека ICU для .NET, она же устанавливается в образ Docker на Ubuntu 24.04. nginx -v выводит версию, файл /etc/nginx/mime.types существует
  2. Отключите стандартный юнит nginx, иначе он запустит второй nginx со своим конфигом: 
    sudo systemctl disable --now nginx
    systemctl is-enabled nginx — disabled, systemctl is-active nginx — inactive
  3. Для MachineInfo установите cpuid: 
    sudo apt install cpuid
    MachineInfo собирает параметры машины для лицензии командами hostname, cpuid и lsblk --nodeps -no serial <Devices:HDD>. Если cpuid не установлен, вместо серийного номера процессора служба возвращает000000000000. cpuid | grep 'processor serial number' выводит строку
  4. Создайте пользователя служб и разрешите его юнитам работать без входа в систему: 
    sudo useradd -m -s /bin/bash orch-user
sudo loginctl enable-linger orch-user
    Без linger службы стартуют только после входа пользователя и останавливаются после выхода. loginctl show-user orch-user --property=Linger — Linger=yes
  5. Создайте каталоги и назначьте их владельцем пользователя служб: 
    sudo mkdir -p /opt/Primo/{MachineInfo,WebApi,RobotLogs,Analytic,Notifications,States,Queues,Licenses,LogEventsWebhook,NuGet2,RDP2,ArcSight,nginx,Data}
sudo chown -R orch-user:orch-user /opt/Primo/{MachineInfo,WebApi,RobotLogs,Analytic,Notifications,States,Queues,Licenses,LogEventsWebhook,NuGet2,RDP2,ArcSight,nginx,Data}
    В каталоге /opt/Primo/Data службы хранят загруженные дистрибутивы, архивы проектов и пакеты. Владелец меняется только у перечисленных каталогов: если на этом же сервере установлен агент, каталоги /opt/Primo/Agent и /opt/Primo/AgentData должны остаться за пользователем агента. ls -l /opt/Primo — владелец перечисленных каталогов orch-user
  6. Скопируйте архивы и файлы nginx в каталог пользователя служб, например в /home/orch-user/dist: 
    sudo mkdir -p /home/orch-user/dist
sudo cp <каталог с файлами поставки>/linux/*.zip <каталог с файлами поставки>/ui/*.zip <каталог с файлами поставки>/data/NGINX/* /home/orch-user/dist/
sudo chown -R orch-user:orch-user /home/orch-user/dist
    Домашний каталог пользователя служб закрыт для других учётных записей, поэтому копирование выполняется через sudo. Файлы nginx — nginx.linux.conf и Primo.Orchestrator.Nginx.user.service — находятся в папке версии orchestrator/data/NGINX/, архив UI4 — в orchestrator/ui/. sudo ls /home/orch-user/dist показывает архивы служб, архив UI4, nginx.linux.conf и юнит nginx
  7. Откройте на файерволе входящий 44392/tcp, если файервол включён. Для ufw: sudo ufw allow 44392/tcp. С сервера должны быть доступны СУБД (5432 для PostgreSQL) и RabbitMQ (5672); при установке на этот же сервер дополнительных действий не требуется.

Параметры, которые возвращает MachineInfo (имя хоста, серийные номера процессора и диска), используются для лицензии. Установитеcpuid, задайте Devices:HDD и имя хоста до запроса лицензии и не изменяйте их после этого.

2. СУБД и RabbitMQ

Установите их по инструкции поставщика или используйте существующие. Для Оркестратора требуются:

  • Базы PostgreSQL: ltools, ltoolsidentity, ltoolslicense, ltoolsltwrepo (WebApi), ltoolslogs (RobotLogs), ltoolsanalytic (Analytic), ltoolsnuget (NuGet2). Licenses работает с ltools.
  • Для каждой БД — рабочий пользователь и пользователь миграций (допускается один и тот же). WebApi применяет миграции при каждом старте, поэтому пользователю миграций нужны права на создание объектов, а если базы не созданы заранее — и на создание БД.
  • Пользователь RabbitMQ для служб, порт 5672.

Пример для случая, когда СУБД и RabbitMQ устанавливаются на этот же сервер. Установка пакетов на Ubuntu 24.04 (PostgreSQL 16, RabbitMQ 3.12): sudo apt install postgresql rabbitmq-server. Обе службы запускаются сразу и включаются в автозапуск.

  1. Создайте в PostgreSQL пользователя и базы. Пароль задайте собственный, без пробелов: 
    sudo -u postgres psql -c "CREATE ROLE orch LOGIN PASSWORD '<пароль БД>';"
for d in ltools ltoolsidentity ltoolslicense ltoolsltwrepo ltoolslogs ltoolsanalytic ltoolsnuget; do
  sudo -u postgres createdb -O orch $d
done
    команда psql -h localhost -U orch -d ltools -c "select 1" запрашивает пароль и выводит 1
  2. Создайте пользователя RabbitMQ и выдайте ему права: 
    sudo rabbitmqctl add_user orch '<пароль RabbitMQ>'
sudo rabbitmqctl set_permissions -p / orch ".*" ".*" ".*"
    sudo rabbitmqctl list_users показывает пользователя orch

В примере базы принадлежат пользователю orch, поэтому он же применяет миграции. Имя пользователя и пароли указываются в конфигах служб на шаге 4.

3. Пароли для конфигов

Пароли СУБД и RabbitMQ в конфигах указываются зашифрованными. Зашифруйте два пароля, заданные в разделе 2: пароль пользователя БД и пароль пользователя RabbitMQ. Утилиту запускают дважды, по разу на каждый пароль; обе полученные строки понадобятся в разделе 4. Для шифрования используется утилита из архива PasswordEncryptor-linux.

  1. Распакуйте и запустите утилиту: 
    unzip primo-rpa-orchestrator-passwordencryptor-*-linux.zip -d ~/encryptor
chmod +x ~/encryptor/Primo.Orchestrator.PasswordEncryptor
~/encryptor/Primo.Orchestrator.PasswordEncryptor
  2. Утилита ничего не выводит и ожидает ввода строки. Введите пароль и нажмите Enter. Если используется собственная сольPRIMOSALT, введите через пробел: <пароль> <соль>. утилита выводит Copy following string: и зашифрованную строку; эта строка вставляется в конфиг. Для выхода нажмите любую клавишу

Пароль не должен содержать пробелов: утилита делит строку по пробелу. Если PRIMOSALT задан, он должен быть одинаковым на всех службах и агентах; в пользовательских юнитах для него есть закомментированная строка #Environment=PRIMOSALT=.

4. Службы Оркестратора

Все шаги этого раздела выполняйте под orch-user, не через sudo: иначе файлы получат владельца root и юниты не запустятся.

  1. Откройте оболочку пользователя служб — войдите по SSH под orch-user или из текущей сессии: 
    sudo su - orch-user
export XDG_RUNTIME_DIR=/run/user/$(id -u)
    whoami — orch-user; systemctl --user status отвечает без ошибки подключения к шине
  2. Распакуйте архивы и сделайте файлы исполняемыми: 
    cd ~/dist
for s in MachineInfo WebApi RobotLogs Analytic Notifications States Queues Licenses LogEventsWebhook RDP2 ArcSight; do
  unzip -q -o primo-rpa-orchestrator-"${s,,}"-*-linux.zip -d /opt/Primo/$s

unzip -q -o primo-rpa-orchestrator-nuget2-*-linux.zip -d /opt/Primo/NuGet2

    Если RDP2 и ArcSight не требуются, исключите их из списка. в каждом каталоге есть исполняемый файл, appsettings.ProdLinux.json и юниты *.service, *.user.service
  3. Настройте appsettings.ProdLinux.json каждой службы — см. «Минимальные изменения для запуска» ниже. Вместо изменения файла допускается добавить в юнит строки Environment=: секция и ключ через двойное подчёркивание, например Environment=RabbitMQ__Host=db01. Переменные окружения перекрывают файл.
  4. Установите пользовательские юниты: 
    mkdir -p ~/.config/systemd/user

  cp /opt/Primo/$s/Primo.Orchestrator.$s.user.service ~/.config/systemd/user/Primo.Orchestrator.$s.service
done
cp /opt/Primo/NuGet2/Primo.Orchestrator.NuGet.user.service ~/.config/systemd/user/Primo.Orchestrator.NuGet.service
systemctl --user daemon-reload
    Файл копируется без .user в имени — по этому имени выполняется управление службой. systemctl --user list-unit-files 'Primo.Orchestrator.*' показывает все юниты
  5. Запустите MachineInfo: 
    systemctl --user enable --now Primo.Orchestrator.MachineInfo

    В поставочном конфиге MachineInfo слушает порт 5051 по HTTPS со встроенным сертификатом, поэтому проверка выполняется с ключом -k. ответ Healthy
  6. Запустите WebApi. При первом запуске служба создаёт таблицы в базах, это занимает около минуты: 
    systemctl --user enable --now Primo.Orchestrator.WebApi

    for u in RobotLogs Analytic Notifications States Queues Licenses LogEventsWebhook NuGet; do
  systemctl --user enable --now Primo.Orchestrator.$u
done

    for p in 56748 56749 56751 56750 5088 5089 56770; do echo "$p $(curl -s http://localhost:$p/health)"; done

Минимальные изменения для запуска

Набор изменений, с которым Оркестратор запускается на одном сервере. Файл каждой службы — /opt/Primo/<служба>/appsettings.ProdLinux.json, редактируется под orch-user, например nano /opt/Primo/WebApi/appsettings.ProdLinux.json. Параметры, не названные в списке, оставьте как в файле: почта, приёмник событий, ключ NuGet, каталоги данных для запуска изменять не требуется.

  1. Подключение к RabbitMQ — файлы WebApi, RobotLogs, Analytic, Notifications, States, Queues, Licenses, LogEventsWebhook. В секции RabbitMQ задайте три строки: 
    "Host": "127.0.0.1",
"UserName": "orch",
"Password": "<зашифрованный пароль RabbitMQ>",
  2. Подключение к базам — файлы WebApi (четыре строки), RobotLogs, Analytic, Licenses, NuGet2 (по одной). В каждой строке, которая начинается с PORT=5432;, замените имя пользователя и пароль в конце строки. Было: 
    …;HOST=127.0.0.1;USER ID=postgres;SearchPath=public;PASSWORD=<пример>"
    Стало: 
    …;HOST=127.0.0.1;USER ID=orch;SearchPath=public;PASSWORD=<зашифрованный пароль БД>"
    Строку с базой ltoolssecrets не изменяйте.
  3. Внешний адрес — файл WebApi. Замените адрес из примера в четырёх параметрах: 
    "OrchBaseUrl": "https://<адрес>:44392",
"RobotLogsBaseUrl": "https://<адрес>:44392",
"RdpBaseUrl": "https://<адрес>:44392/rdpstream",
"NuGetBaseUrl": "https://<адрес>:44392",
  4. Адрес WebApi для служб — файлы RobotLogs, Licenses, Queues, RDP2. В секции Orchestrator задайте "BaseUrl": "http://localhost:5001". В файле LogEventsWebhook задайте "LoginUrl": "http://localhost:5001/api/account".
  5. Секция, которой нет в файле — файлы States и Analytic. Добавьте секцию сразу после первой открывающей скобки файла; запятая после закрывающей скобки секции обязательна: 
    {
  "Orchestrator": {
    "BaseUrl": "http://localhost:5001"
  },
  …остальное содержимое файла без изменений
  6. Диск для лицензии — файл MachineInfo. В параметре "HDD" укажите диск сервера с путём, например "/dev/vda". Имя диска выводит команда lsblk --nodeps -no name,serial.

Службы RDP2 и ArcSight для запуска не требуются. RDP2 нужна, только если роботы работают на Windows.

5. nginx и UI4

Шаги также выполняются под orch-user.

  1. Скопируйте конфиг, сертификат и UI: 
    cd ~/dist
# только для стенда: самоподписанный сертификат на адрес сервера
openssl req -x509 -newkey rsa:2048 -nodes -days 365 -keyout cert1.rsa -out cert1.crt -subj "/CN=<адрес>" -addext "subjectAltName=DNS:<имя сервера>,IP:<IP сервера>"
mkdir -p /opt/Primo/nginx/www
cp nginx.linux.conf /opt/Primo/nginx/nginx.conf
cp cert1.crt cert1.rsa /opt/Primo/nginx/
chmod 600 /opt/Primo/nginx/cert1.rsa
unzip -q primo-rpa-orchestrator-ui-*.zip -d /opt/Primo/nginx/www
    Для промышленной установки команду openssl не выполняйте: сертификат на имя сервера выпускает удостоверяющий центр организации, его файлы копируются в ~/dist под именами cert1.crt и cert1.rsa; ключ должен быть без пароля. В subjectAltName укажите имеющиеся значения: только DNS:…, только IP:… или оба. Если у сервера нет DNS-имени, вместо <адрес> подставьте IP и оставьте в subjectAltName только IP:<IP сервера>. /opt/Primo/nginx/www/index.html существует (находится в корне www, а не во вложенной папке)
  2. Установите юнит и запустите nginx: 
    cp Primo.Orchestrator.Nginx.user.service ~/.config/systemd/user/Primo.Orchestrator.Nginx.service
systemctl --user daemon-reload
systemctl --user enable --now Primo.Orchestrator.Nginx
    Перед стартом юнит создаёт logs и temp в /opt/Primo/nginx и проверяет конфиг (nginx -t). systemctl --user reload тоже сначала проверяет конфиг: при ошибке в конфиге nginx продолжает работать с прежним. systemctl --user status Primo.Orchestrator.Nginx — active (running); curl -k https://localhost:44392/ возвращает страницу UI

Журналы nginx: /opt/Primo/nginx/logs/nginx_error.log и nginx_access.log (JSON).

6. Проверка

  1. Все юниты запущены: 
    systemctl --user list-units 'Primo.Orchestrator.*'
    у всех active running
  2. Откройте в браузере https://<адрес>:44392. При самоподписанном сертификате браузер выводит предупреждение о небезопасном соединении: выберите «Дополнительно» и продолжите. открывается страница входа UI4
  3. Перезагрузите сервер. после перезагрузки все юниты снова active без входа orch-user в систему

    Если RabbitMQ установлен на этом же сервере, после перезагрузки проверьте curl http://localhost:56749/health. Службы Оркестратора запускаются раньше RabbitMQ; Analytic в этом случае остаётся в состоянии Unhealthy и повторно не подключается. Перезапустите её: systemctl --user restart Primo.Orchestrator.Analytic.

Далее — Первый запуск (лицензия, администратор) и Проверка установки.

7. Машины роботов на Ubuntu

На каждую машину роботов устанавливается агент. Он всегда работает от пользователя Agent:UserName (по умолчанию agent), общая группа агента и роботов — Agent:GroupName (по умолчанию primo-rpa). Основной вариант — пользовательский юнит: обновление агента из Оркестратора управляет им командой systemctl --user.

Что нужно: архив primo-rpa-orchestrator-agent-<версия>-linux.zip (в нём агент, LTools.Orchestrator.Agent.Runner, appsettings.Runner.json, launch-as-user.expect и юниты), sudo на машине.

  1. Установите пакеты: 
    sudo apt install expect unzip xvfb xauth x11-utils dbus-x11
    Пакет x11-utils содержит утилиту xprop: без неё запуск роботов завершается без сообщения в интерфейсе. У пользователя робота должен существовать каталог ~/.local/share — подробности на странице Машины роботов и агент. Также требуются: X-сервер — /usr/bin/Xvnc (позволяет просматривать сеанс робота и управлять им) или /usr/bin/Xvfb (без просмотра), /usr/bin/xauth, для Xvnc — /usr/bin/vncpasswd; графическое окружение, команда запуска сеанса которого указывается в шаге 6. ls /usr/bin/expect /usr/bin/xauth и ls /usr/bin/Xvnc (или /usr/bin/Xvfb) находят файлы
  2. Создайте группу и пользователя агента, добавьте в группу пользователей роботов: 
    sudo groupadd primo-rpa
sudo useradd -g primo-rpa -m -s /bin/bash agent
sudo usermod -aG primo-rpa <пользователь робота>
    Другие имена — укажите в Agent:UserName и Agent:GroupName. id agent показывает группу primo-rpa
  3. Разрешите агенту запуск роботов и перезагрузку без пароля — файл в /etc/sudoers.d/ (редактируйте через sudo visudo -f /etc/sudoers.d/primo-agent): 
    agent ALL=(root) NOPASSWD: /usr/bin/systemd-run -G --uid=agent --gid=primo-rpa --property=EnvironmentFile=/dev/shm/agent-*-env /opt/Primo/Agent/launch-as-user.expect
agent ALL=(root) NOPASSWD: /usr/bin/systemd-run -G --unit=primo-robot-* --uid=agent --gid=primo-rpa --property=EnvironmentFile=/dev/shm/agent-*-env /opt/Primo/Agent/launch-as-user.expect
agent ALL=(root) NOPASSWD: /usr/bin/systemctl stop primo-robot-*.service
agent ALL=(root) NOPASSWD: /usr/sbin/reboot
    sudo -l -U agent показывает четыре команды
  4. Включите linger и подготовьте каталоги: 
    sudo loginctl enable-linger agent
sudo mkdir -p /opt/Primo/Agent <каталог данных агента> <каталог роботов>
sudo chown agent:primo-rpa /opt/Primo/Agent <каталог данных агента> <каталог роботов>
sudo chmod 775 <каталог роботов>
    Агент работает с UMask=0002, чтобы он и роботы могли удалять файлы друг друга в каталоге проекта.
  5. Откройте входящий 5002/tcp — на этот порт обращается WebApi.
  6. Под пользователем агента распакуйте архив и настройте конфиг: 
    sudo su - agent
export XDG_RUNTIME_DIR=/run/user/$(id -u)
unzip -q -o primo-rpa-orchestrator-agent-*-linux.zip -d /opt/Primo/Agent
cd /opt/Primo/Agent
chmod +x Primo.Orchestrator.Agent LTools.Orchestrator.Agent.Runner launch-as-user.expect
    В appsettings.ProdLinux.json задайте Agent:DataPath и DeployRobot:RobotsPath (по умолчанию C:\LTools — для Linux не подходит). На Ubuntu обязательно задайте AgentCommands:Session — полный путь к команде запуска графического сеанса (пример в коде — /usr/bin/mate-session). Значение по умолчанию подставляется только для Astra, РЕД ОС и CentOS (по NAME в /etc/os-release); для Ubuntu его нет, и без параметра роботы не запускаются.

    Как агент использует команду: сеанс запускается в фоне, через 5 секунд стартует робот, после него выполняется AgentCommands:StopSession (по умолчанию пусто). Если команда оканчивается на {}, вместо этого скрипт робота подставляется на место {}, и команда завершения не вызывается.

  7. Установите и запустите юнит (также под agent): 
    mkdir -p ~/.config/systemd/user
cp /opt/Primo/Agent/Primo.Orchestrator.Agent.user.service ~/.config/systemd/user/Primo.Orchestrator.Agent.service
systemctl --user daemon-reload
systemctl --user enable --now Primo.Orchestrator.Agent
    curl -k https://localhost:5002/api/Version возвращает версию агента; в journalctl --user -u Primo.Orchestrator.Agent нет предупреждений «the launch of robots is impossible»
  8. Зарегистрируйте машину: в UI4 Настройки → Система → Машины роботов, Добавить машину, заполните Наименование и IP/DNS, включите Linux (после сохранения не меняется) и сохраните. в списке машин в колонке Версия агента появилась версия

При старте агент проверяет: доступен ли sudo, есть ли expect, исполняемы ли launch-as-user.expect и команда сеанса, разрешён ли в sudoers вызов systemd-run, существуют ли пользователь и группа. Каждая проблема — отдельное предупреждение в журнале. Подробнее об агенте — Машины роботов и агент.

Вариант от root: если nginx должен слушать порт ниже 1024

Службы работают от root через системные юниты. Вариант используется, если nginx должен слушать порт ниже 1024 (например, 443). Чем отличаются варианты — в начале страницы, в блоке «Linux: службы работают без root»; как перейти с root — Переход с root на работу без root.

  1. Выполните разделы 1–3 без шагов про пользователя orch-user, linger и chown.
  2. Распакуйте архивы командами из раздела 4 через sudo, настройте конфиги.
  3. Установите системные юниты — файлы без .user: 
    for s in MachineInfo WebApi RobotLogs Analytic Notifications States Queues Licenses LogEventsWebhook RDP2 ArcSight; do
  sudo cp /opt/Primo/$s/Primo.Orchestrator.$s.service /etc/systemd/system/
done
sudo cp /opt/Primo/NuGet2/Primo.Orchestrator.NuGet.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now Primo.Orchestrator.MachineInfo
sudo systemctl enable --now Primo.Orchestrator.WebApi
    затем остальные службы в том же порядке, что в разделе 4. systemctl status Primo.Orchestrator.WebApi — active (running)
  4. nginx: файлы — как в разделе 5, но через sudo; юнит Primo.Orchestrator.Nginx.service в /etc/systemd/system/. Главный процесс nginx работает от root, рабочие — от пользователя сборки nginx (на Ubuntu обычно nobody), поэтому www должен быть доступен всем на чтение (755 / 644). systemctl status Primo.Orchestrator.Nginx — active (running)

В системных юнитах служб, кроме RDP2 и nginx, нет Restart=always: после сбоя служба автоматически не перезапускается. В пользовательских юнитах служб перезапуск через 5 секунд задан.

Установка служб Оркестратора как служб Windows и публикация UI4 через nginx.

Что нужно

  • Архивы служб для Windows: primo-rpa-orchestrator-<служба>-<версия>-windows.zip.
  • Архив UI4, конфиг nginx.win.conf, сертификат cert1.crt/cert1.rsa.
  • Развёрнутые СУБД и RabbitMQ.
  • PowerShell от имени администратора.

Архивы self-contained: установка .NET не требуется.

Службы Оркестратора

Каждый .exe без аргумента --console работает как служба Windows; с --console — как консольное приложение (режим для диагностики).

  1. Задайте окружение на уровне машины (один раз): 
    [System.Environment]::SetEnvironmentVariable('ASPNETCORE_ENVIRONMENT', 'ProdWin', [System.EnvironmentVariableTarget]::Machine)
    в новом окне PowerShell $env:ASPNETCORE_ENVIRONMENT возвращает ProdWin
  2. Распакуйте архив службы, например в C:\Primo\WebApi, и настройте appsettings.ProdWin.json.
  3. Зарегистрируйте и запустите службу: 
    New-Service -Name "Primo.Orchestrator.WebApi" -BinaryPathName "C:\Primo\WebApi\Primo.Orchestrator.WebApi.exe" -DisplayName "Primo.Orchestrator.WebApi" -StartupType Automatic
Start-Service "Primo.Orchestrator.WebApi"
    Get-Service Primo.Orchestrator.WebApi — Running; http://localhost:5001/health отвечает Healthy
  4. Повторите для остальных служб в порядке со страницы Установка.

Второй экземпляр WebApi на том же порту не запускается: при старте экземпляр запрашивает системную блокировку (mutex) по номеру порта и через 2 секунды ожидания завершается с ошибкой. Если служба сразу останавливается — проверьте, не запущена ли копия в консоли.

nginx и UI4

  1. Распакуйте nginx для Windows, например в C:\Primo\nginx-1.21.x.
  2. Замените conf\nginx.conf файлом nginx.win.conf; разместите cert1.crt и cert1.rsa в conf\. nginx -t из каталога nginx не выдаёт ошибок
  3. Содержимое архива UI4 распакуйте в html\ (в конфиге root html), index.html — в корне.
  4. Запустите nginx. UI открывается на https://<адрес>:44392

Конфиг слушает 44392 по HTTPS и проксирует запросы на службы по 127.0.0.1. Журналы — logs\error.log и logs\access.log.

Вариант с IIS не поддерживается. WebApi устанавливается службой Windows за nginx; в его конфиге UseIISIntegration = false.

Как службы читают конфигурацию

Каждая служба читает настройки в таком порядке (следующий источник перекрывает предыдущий):

  1. appsettings.json;
  2. appsettings.<окружение>.json — appsettings.ProdLinux.json или appsettings.ProdWin.json;
  3. аргументы командной строки;
  4. переменные окружения: секция и ключ через двойное подчёркивание, например RabbitMQ__Host.

Окружение задаёт переменная ASPNETCORE_ENVIRONMENT: ProdLinux или ProdWin. Если она не задана, служба сразу завершается с ошибкой.

У WebApi есть режим только миграций: Primo.Orchestrator.WebApi --migration. В этом режиме миграции применяются к четырём БД, ход выводится в консоль (в конце —Migrations done successfully или Migration error: …), API не запускается. Режим подходит для проверки доступа к БД до первого запуска.
