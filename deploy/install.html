Установка

Применимо: 1.26.9WindowsLinuxDocker

Общий порядок установки серверной части и инструкции для каждой ОС на вкладках ниже.

Порядок

Порядок задан зависимостями служб (так же они описаны в depends_on поставочного compose):

  1. СУБД (PostgreSQL или MS SQL Server) и RabbitMQ. к ним можно подключиться с сервера Оркестратора по портам 5432 и 5672
  2. MachineInfo. /health на порту 5051 отвечает Healthy
  3. WebApi. При старте он применяет миграции к БД ltools, ltoolsidentity, ltoolslicense, ltoolsltwrepo. /health на порту 5001 отвечает Healthy, в журнале нет ошибок миграций
  4. Остальные службы: RobotLogs, Analytic, Notifications, States, Queues, Licenses, LogEventsWebhook, NuGet2. каждая отвечает на /health
  5. nginx с UI4 и сертификатом. UI открывается по https://<адрес>:44392
  6. RDP2 — если нужны RDP-сессии.
  7. Агенты на машинах роботов — см. Машины роботов и агент.

Конфигурация служб

Каждая служба читает настройки в таком порядке (следующий источник перекрывает предыдущий):

  1. appsettings.json;
  2. appsettings.<окружение>.json — appsettings.ProdLinux.json или appsettings.ProdWin.json;
  3. аргументы командной строки;
  4. переменные окружения: секция и ключ через двойное подчёркивание, например RabbitMQ__Host.

Окружение задаёт переменная ASPNETCORE_ENVIRONMENT: ProdLinux или ProdWin. Если она не задана, служба сразу завершается с ошибкой.

У WebApi есть режим только миграций: Primo.Orchestrator.WebApi --migration. Он применяет миграции к четырём БД, пишет ход в консоль (в конце — Migrations done successfully или Migration error: …) и не поднимает API. Удобно, чтобы проверить доступ к БД до первого запуска.

По коду процесс в режиме --migration не завершается сам после миграций (хост продолжает работать без API) — проверить на стенде и описать, нужно ли останавливать его вручную.

Установка по ОС

Выберите ОС сервера — на вкладке весь путь установки сверху вниз. Выбор запоминается, а ссылка с адресом вкладки (например, install.html#astra) открывает сразу нужную ОС.

Установка Оркестратора одним файлом docker-compose.yml: PostgreSQL, RabbitMQ, все службы, UI на nginx с HTTPS.

Что нужно

  • Linux-сервер с Docker Engine и плагином docker compose.
  • Доступ к реестру образов Primo RPA.
  • В одном каталоге: docker-compose.yml, nginx.conf (это nginx.docker.conf из поставки), cert1.crt, cert1.rsa.

Шаги

  1. Заполните блок x-globals:
    • tz и TimeOffset — часовой пояс и смещение в часах;
    • culture — язык;
    • base-url — внешний адрес Оркестратора, например https://orch.example.local:44392. Он уходит в NuGet__NuGetBaseUrl, RobotDeployment__OrchBaseUrl, RobotDeployment__RobotLogsBaseUrl.
    в файле не осталось адреса из примера
  2. В сервисе web-api поправьте RDP__RdpBaseUrl: https://<внешний адрес>:44392/rdpstream. адрес совпадает с base-url плюс /rdpstream
  3. Замените все значения в x-secrets. Пароли с суффиксом -encrypted зашифруйте утилитой PasswordEncryptor; открытые и зашифрованные значения должны соответствовать друг другу. в файле нет паролей из примера
  4. primo-machine-key (CustomerBinding__Key у machine-info) — ключ, к которому привязывается лицензия вместо параметров оборудования. Задайте его до запроса лицензии.
  5. В nginx.conf в блоке upstream rdpstream укажите адрес машины с RDP2 (RDP2 работает вне compose). server <адрес RDP2>:5102;
  6. Положите cert1.crt и cert1.rsa рядом с compose. Другие имена — только если поправите пути в nginx.conf. файлы на месте, ключ читается
  7. Войдите в реестр (docker login) и запустите: 
    docker compose up -d
    docker compose ps показывает все сервисы в состоянии healthy
  8. Откройте https://<внешний адрес>:44392. открывается страница входа UI4

Порядок старта задан в compose: web-api ждёт здоровых PostgreSQL, RabbitMQ и machine-info, остальные службы — здоровый web-api. Первый старт web-api дольше обычного: он создаёт и мигрирует БД.

Порты 5432 и 15672 опубликованы на хосте. Если доступ к БД и консоли RabbitMQ извне не нужен — уберите их из ports.

Адрес клиентского реестра в коде указан только в комментарии скрипта сборки (azure/docker.ps1, путь primo-rpa/orchestrator, теги вида <версия>-<дата>-ubuntu). Уточнить адрес, способ получения учётных данных и офлайн-вариант (перенос образов через docker save/load).

Healthcheck сервиса ui обращается к https://localhost:44392/health, но в nginx.docker.conf отдельного location /health нет — запрос обслуживает location / (отдаёт index.html). Работает, но проверяет только nginx. В astra-шаблоне /health есть.

Можно ли менять CustomerBinding__Key после выдачи лицензии — в коде не видно; уточнить у разработки.

Что нужно

  • Архивы служб <Имя>-linux-<версия>.zip из таблицы выше и PasswordEncryptor-linux-<версия>.zip. Архивы self-contained: .NET ставить не нужно. В каждом архиве есть appsettings.ProdLinux.json и два юнита: *.service (от root) и *.user.service (без root).
  • Архив UI4, конфиг nginx.linux.conf, юниты Primo.Orchestrator.Nginx.user.service и Primo.Orchestrator.Nginx.service.
  • Сертификат и ключ на внешнее имя Оркестратора — файлы cert1.crt и cert1.rsa.
  • PostgreSQL (или MS SQL Server) и RabbitMQ — на этом или отдельном сервере.
  • Учётная запись с sudo на сервере.
  • Внешний адрес Оркестратора (DNS-имя или IP), ниже — <адрес>.

Файлы из каталога nginx/ (конфиг, юниты, readme) и архив UI4 в azure/build.ps1 не упаковываются — уточнить, в каком виде они входят в поставку.

1. Подготовка сервера

  1. Установите пакеты: 
    sudo apt update
sudo apt install nginx unzip curl libicu72
    От пакета nginx нужны только /usr/sbin/nginx и /etc/nginx/mime.types. libicu72 — библиотека ICU для .NET, её же ставят в образ Docker на Astra 1.8. nginx -v выводит версию, файл /etc/nginx/mime.types существует
  2. Отключите стандартный юнит nginx, иначе он запустит второй nginx со своим конфигом: 
    sudo systemctl disable --now nginx
    systemctl is-enabled nginx — disabled, systemctl is-active nginx — inactive
  3. Для MachineInfo установите cpuid: 
    sudo apt install cpuid
    MachineInfo собирает параметры машины для лицензии командами hostname, cpuid и lsblk --nodeps -no serial <Devices:HDD>. Если cpuid нет, вместо серийного номера процессора служба отдаёт 000000000000. cpuid | grep 'processor serial number' выводит строку
  4. Создайте пользователя служб и разрешите его юнитам работать без входа в систему: 
    sudo useradd -m -s /bin/bash orch-user
sudo loginctl enable-linger orch-user
    Без linger службы стартуют только после входа пользователя и останавливаются после выхода. loginctl show-user orch-user --property=Linger — Linger=yes
  5. Создайте каталоги и отдайте их пользователю служб: 
    sudo mkdir -p /opt/Primo/{MachineInfo,WebApi,RobotLogs,Analytic,Notifications,States,Queues,Licenses,LogEventsWebhook,NuGet2,RDP2,ArcSight,nginx}
sudo chown -R orch-user:orch-user /opt/Primo
    ls -l /opt/Primo — владелец всех каталогов orch-user
  6. Скопируйте архивы и файлы nginx в домашний каталог пользователя, например в /home/orch-user/dist, и отдайте их ему: sudo chown -R orch-user:orch-user /home/orch-user/dist.
  7. Откройте на файерволе входящий 44392/tcp. С сервера должны быть доступны СУБД (5432 для PostgreSQL) и RabbitMQ (5672).

Параметры, которые отдаёт MachineInfo (имя хоста, серийные номера процессора и диска), используются для лицензии. Поставьте cpuid, задайте Devices:HDD и имя хоста до запроса лицензии и не меняйте их потом.

Обязателен ли cpuid и как смена параметров машины влияет на действующую лицензию — уточнить у разработки. Проверить, отдаёт ли lsblk серийный номер диска без root.

Astra 1.7: в коде нет версии пакета ICU (libicu72 — для 1.8). Уточнить имя пакета для 1.7.

Замкнутая программная среда (ЗПС) Astra: в конвейере подписываются (bsign) только исполняемые файлы образов Docker (azure/sign_image.sh), архивы *-linux.zip в azure/build.ps1 не подписываются. Уточнить, как запускать службы при включённой ЗПС.

Команды открытия порта на файерволе Astra в коде не найдены — дать после проверки на стенде.

2. СУБД и RabbitMQ

Установите их по инструкции поставщика или используйте существующие. Оркестратору нужно:

  • Базы PostgreSQL: ltools, ltoolsidentity, ltoolslicense, ltoolsltwrepo (WebApi), ltoolslogs (RobotLogs), ltoolsanalytic (Analytic), ltoolsnuget (NuGet2). Licenses работает с ltools.
  • Для каждой БД — рабочий пользователь и пользователь миграций (может быть один). WebApi применяет миграции при каждом старте, поэтому пользователю миграций нужны права на создание объектов, а если базы не созданы заранее — и на создание БД.
  • Пользователь RabbitMQ для служб, порт 5672.

Минимальные версии PostgreSQL и RabbitMQ в коде не заданы (в compose — образы postgres:14 и rabbitmq:3-management). Старые доки для Astra/Ubuntu ставили PostgreSQL и RabbitMQ по инструкциям поставщиков и вписывали имя хоста в /etc/hosts для RabbitMQ — в коде не найдено.

3. Пароли для конфигов

Пароли СУБД и RabbitMQ в конфигах указываются зашифрованными. Шифрует их утилита из архива PasswordEncryptor-linux.

  1. Распакуйте и запустите утилиту: 
    unzip PasswordEncryptor-linux-*.zip -d ~/encryptor
chmod +x ~/encryptor/Primo.Orchestrator.PasswordEncryptor
~/encryptor/Primo.Orchestrator.PasswordEncryptor
  2. Утилита ничего не выводит и ждёт строку. Введите пароль и нажмите Enter. Если вы задаёте свою соль PRIMOSALT, введите через пробел: <пароль> <соль>. утилита печатает Copy following string: и зашифрованную строку; её и вставляйте в конфиг. Для выхода нажмите любую клавишу

Пароль не должен содержать пробелов: утилита делит строку по пробелу. Если PRIMOSALT задан, он должен быть одинаковым на всех службах и агентах; в пользовательских юнитах для него есть закомментированная строка #Environment=PRIMOSALT=.

4. Службы Оркестратора

Все шаги этого раздела выполняйте под orch-user, не через sudo: иначе файлы получат владельца root и юниты не запустятся.

  1. Откройте оболочку пользователя служб — войдите по SSH под orch-user или из своей сессии: 
    sudo su - orch-user
export XDG_RUNTIME_DIR=/run/user/$(id -u)
    whoami — orch-user; systemctl --user status отвечает без ошибки подключения к шине
  2. Распакуйте архивы и сделайте файлы исполняемыми: 
    cd ~/dist
for s in MachineInfo WebApi RobotLogs Analytic Notifications States Queues Licenses LogEventsWebhook RDP2 ArcSight; do
  unzip -q -o "$s"-linux-*.zip -d /opt/Primo/$s
  chmod +x /opt/Primo/$s/Primo.Orchestrator.$s
done
unzip -q -o NuGet2-linux-*.zip -d /opt/Primo/NuGet2
chmod +x /opt/Primo/NuGet2/BaGet
    RDP2 и ArcSight уберите из списка, если они не нужны. в каждом каталоге есть исполняемый файл, appsettings.ProdLinux.json и юниты *.service, *.user.service
  3. Настройте appsettings.ProdLinux.json каждой службы (таблица ниже). Вместо правки файла можно добавить в юнит строки Environment=: секция и ключ через двойное подчёркивание, например Environment=RabbitMQ__Host=db01. Переменные окружения перекрывают файл.
  4. Установите пользовательские юниты: 
    mkdir -p ~/.config/systemd/user
for s in MachineInfo WebApi RobotLogs Analytic Notifications States Queues Licenses LogEventsWebhook RDP2 ArcSight; do
  cp /opt/Primo/$s/Primo.Orchestrator.$s.user.service ~/.config/systemd/user/Primo.Orchestrator.$s.service
done
cp /opt/Primo/NuGet2/Primo.Orchestrator.NuGet.user.service ~/.config/systemd/user/Primo.Orchestrator.NuGet.service
systemctl --user daemon-reload
    Файл копируется без .user в имени — по этому имени службой и управляют. systemctl --user list-unit-files 'Primo.Orchestrator.*' показывает все юниты
  5. Запустите MachineInfo: 
    systemctl --user enable --now Primo.Orchestrator.MachineInfo
curl http://localhost:5051/health
    ответ Healthy
  6. Проверьте доступ WebApi к БД в режиме только миграций, затем запустите службу: 
    cd /opt/Primo/WebApi
ASPNETCORE_ENVIRONMENT=ProdLinux ./Primo.Orchestrator.WebApi --migration
# дождитесь строки Migrations done successfully и остановите процесс (Ctrl+C)
systemctl --user enable --now Primo.Orchestrator.WebApi
curl http://localhost:5001/health
    миграции прошли без Migration error; /health отвечает Healthy
  7. Запустите остальные службы: 
    for u in RobotLogs Analytic Notifications States Queues Licenses LogEventsWebhook NuGet; do
  systemctl --user enable --now Primo.Orchestrator.$u
done
    Если нужны — так же запустите Primo.Orchestrator.RDP2 и Primo.Orchestrator.ArcSight. /health отвечает Healthy на портах 56748, 56749, 56751, 56750, 5088, 5089, 56770; curl http://localhost:8081/ отвечает без ошибки; RDP2 — curl -k https://localhost:5102/health

5. nginx и UI4

Тоже под orch-user.

7. Машины роботов на Astra Linux

На каждую машину роботов ставится агент. Он всегда работает от пользователя Agent:UserName (по умолчанию agent), общая группа агента и роботов — Agent:GroupName (по умолчанию primo-rpa). Основной вариант — пользовательский юнит: обновление агента из Оркестратора управляет им командой systemctl --user.

Что нужно: архив Agent-linux-<версия>.zip (в нём агент, LTools.Orchestrator.Agent.Runner, appsettings.Runner.json, launch-as-user.expect и юниты), sudo на машине.

  1. Установите пакеты: 
    sudo apt install expect
    Ещё нужны: X-сервер — /usr/bin/Xvnc (с ним можно смотреть сеанс робота и управлять им) или /usr/bin/Xvfb (без просмотра), /usr/bin/xauth, для Xvnc — /usr/bin/vncpasswd; графическая оболочка Fly (/usr/bin/fly-wm). На Astra 1.8 — ещё /usr/bin/dbus-launch: агент вызывает его перед запуском сеанса робота. ls /usr/bin/expect /usr/bin/fly-wm /usr/bin/xauth и ls /usr/bin/Xvnc (или /usr/bin/Xvfb) находят файлы
  2. Создайте группу и пользователя агента, добавьте в группу пользователей роботов: 
    sudo groupadd primo-rpa
sudo useradd -g primo-rpa -m -s /bin/bash agent
sudo usermod -aG primo-rpa <пользователь робота>
    Другие имена — укажите в Agent:UserName и Agent:GroupName (с 1.26.9). id agent показывает группу primo-rpa
  3. Разрешите агенту запуск роботов и перезагрузку без пароля — файл в /etc/sudoers.d/ (редактируйте через sudo visudo -f /etc/sudoers.d/primo-agent): 
    agent ALL=(root) NOPASSWD: /usr/bin/systemd-run -G --uid=agent --gid=primo-rpa --property=EnvironmentFile=/dev/shm/agent-*-env /opt/Primo/Agent/launch-as-user.expect
agent ALL=(root) NOPASSWD: /usr/sbin/reboot
    sudo -l -U agent показывает обе команды
  4. Включите linger и подготовьте каталоги: 
    sudo loginctl enable-linger agent
sudo mkdir -p /opt/Primo/Agent <каталог данных агента> <каталог роботов>
sudo chown agent:primo-rpa /opt/Primo/Agent <каталог данных агента> <каталог роботов>
sudo chmod 775 <каталог роботов>
    Агент работает с UMask=0002, чтобы он и роботы могли удалять файлы друг друга в каталоге проекта.
  5. Откройте входящий 5002/tcp — на этот порт обращается WebApi.
  6. Под пользователем агента распакуйте архив и настройте конфиг: 
    sudo su - agent
export XDG_RUNTIME_DIR=/run/user/$(id -u)
unzip -q -o Agent-linux-*.zip -d /opt/Primo/Agent
cd /opt/Primo/Agent
chmod +x Primo.Orchestrator.Agent LTools.Orchestrator.Agent.Runner launch-as-user.expect
    В appsettings.ProdLinux.json задайте Agent:DataPath и DeployRobot:RobotsPath (по умолчанию C:\LTools — для Linux не подходит). AgentCommands:Session на Astra можно не задавать: если параметр пуст, агент сам берёт /usr/bin/fly-wm --execOnly {} (определяет ОС по NAME в /etc/os-release).
  7. Установите и запустите юнит (всё ещё под agent): 
    mkdir -p ~/.config/systemd/user
cp /opt/Primo/Agent/Primo.Orchestrator.Agent.user.service ~/.config/systemd/user/Primo.Orchestrator.Agent.service
systemctl --user daemon-reload
systemctl --user enable --now Primo.Orchestrator.Agent
    curl -k https://localhost:5002/api/Version возвращает версию агента; в journalctl --user -u Primo.Orchestrator.Agent нет предупреждений «the launch of robots is impossible»
  8. Зарегистрируйте машину: в UI4 Настройки → Система → Машины роботов, Добавить машину, заполните Наименование и IP/DNS, включите Linux (после сохранения не меняется) и сохраните. в списке машин в колонке Версия агента появилась версия

Скриншот: Настройки → Система → Машины роботов, форма «Добавить машину» с включённым переключателем Linux.

При старте агент сам проверяет: доступен ли sudo, есть ли expect, исполняемы ли launch-as-user.expect и команда сеанса, разрешён ли в sudoers вызов systemd-run, существуют ли пользователь и группа. Каждая проблема — отдельное предупреждение в журнале. Подробнее об агенте — Машины роботов и агент.

Имена пакетов Astra для Xvnc/Xvfb, xauth, vncpasswd, dbus-launch (1.8) в коде не заданы — в коде только пути к файлам (LinuxToolsPaths). Дать список пакетов для 1.7 и 1.8 после проверки. Агент запускает скрипты через /usr/bin/bash — проверить, что этот путь есть на Astra 1.7.

Вариант от root

Службы работают от root через системные юниты. Выбирайте его, если nginx должен слушать порт ниже 1024 (например, 443). Чем отличаются варианты и как переключиться — Службы Linux без root.

  1. Выполните разделы 1–3 без шагов про пользователя orch-user, linger и chown.
  2. Распакуйте архивы командами из раздела 4 через sudo, настройте конфиги.
  3. Установите системные юниты — файлы без .user: 
    for s in MachineInfo WebApi RobotLogs Analytic Notifications States Queues Licenses LogEventsWebhook RDP2 ArcSight; do
  sudo cp /opt/Primo/$s/Primo.Orchestrator.$s.service /etc/systemd/system/
done
sudo cp /opt/Primo/NuGet2/Primo.Orchestrator.NuGet.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now Primo.Orchestrator.MachineInfo
sudo systemctl enable --now Primo.Orchestrator.WebApi
    затем остальные службы в том же порядке, что в разделе 4. systemctl status Primo.Orchestrator.WebApi — active (running)
  4. nginx: файлы — как в разделе 5, но через sudo; юнит Primo.Orchestrator.Nginx.service в /etc/systemd/system/. Главный процесс nginx работает от root, рабочие — от пользователя сборки nginx (на Astra обычно nobody), поэтому www должен быть доступен всем на чтение (755 / 644). systemctl status Primo.Orchestrator.Nginx — active (running)

В системных юнитах служб, кроме RDP2 и nginx, нет Restart=always: упавшая служба сама не перезапустится. В пользовательских юнитах служб перезапуск через 5 секунд задан.

Старые доки: «службы устанавливаются и работают от root». В 1.26.9 в каждом архиве есть пользовательский юнит, а у nginx — отдельная инструкция без root; целевая схема — без root. Строка DOTNET_ROOT=/usr/lib64/dotnet во всех юнитах при self-contained сборке, вероятно, не нужна — уточнить у разработки.

1. Подготовка сервера

  1. Установите пакеты: 
    sudo dnf install nginx unzip curl
    От пакета nginx нужны только /usr/sbin/nginx и /etc/nginx/mime.types. Ещё службам нужна библиотека ICU для .NET (в образах Docker на Astra и Ubuntu ставят libicu72 / libicu74) — проверьте, что она установлена. nginx -v выводит версию, файл /etc/nginx/mime.types существует
  2. Отключите стандартный юнит nginx, иначе он запустит второй nginx со своим конфигом: 
    sudo systemctl disable --now nginx
    systemctl is-enabled nginx — disabled, systemctl is-active nginx — inactive
  3. Для MachineInfo установите cpuid: 
    sudo dnf install cpuid
    MachineInfo собирает параметры машины для лицензии командами hostname, cpuid и lsblk --nodeps -no serial <Devices:HDD>. Если cpuid нет, вместо серийного номера процессора служба отдаёт 000000000000. cpuid | grep 'processor serial number' выводит строку
  4. Создайте пользователя служб и разрешите его юнитам работать без входа в систему: 
    sudo useradd -m -s /bin/bash orch-user
sudo loginctl enable-linger orch-user
    Без linger службы стартуют только после входа пользователя и останавливаются после выхода. loginctl show-user orch-user --property=Linger — Linger=yes
  5. Создайте каталоги и отдайте их пользователю служб: 
    sudo mkdir -p /opt/Primo/{MachineInfo,WebApi,RobotLogs,Analytic,Notifications,States,Queues,Licenses,LogEventsWebhook,NuGet2,RDP2,ArcSight,nginx}
sudo chown -R orch-user:orch-user /opt/Primo
    ls -l /opt/Primo — владелец всех каталогов orch-user
  6. Скопируйте архивы и файлы nginx в домашний каталог пользователя, например в /home/orch-user/dist, и отдайте их ему: sudo chown -R orch-user:orch-user /home/orch-user/dist.
  7. Откройте на файерволе входящий 44392/tcp. С сервера должны быть доступны СУБД (5432 для PostgreSQL) и RabbitMQ (5672).

Параметры, которые отдаёт MachineInfo (имя хоста, серийные номера процессора и диска), используются для лицензии. Поставьте cpuid, задайте Devices:HDD и имя хоста до запроса лицензии и не меняйте их потом.

Обязателен ли cpuid и как смена параметров машины влияет на действующую лицензию — уточнить у разработки. Проверить, отдаёт ли lsblk серийный номер диска без root.

Имена пакетов ICU и cpuid в репозиториях РЕД ОС в коде не найдены (в Dockerfile только libicu72/libicu74 для Astra/Ubuntu) — проверить на РЕД ОС 7.3 и 8. Старые доки для РЕД ОС 8 ставили для WebApi пакет gssntlmssp; в коде упоминаний нет — уточнить, нужен ли он для входа через AD.

Файервол: в коде команд нет. Старые доки (РЕД ОС 8) открывали порты так: sudo firewall-cmd --zone=public --add-port=44392/tcp --permanent, затем sudo firewall-cmd --reload — подтвердить. Старые доки также открывали наружу 5432, 5672, 15672, 25672, 56748, 5051; по конфигу nginx снаружи нужен только 44392.

SELinux: старые доки (РЕД ОС 8) требовали отключить его в /etc/selinux/config. В коде упоминаний SELinux нет — проверить, работают ли юниты и nginx из /opt/Primo с включённым SELinux.

2. СУБД и RabbitMQ

Установите их по инструкции поставщика или используйте существующие. Оркестратору нужно:

  • Базы PostgreSQL: ltools, ltoolsidentity, ltoolslicense, ltoolsltwrepo (WebApi), ltoolslogs (RobotLogs), ltoolsanalytic (Analytic), ltoolsnuget (NuGet2). Licenses работает с ltools.
  • Для каждой БД — рабочий пользователь и пользователь миграций (может быть один). WebApi применяет миграции при каждом старте, поэтому пользователю миграций нужны права на создание объектов, а если базы не созданы заранее — и на создание БД.
  • Пользователь RabbitMQ для служб, порт 5672.

Минимальные версии PostgreSQL и RabbitMQ в коде не заданы (в compose — образы postgres:14 и rabbitmq:3-management). Старые доки для РЕД ОС 8 ставили их из репозитория (dnf install rabbitmq-server, postgresql15-server) — в коде не найдено, версии подтвердить.

3. Пароли для конфигов

Пароли СУБД и RabbitMQ в конфигах указываются зашифрованными. Шифрует их утилита из архива PasswordEncryptor-linux.

  1. Распакуйте и запустите утилиту: 
    unzip PasswordEncryptor-linux-*.zip -d ~/encryptor
chmod +x ~/encryptor/Primo.Orchestrator.PasswordEncryptor
~/encryptor/Primo.Orchestrator.PasswordEncryptor
  2. Утилита ничего не выводит и ждёт строку. Введите пароль и нажмите Enter. Если вы задаёте свою соль PRIMOSALT, введите через пробел: <пароль> <соль>. утилита печатает Copy following string: и зашифрованную строку; её и вставляйте в конфиг. Для выхода нажмите любую клавишу

Пароль не должен содержать пробелов: утилита делит строку по пробелу. Если PRIMOSALT задан, он должен быть одинаковым на всех службах и агентах; в пользовательских юнитах для него есть закомментированная строка #Environment=PRIMOSALT=.

4. Службы Оркестратора

Все шаги этого раздела выполняйте под orch-user, не через sudo: иначе файлы получат владельца root и юниты не запустятся.

  1. Откройте оболочку пользователя служб — войдите по SSH под orch-user или из своей сессии: 
    sudo su - orch-user
export XDG_RUNTIME_DIR=/run/user/$(id -u)
    whoami — orch-user; systemctl --user status отвечает без ошибки подключения к шине
  2. Распакуйте архивы и сделайте файлы исполняемыми: 
    cd ~/dist
for s in MachineInfo WebApi RobotLogs Analytic Notifications States Queues Licenses LogEventsWebhook RDP2 ArcSight; do
  unzip -q -o "$s"-linux-*.zip -d /opt/Primo/$s
  chmod +x /opt/Primo/$s/Primo.Orchestrator.$s
done
unzip -q -o NuGet2-linux-*.zip -d /opt/Primo/NuGet2
chmod +x /opt/Primo/NuGet2/BaGet
    RDP2 и ArcSight уберите из списка, если они не нужны. в каждом каталоге есть исполняемый файл, appsettings.ProdLinux.json и юниты *.service, *.user.service
  3. Настройте appsettings.ProdLinux.json каждой службы (таблица ниже). Вместо правки файла можно добавить в юнит строки Environment=: секция и ключ через двойное подчёркивание, например Environment=RabbitMQ__Host=db01. Переменные окружения перекрывают файл.
  4. Установите пользовательские юниты: 
    mkdir -p ~/.config/systemd/user
for s in MachineInfo WebApi RobotLogs Analytic Notifications States Queues Licenses LogEventsWebhook RDP2 ArcSight; do
  cp /opt/Primo/$s/Primo.Orchestrator.$s.user.service ~/.config/systemd/user/Primo.Orchestrator.$s.service
done
cp /opt/Primo/NuGet2/Primo.Orchestrator.NuGet.user.service ~/.config/systemd/user/Primo.Orchestrator.NuGet.service
systemctl --user daemon-reload

7. Машины роботов на РЕД ОС

На каждую машину роботов ставится агент. Он всегда работает от пользователя Agent:UserName (по умолчанию agent), общая группа агента и роботов — Agent:GroupName (по умолчанию primo-rpa). Основной вариант — пользовательский юнит: обновление агента из Оркестратора управляет им командой systemctl --user.

Что нужно: архив Agent-linux-<версия>.zip (в нём агент, LTools.Orchestrator.Agent.Runner, appsettings.Runner.json, launch-as-user.expect и юниты), sudo на машине.

  1. Установите пакеты: 
    sudo dnf install expect
    Ещё нужны: X-сервер — /usr/bin/Xvnc (с ним можно смотреть сеанс робота и управлять им) или /usr/bin/Xvfb (без просмотра), /usr/bin/xauth, для Xvnc — /usr/bin/vncpasswd; окружение MATE (/usr/bin/mate-session). ls /usr/bin/expect /usr/bin/mate-session /usr/bin/xauth и ls /usr/bin/Xvnc (или /usr/bin/Xvfb) находят файлы
  2. Создайте группу и пользователя агента, добавьте в группу пользователей роботов: 
    sudo groupadd primo-rpa
sudo useradd -g primo-rpa -m -s /bin/bash agent
sudo usermod -aG primo-rpa <пользователь робота>
    Другие имена — укажите в Agent:UserName и Agent:GroupName (с 1.26.9). id agent показывает группу primo-rpa
  3. Разрешите агенту запуск роботов и перезагрузку без пароля — файл в /etc/sudoers.d/ (редактируйте через sudo visudo -f /etc/sudoers.d/primo-agent): 
    agent ALL=(root) NOPASSWD: /usr/bin/systemd-run -G --uid=agent --gid=primo-rpa --property=EnvironmentFile=/dev/shm/agent-*-env /opt/Primo/Agent/launch-as-user.expect
agent ALL=(root) NOPASSWD: /usr/sbin/reboot
    sudo -l -U agent показывает обе команды
  4. Включите linger и подготовьте каталоги: 
    sudo loginctl enable-linger agent
sudo mkdir -p /opt/Primo/Agent <каталог данных агента> <каталог роботов>
sudo chown agent:primo-rpa /opt/Primo/Agent <каталог данных агента> <каталог роботов>
sudo chmod 775 <каталог роботов>
    Агент работает с UMask=0002, чтобы он и роботы могли удалять файлы друг друга в каталоге проекта.
  5. Откройте входящий 5002/tcp — на этот порт обращается WebApi.
  6. Под пользователем агента распакуйте архив и настройте конфиг: 
    sudo su - agent
export XDG_RUNTIME_DIR=/run/user/$(id -u)
unzip -q -o Agent-linux-*.zip -d /opt/Primo/Agent
cd /opt/Primo/Agent
chmod +x Primo.Orchestrator.Agent LTools.Orchestrator.Agent.Runner launch-as-user.expect
    В appsettings.ProdLinux.json задайте Agent:DataPath и DeployRobot:RobotsPath (по умолчанию C:\LTools — для Linux не подходит). AgentCommands:Session на РЕД ОС можно не задавать: если параметр пуст, агент сам берёт /usr/bin/mate-session (определяет ОС по NAME в /etc/os-release, который должен начинаться с RED OS).

    Как агент использует команду: сеанс MATE запускается в фоне, через 5 секунд стартует робот, после него выполняется AgentCommands:StopSession (по умолчанию пусто).

  7. Установите и запустите юнит (всё ещё под agent): 
    mkdir -p ~/.config/systemd/user
cp /opt/Primo/Agent/Primo.Orchestrator.Agent.user.service ~/.config/systemd/user/Primo.Orchestrator.Agent.service
systemctl --user daemon-reload
systemctl --user enable --now Primo.Orchestrator.Agent
    curl -k https://localhost:5002/api/Version возвращает версию агента; в journalctl --user -u Primo.Orchestrator.Agent нет предупреждений «the launch of robots is impossible»
  8. Зарегистрируйте машину: в UI4 Настройки → Система → Машины роботов, Добавить машину, заполните Наименование и IP/DNS, включите Linux (после сохранения не меняется) и сохраните. в списке машин в колонке Версия агента появилась версия

Скриншот: Настройки → Система → Машины роботов, форма «Добавить машину» с включённым переключателем Linux.

При старте агент сам проверяет: доступен ли sudo, есть ли expect, исполняемы ли launch-as-user.expect и команда сеанса, разрешён ли в sudoers вызов systemd-run, существуют ли пользователь и группа. Каждая проблема — отдельное предупреждение в журнале. Подробнее об агенте — Машины роботов и агент.

Имена пакетов РЕД ОС для Xvnc/Xvfb, xauth, vncpasswd, MATE в коде не заданы — в коде только пути к файлам (LinuxToolsPaths). Нужна ли команда StopSession для MATE — уточнить у разработки.

Вариант от root

Службы работают от root через системные юниты. Выбирайте его, если nginx должен слушать порт ниже 1024 (например, 443). Чем отличаются варианты и как переключиться — Службы Linux без root.

  1. Выполните разделы 1–3 без шагов про пользователя orch-user, linger и chown.
  2. Распакуйте архивы командами из раздела 4 через sudo, настройте конфиги.
  3. Установите системные юниты — файлы без .user: 
    for s in MachineInfo WebApi RobotLogs Analytic Notifications States Queues Licenses LogEventsWebhook RDP2 ArcSight; do
  sudo cp /opt/Primo/$s/Primo.Orchestrator.$s.service /etc/systemd/system/
done
sudo cp /opt/Primo/NuGet2/Primo.Orchestrator.NuGet.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now Primo.Orchestrator.MachineInfo
sudo systemctl enable --now Primo.Orchestrator.WebApi
    затем остальные службы в том же порядке, что в разделе 4. systemctl status Primo.Orchestrator.WebApi — active (running)
  4. nginx: файлы — как в разделе 5, но через sudo; юнит Primo.Orchestrator.Nginx.service в /etc/systemd/system/. Главный процесс nginx работает от root, рабочие — от пользователя по умолчанию сборки nginx, поэтому www должен быть доступен всем на чтение (755 / 644). systemctl status Primo.Orchestrator.Nginx — active (running)

В системных юнитах служб, кроме RDP2 и nginx, нет Restart=always: упавшая служба сама не перезапустится. В пользовательских юнитах служб перезапуск через 5 секунд задан.

Старые доки: «службы устанавливаются и работают от root». В 1.26.9 в каждом архиве есть пользовательский юнит, а у nginx — отдельная инструкция без root; целевая схема — без root. Строка DOTNET_ROOT=/usr/lib64/dotnet во всех юнитах при self-contained сборке, вероятно, не нужна — уточнить у разработки.

1. Подготовка сервера

  1. Установите пакеты: 
    sudo apt update
sudo apt install nginx unzip curl libicu74
    От пакета nginx нужны только /usr/sbin/nginx и /etc/nginx/mime.types. libicu74 — библиотека ICU для .NET, её же ставят в образ Docker на Ubuntu 24.04. nginx -v выводит версию, файл /etc/nginx/mime.types существует
  2. Отключите стандартный юнит nginx, иначе он запустит второй nginx со своим конфигом: 
    sudo systemctl disable --now nginx
    systemctl is-enabled nginx — disabled, systemctl is-active nginx — inactive
  3. Для MachineInfo установите cpuid: 
    sudo apt install cpuid
    MachineInfo собирает параметры машины для лицензии командами hostname, cpuid и lsblk --nodeps -no serial <Devices:HDD>. Если cpuid нет, вместо серийного номера процессора служба отдаёт 000000000000. cpuid | grep 'processor serial number' выводит строку
  4. Создайте пользователя служб и разрешите его юнитам работать без входа в систему: 
    sudo useradd -m -s /bin/bash orch-user
sudo loginctl enable-linger orch-user
    Без linger службы стартуют только после входа пользователя и останавливаются после выхода. loginctl show-user orch-user --property=Linger — Linger=yes
  5. Создайте каталоги и отдайте их пользователю служб: 
    sudo mkdir -p /opt/Primo/{MachineInfo,WebApi,RobotLogs,Analytic,Notifications,States,Queues,Licenses,LogEventsWebhook,NuGet2,RDP2,ArcSight,nginx}
sudo chown -R orch-user:orch-user /opt/Primo
    ls -l /opt/Primo — владелец всех каталогов orch-user
  6. Скопируйте архивы и файлы nginx в домашний каталог пользователя, например в /home/orch-user/dist, и отдайте их ему: sudo chown -R orch-user:orch-user /home/orch-user/dist.
  7. Откройте на файерволе входящий 44392/tcp. С сервера должны быть доступны СУБД (5432 для PostgreSQL) и RabbitMQ (5672).

Параметры, которые отдаёт MachineInfo (имя хоста, серийные номера процессора и диска), используются для лицензии. Поставьте cpuid, задайте Devices:HDD и имя хоста до запроса лицензии и не меняйте их потом.

Обязателен ли cpuid и как смена параметров машины влияет на действующую лицензию — уточнить у разработки. Проверить, отдаёт ли lsblk серийный номер диска без root.

Имя пакета ICU указано для Ubuntu 24.04 (как в образе Docker). Для других версий Ubuntu — уточнить.

Команды открытия порта на файерволе Ubuntu в коде не найдены — дать после проверки на стенде.

2. СУБД и RabbitMQ

Установите их по инструкции поставщика или используйте существующие. Оркестратору нужно:

  • Базы PostgreSQL: ltools, ltoolsidentity, ltoolslicense, ltoolsltwrepo (WebApi), ltoolslogs (RobotLogs), ltoolsanalytic (Analytic), ltoolsnuget (NuGet2). Licenses работает с ltools.
  • Для каждой БД — рабочий пользователь и пользователь миграций (может быть один). WebApi применяет миграции при каждом старте, поэтому пользователю миграций нужны права на создание объектов, а если базы не созданы заранее — и на создание БД.
  • Пользователь RabbitMQ для служб, порт 5672.

Минимальные версии PostgreSQL и RabbitMQ в коде не заданы (в compose — образы postgres:14 и rabbitmq:3-management). Старые доки для Astra/Ubuntu ставили PostgreSQL и RabbitMQ по инструкциям поставщиков и вписывали имя хоста в /etc/hosts для RabbitMQ — в коде не найдено.

7. Машины роботов на Ubuntu

На каждую машину роботов ставится агент. Он всегда работает от пользователя Agent:UserName (по умолчанию agent), общая группа агента и роботов — Agent:GroupName (по умолчанию primo-rpa). Основной вариант — пользовательский юнит: обновление агента из Оркестратора управляет им командой systemctl --user.

Что нужно: архив Agent-linux-<версия>.zip (в нём агент, LTools.Orchestrator.Agent.Runner, appsettings.Runner.json, launch-as-user.expect и юниты), sudo на машине.

  1. Установите пакеты: 
    sudo apt install expect
    Ещё нужны: X-сервер — /usr/bin/Xvnc (с ним можно смотреть сеанс робота и управлять им) или /usr/bin/Xvfb (без просмотра), /usr/bin/xauth, для Xvnc — /usr/bin/vncpasswd; графическое окружение, команду запуска сеанса которого вы укажете в шаге 6. ls /usr/bin/expect /usr/bin/xauth и ls /usr/bin/Xvnc (или /usr/bin/Xvfb) находят файлы
  2. Создайте группу и пользователя агента, добавьте в группу пользователей роботов: 
    sudo groupadd primo-rpa
sudo useradd -g primo-rpa -m -s /bin/bash agent
sudo usermod -aG primo-rpa <пользователь робота>
    Другие имена — укажите в Agent:UserName и Agent:GroupName (с 1.26.9). id agent показывает группу primo-rpa
  3. Разрешите агенту запуск роботов и перезагрузку без пароля — файл в /etc/sudoers.d/ (редактируйте через sudo visudo -f /etc/sudoers.d/primo-agent): 
    agent ALL=(root) NOPASSWD: /usr/bin/systemd-run -G --uid=agent --gid=primo-rpa --property=EnvironmentFile=/dev/shm/agent-*-env /opt/Primo/Agent/launch-as-user.expect
agent ALL=(root) NOPASSWD: /usr/sbin/reboot
    sudo -l -U agent показывает обе команды
  4. Включите linger и подготовьте каталоги: 
    sudo loginctl enable-linger agent
sudo mkdir -p /opt/Primo/Agent <каталог данных агента> <каталог роботов>
sudo chown agent:primo-rpa /opt/Primo/Agent <каталог данных агента> <каталог роботов>
sudo chmod 775 <каталог роботов>
    Агент работает с UMask=0002, чтобы он и роботы могли удалять файлы друг друга в каталоге проекта.
  5. Откройте входящий 5002/tcp — на этот порт обращается WebApi.
  6. Под пользователем агента распакуйте архив и настройте конфиг: 
    sudo su - agent
export XDG_RUNTIME_DIR=/run/user/$(id -u)
unzip -q -o Agent-linux-*.zip -d /opt/Primo/Agent
cd /opt/Primo/Agent
chmod +x Primo.Orchestrator.Agent LTools.Orchestrator.Agent.Runner launch-as-user.expect
    В appsettings.ProdLinux.json задайте Agent:DataPath и DeployRobot:RobotsPath (по умолчанию C:\LTools — для Linux не подходит). На Ubuntu обязательно задайте AgentCommands:Session — полный путь к команде запуска графического сеанса (пример в коде — /usr/bin/mate-session). Значение по умолчанию агент подставляет только для Astra, РЕД ОС и CentOS (по NAME в /etc/os-release); для Ubuntu его нет, и без параметра роботы не запустятся.

    Как агент использует команду: сеанс запускается в фоне, через 5 секунд стартует робот, после него выполняется AgentCommands:StopSession (по умолчанию пусто). Если команда оканчивается на {}, вместо этого скрипт робота подставляется на место {}, и команда завершения не вызывается.

  7. Установите и запустите юнит (всё ещё под agent): 
    mkdir -p ~/.config/systemd/user
cp /opt/Primo/Agent/Primo.Orchestrator.Agent.user.service ~/.config/systemd/user/Primo.Orchestrator.Agent.service
systemctl --user daemon-reload
systemctl --user enable --now Primo.Orchestrator.Agent
    curl -k https://localhost:5002/api/Version возвращает версию агента; в journalctl --user -u Primo.Orchestrator.Agent нет предупреждений «the launch of robots is impossible»
  8. Зарегистрируйте машину: в UI4 Настройки → Система → Машины роботов, Добавить машину, заполните Наименование и IP/DNS, включите Linux (после сохранения не меняется) и сохраните. в списке машин в колонке Версия агента появилась версия

Скриншот: Настройки → Система → Машины роботов, форма «Добавить машину» с включённым переключателем Linux.

При старте агент сам проверяет: доступен ли sudo, есть ли expect, исполняемы ли launch-as-user.expect и команда сеанса, разрешён ли в sudoers вызов systemd-run, существуют ли пользователь и группа. Каждая проблема — отдельное предупреждение в журнале. Подробнее об агенте — Машины роботов и агент.

Проверенное значение AgentCommands:Session (и при необходимости StopSession) для Ubuntu и графическое окружение для роботов в коде не заданы. Имена пакетов Ubuntu для Xvnc/Xvfb, xauth, vncpasswd — тоже: в коде только пути к файлам (LinuxToolsPaths). Дать после проверки на стенде.

Вариант от root

Службы работают от root через системные юниты. Выбирайте его, если nginx должен слушать порт ниже 1024 (например, 443). Чем отличаются варианты и как переключиться — Службы Linux без root.

  1. Выполните разделы 1–3 без шагов про пользователя orch-user, linger и chown.
  2. Распакуйте архивы командами из раздела 4 через sudo, настройте конфиги.
  3. Установите системные юниты — файлы без .user: 
    for s in MachineInfo WebApi RobotLogs Analytic Notifications States Queues Licenses LogEventsWebhook RDP2 ArcSight; do
  sudo cp /opt/Primo/$s/Primo.Orchestrator.$s.service /etc/systemd/system/
done
sudo cp /opt/Primo/NuGet2/Primo.Orchestrator.NuGet.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now Primo.Orchestrator.MachineInfo
sudo systemctl enable --now Primo.Orchestrator.WebApi
    затем остальные службы в том же порядке, что в разделе 4. systemctl status Primo.Orchestrator.WebApi — active (running)
  4. nginx: файлы — как в разделе 5, но через sudo; юнит Primo.Orchestrator.Nginx.service в /etc/systemd/system/. Главный процесс nginx работает от root, рабочие — от пользователя сборки nginx (на Ubuntu обычно nobody), поэтому www должен быть доступен всем на чтение (755 / 644). systemctl status Primo.Orchestrator.Nginx — active (running)

В системных юнитах служб, кроме RDP2 и nginx, нет Restart=always: упавшая служба сама не перезапустится. В пользовательских юнитах служб перезапуск через 5 секунд задан.

Старые доки: «службы устанавливаются и работают от root». В 1.26.9 в каждом архиве есть пользовательский юнит, а у nginx — отдельная инструкция без root; целевая схема — без root. Строка DOTNET_ROOT=/usr/lib64/dotnet во всех юнитах при self-contained сборке, вероятно, не нужна — уточнить у разработки.

Установка служб Оркестратора как служб Windows и публикация UI4 через nginx.

Что нужно

  • Архивы служб для Windows (без суффикса -linux).
  • Архив UI4, конфиг nginx.win.conf, сертификат cert1.crt/cert1.rsa.
  • Готовые СУБД и RabbitMQ.
  • PowerShell от имени администратора.

Архивы self-contained: .NET ставить не нужно.

Службы Оркестратора

Каждый .exe без аргумента --console работает как служба Windows; с --console — как консольное приложение (удобно для диагностики).

  1. Задайте окружение на уровне машины (один раз): 
    [System.Environment]::SetEnvironmentVariable('ASPNETCORE_ENVIRONMENT', 'ProdWin', [System.EnvironmentVariableTarget]::Machine)
    в новом окне PowerShell $env:ASPNETCORE_ENVIRONMENT возвращает ProdWin
  2. Распакуйте архив службы, например в C:\Primo\WebApi, и настройте appsettings.ProdWin.json.
  3. Зарегистрируйте и запустите службу: 
    New-Service -Name "Primo.Orchestrator.WebApi" -BinaryPathName "C:\Primo\WebApi\Primo.Orchestrator.WebApi.exe" -DisplayName "Primo.Orchestrator.WebApi" -StartupType Automatic
Start-Service "Primo.Orchestrator.WebApi"
    Get-Service Primo.Orchestrator.WebApi — Running; http://localhost:5001/health отвечает Healthy
  4. Повторите для остальных служб в порядке со страницы Установка.

Второй экземпляр WebApi на том же порту не запустится: при старте он берёт системную блокировку (mutex) по номеру порта и через 2 секунды ожидания завершается с ошибкой. Если служба сразу останавливается — проверьте, не запущена ли копия в консоли.

nginx и UI4

  1. Распакуйте nginx для Windows, например в C:\Primo\nginx-1.21.x.
  2. Замените conf\nginx.conf файлом nginx.win.conf; положите cert1.crt и cert1.rsa в conf\. nginx -t из каталога nginx не выдаёт ошибок
  3. Содержимое архива UI4 распакуйте в html\ (в конфиге root html), index.html — в корне.
  4. Запустите nginx. UI открывается на https://<адрес>:44392

Конфиг слушает 44392 по HTTPS и проксирует запросы на службы по 127.0.0.1. Журналы — logs\error.log и logs\access.log.

Вариант с IIS не поддерживается. WebApi ставится службой Windows за nginx; в его конфиге UseIISIntegration = false.

Скрипт регистрации служб сервера на Windows в выгрузке не найден; команды New-Service выше — по образцу PrimoWorker.ps1 агента. Имена служб для остальных компонентов (Primo.Orchestrator.<Имя>) и учётную запись службы подтвердить.
