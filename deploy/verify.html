Проверка установки

Применимо: 1.26.9WindowsLinuxDocker

На странице описана проверка Оркестратора после установки: службы запущены и отвечают, агенты доступны, тестовый проект выполняется на роботе, результат записывается в журнал. Та же проверка выполняется после каждого обновления.

Результаттестовый проект выполнен, журнал робота открывается

Этап 1 из 3

Службы запущены

  1. Выполните docker compose ps. у всех сервисов статус healthy; compose автоматически опрашивает /health каждые 30 секунд
  2. Если сервис unhealthy — docker compose logs <сервис>. Службы пишут журнал в консоль в формате JSON.
  1. Под пользователем служб: systemctl --user status Primo.Orchestrator.<Имя>. Для варианта от root — sudo systemctl status …. active (running)
  2. Журнал службы: journalctl --user -t Primo.Orchestrator.<Имя> (от root — без --user); имя задано в юните (SyslogIdentifier).
  3. nginx: /opt/Primo/nginx/logs/nginx_error.log.
  1. Get-Service Primo.Orchestrator.*. все службы Running
  2. Если служба не стартует — запустите её .exe с аргументом --console из каталога службы и проверьте ошибку в консоли.
Этап 2 из 3

Службы и агенты отвечают

Каждая служба (WebApi, MachineInfo, RobotLogs, Analytic, Notifications, States, Queues, Licenses, LogEventsWebhook, NuGet2, RDP2, ArcSight, агент) отвечает на три адреса без авторизации:

АдресЗначение
/healthОбщее состояние (у большинства служб совпадает с readiness)
/health/readinessГотова принимать запросы
/health/livenessПроцесс работает

Ответ — Healthy (HTTP 200) или Unhealthy (HTTP 503).

Когда служба отвечает Unhealthy
СлужбаУсловие готовности
WebApi, MachineInfo, Notifications, LogEventsWebhook, ArcSightВсегда Healthy, если процесс отвечает. Подключение к БД и RabbitMQ при этом не проверяется.
RobotLogs, Analytic, States, Queues, Licenses, RDP2Healthy, когда службе известен адрес WebApi: задан Orchestrator:BaseUrl или адрес получен от WebApi.
АгентHealthy только после того, как WebApi хотя бы раз к нему обратился (т. е. машина зарегистрирована и опрошена).
MCP Server/mcp/health; 503, пока Оркестратор недоступен.

В Docker порты служб наружу не открыты: службы каждые 30 секунд опрашивает compose, и состояние healthy из этапа 1 — результат этой проверки. С сервера проверьте только вход через nginx:

curl -k -f https://localhost:44392/api/Version   # печатает номер версии

На сервере (порты — со страницы Порты и сетевой трафик):

curl -f http://localhost:5001/health        # WebApi
curl -f http://localhost:5051/health        # MachineInfo
curl -f http://localhost:56748/health       # RobotLogs
curl -k -f https://localhost:44392/api/Version   # WebApi через nginx, без авторизации

С сервера WebApi — до агента:

curl -k https://<IP машины робота>:5002/api/Worker   # 200 и версия агента
curl -k https://<IP машины робота>:5002/api/Version
Этап 3 из 3

Тестовый запуск

Последняя проверка — сквозная: проект проходит путь от Оркестратора до робота, результат возвращается в журнал. Требуется тестовый RPA-проект — архив zip. Подходит любой простой проект из Студии или готовый TestUploadProject.zip из открытого репозитория с примерами: он только записывает строку в журнал. Требуются также машина и робот из Первого запуска.

  1. Настройки → Лицензии. есть действующая лицензия
  2. Настройки → Система → Машины роботов. у каждой машины заполнены Доступна и Версия агента
  3. RPA-проекты → Все RPA-проекты → Добавить RPA-проект: выберите архив проекта. Через несколько секунд форма раскроется — заполните Наименование и нажмите Сохранить. сообщение «Проект успешно создан», проект появился в списке
  4. Откройте Роботы → Все роботы, в строке робота нажмите кнопку запуска ▷, выберите проект и подтвердите. сообщение о запуске робота с проектом; запуск виден в RPA-проекты → Запуски и в Журналы → События оркестратора
  5. Дождитесь окончания. у запуска в RPA-проекты → Запуски заполнен результат, журнал робота открывается кнопкой журнала в строке робота

Проверка завершена: Оркестратор, агент и робот работают совместно.

Возможные проблемы

Наиболее частые причины обращений в поддержку на этапе проверки:

Служба не стартует или отвечает Unhealthy

Начните с журнала службы (этап 1). Наиболее частые причины: нет доступа к БД или RabbitMQ либо не задано окружение ASPNETCORE_ENVIRONMENT. → Интерфейс не открывается или падает WebApi

Запуск завис на 50 % или 75 %

Робот не получил сессию или не стартовал на машине. → Робот не запускается: запуск завис на 50 % или 75 %

Проект выполнился, а журнал робота пустой

Причин несколько, они проверяются по порядку. → Журнал робота пустой или не открывается
