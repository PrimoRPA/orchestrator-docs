В Docker отдельные пользователи ОС для служб не нужны: службы работают внутри контейнеров от собственного пользователя, не от root.

Пароли СУБД и RabbitMQ в конфигах хранятся зашифрованными — их шифрует утилита PasswordEncryptor на шаге установки.

Службы Linux: от root или от пользователя

Для каждой службы в архиве два юнита:

ФайлКак работаетКуда ставить
Primo.Orchestrator.<Имя>.serviceСистемная служба, User=root/etc/systemd/system/
Primo.Orchestrator.<Имя>.user.serviceСлужба пользователя (systemctl --user), без root, Restart=always~/.config/systemd/user/ того пользователя, от которого работают службы

Для работы без root:

  • каталоги /opt/Primo/<Имя> принадлежат этому пользователю;
  • включите loginctl enable-linger <пользователь> — иначе службы остановятся, когда пользователь выйдет из системы;
  • копируйте файлы и запускайте systemctl --user под этим пользователем, не через sudo, иначе файлы получат владельца root.

В обоих юнитах задано ASPNETCORE_ENVIRONMENT=ProdLinux. Без этой переменной служба не стартует.

nginx на Linux
  • От root (Primo.Orchestrator.Nginx.service): от root работает только главный процесс, рабочие — от пользователя сборки nginx по умолчанию (обычно nobody). Каталог UI /opt/Primo/nginx/www должен быть доступен всем на чтение. Можно слушать порты ниже 1024.
  • Не от root (Primo.Orchestrator.Nginx.user.service): каталог /opt/Primo/nginx принадлежит пользователю служб, нужен enable-linger.
  • Закрытый ключ cert1.rsa — права 600.
Службы Windows

Без аргумента --console каждая служба запускается как служба Windows. Нужна системная переменная ASPNETCORE_ENVIRONMENT=ProdWin.

Учётная запись служб Windows в коде не задана. Старые доки: «службы устанавливаются под администратором и работают под LocalSystem» — подтвердить или описать минимальные права.

Агент на Linux
  • Пользователь агента — Agent:UserName, по умолчанию agent; общая группа агента и роботов — Agent:GroupName, по умолчанию primo-rpa. Оба должны существовать на машине. Имена можно менять.
  • Системный юнит агента: User=agent, UMask=0002.
  • Через sudo без пароля агенту нужны: /usr/bin/systemd-run -G --uid=<агент> --gid=<группа> --property=EnvironmentFile=/dev/shm/agent-*-env /opt/Primo/Agent/launch-as-user.expect (запуск роботов) и /usr/sbin/reboot (перезагрузка машины из Оркестратора).
  • Для пользователя агента нужен loginctl enable-linger.

Агент сам проверяет это при старте и пишет в журнал предупреждение, если чего-то не хватает. Подробнее — Машины роботов и агент.

Агент на Windows

Служба Primo.Orchestrator.Agent. Робот запускается заданием Планировщика заданий от имени пользователя, указанного в карточке машины.

Учётная запись службы агента на Windows в коде не задана (скрипт PrimoWorker.ps1 создаёт службу без указания пользователя, т. е. LocalSystem) — подтвердить требования.

СУБД и RabbitMQ
  • Для каждой БД задаются два пользователя: рабочий (DbConnection:Items:<БД>:UserName) и для миграций (…:MigrationUserName). WebApi применяет миграции к своим БД при каждом старте, поэтому пользователю миграций нужны права на создание объектов, а если БД не созданы заранее — и на создание БД.
  • Пользователь RabbitMQ — RabbitMQ:UserName; один и тот же для всех служб в поставочном compose.
  • Пароли СУБД и RabbitMQ в конфиге указываются зашифрованными (в compose — значения *-encrypted); шифрует их утилита PasswordEncryptor. Исключение — MCP Server: ему пароль передаётся открытым текстом.

Системные юниты (User=root) всех служб, кроме RDP2, не содержат Restart=always — в отличие от пользовательских. Уточнить, намеренно ли.

Строки «Учётная запись почты» и «для подключения к Active Directory» добавлены по параметрам Email:* и ActiveDirectory:MultyForest:*:AdminPassword — подтвердить, какие права нужны учётке AD. Для Windows не описано, под какой учётной записью работают службы и какие права нужны пользователям роботов (вход по RDP) — нужен ответ разработки.
