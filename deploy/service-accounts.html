В Docker отдельные пользователи ОС для служб не требуются: службы работают внутри контейнеров от собственного пользователя, не от root.

Пароли СУБД и RabbitMQ в конфигах хранятся зашифрованными: их шифруют утилитой PasswordEncryptor при установке.

Службы Linux: от root или от пользователя

Для каждой службы в архиве два юнита:

ФайлКак работаетКуда устанавливать
Primo.Orchestrator.<Имя>.serviceСистемная служба, User=root/etc/systemd/system/
Primo.Orchestrator.<Имя>.user.serviceСлужба пользователя (systemctl --user), без root, Restart=always~/.config/systemd/user/ того пользователя, от которого работают службы

Для работы без root:

  • каталоги /opt/Primo/<Имя> принадлежат этому пользователю;
  • включите loginctl enable-linger <пользователь> — иначе службы остановятся, когда пользователь выйдет из системы;
  • копируйте файлы и запускайте systemctl --user под этим пользователем, не через sudo, иначе файлы получат владельца root.

В обоих юнитах задано ASPNETCORE_ENVIRONMENT=ProdLinux. Без этой переменной служба не стартует.

nginx на Linux
  • От root (Primo.Orchestrator.Nginx.service): от root работает только главный процесс, рабочие — от пользователя сборки nginx по умолчанию (обычно nobody). Каталог UI /opt/Primo/nginx/www должен быть доступен всем на чтение. Допускается прослушивание портов ниже 1024.
  • Не от root (Primo.Orchestrator.Nginx.user.service): каталог /opt/Primo/nginx принадлежит пользователю служб, нужен enable-linger.
  • Закрытый ключ cert1.rsa — права 600.
Службы Windows

Без аргумента --console каждая служба запускается как служба Windows. Нужна системная переменная ASPNETCORE_ENVIRONMENT=ProdWin.

Агент на Linux
  • Пользователь агента — Agent:UserName, по умолчанию agent; общая группа агента и роботов — Agent:GroupName, по умолчанию primo-rpa. Оба должны существовать на машине. Имена допускается изменять.
  • Системный юнит агента: User=agent, UMask=0002.
  • Через sudo без пароля агенту нужны: /usr/bin/systemd-run -G --uid=<агент> --gid=<группа> --property=EnvironmentFile=/dev/shm/agent-*-env /opt/Primo/Agent/launch-as-user.expect (запуск роботов) и /usr/sbin/reboot (перезагрузка машины из Оркестратора).
  • Для пользователя агента нужен loginctl enable-linger.

Эти условия проверяются при старте агента; если какое-либо из них не выполнено, в журнал записывается предупреждение. Подробнее — Машины роботов и агент.

Агент на Windows

Служба Primo.Orchestrator.Agent. Робот запускается заданием Планировщика заданий от имени пользователя, указанного в карточке машины.

СУБД и RabbitMQ
  • Пользователь PostgreSQL задаётся отдельно для каждой БД в конфигурации той службы, которая с ней работает: DbConnection:Items:<имя>:UserName и DbConnection:Items:<имя>:Password. Имена записей: у WebApi — Default, Identity, License, ProcessRepository; у RobotLogs — Logs; у Analytic — Analytic; у Licenses — Licenses. Значения по умолчанию нет; параметры читаются при старте службы, после изменения требуется перезапуск. Во всех записях допускается один и тот же пользователь.
  • WebApi, RobotLogs и Analytic при каждом старте применяют миграции к своим БД под этим же пользователем, а если БД нет — создают её. Поэтому рабочему пользователю нужны:
    • право подключения к каждой БД Оркестратора;
    • права на создание и изменение таблиц, индексов и других объектов в схеме БД — достаточно назначить пользователя владельцем баз;
    • право на создание БД (CREATEDB) — только если базы не созданы заранее.
  • Отдельного пользователя для миграций нет. Параметры DbConnection:Items:<имя>:MigrationUserName и DbConnection:Items:<имя>:MigrationPassword читаются из конфигурации, но службами не используются: создание БД и миграции выполняются под UserName. Если оставить рабочему пользователю только чтение и запись данных, миграции при старте службы завершатся ошибкой.
  • Для MS SQL Server пользователь указывается в строках подключения ConnectionStrings:* (у WebApi — DefaultConnection, IdentityConnection, LicenseConnection, ProcessRepositoryConnection); требования к правам те же.
  • Пользователь RabbitMQ — RabbitMQ:UserName; один и тот же для всех служб в поставочном compose.
  • Пароли СУБД и RabbitMQ в конфиге указываются зашифрованными (в compose — значения *-encrypted); шифрует их утилита PasswordEncryptor.
