Структура БД

Применимо: 1.26.9WindowsLinuxDocker

Какие базы данных использует Оркестратор 1.26.9, какая служба с какой работает и какие таблицы в них есть. Список таблиц собран из контекстов EF Core и снимков миграций; описания — из комментариев к сущностям в коде.

Публикацию структуры БД согласовать с разработкой: раньше были возражения; описание таблиц передавалось клиентам по запросу.

Базы данных

Структуру баз создают и обновляют миграции EF Core при старте служб. Для каждой базы есть два набора миграций — для PostgreSQL и для MS SQL Server; выбор делает ключ DBVendor. Имена баз ниже — те, что заданы в Docker-образах; при установке на Windows или Linux имена задаёт администратор в строках подключения.

Служба Licenses подключается к основной БД (ltools) с контекстом ApplicationDbContext, но миграции не выполняет — их делает WebApi. Поэтому WebApi нужно запускать первым.

Для PostgreSQL можно задать отдельного пользователя для миграций: DbConnection:Items:<имя>:MigrationUserName и MigrationPassword. Схема задаётся через SearchPath; таблица истории миграций __EFMigrationsHistory создаётся в этой схеме.

RpaProjectQueueRpaProjectQueueСостояние очереди проектов на выполнение - для отображения в UI. В качестве реальной очереди используется RabbitMQ или, если настроена очередь со строгим порядком, то эта таблица сама выступает в качестве очереди проектов (не только для отображения в UI) Данные для показа состояния очереди на главной странице формируются следующим образом: 1. Перед добавления проекта в RabbitMQ он добавляется в БД в таблицу RpaProjectQueue (обычная таблица, не очередь). Фиксируется дата добавления CreatedAt. В очереди проект содержит RpaProjectQueue.Id. 2. После извлечения проекта из очереди и его успешной отправки в Агент для робота с RobotId, у записи RpaProjectQueue.Id проставляется RobotId, что для этой записи является признаком логического удаления. Логически удаленные записи не отображаются в плашке на главной, запрос из Api их фильтрует. Через некоторое время (параметр ProjectQueue.CleaningDepth) записи будут удалены физически 3. Если нет свободных роботов, для записи из RpaProjectQueue не установится RobotId, но установится/изменится дата UpdatedAt. Такое сочетание является признаком того, что проект ожидает своего выполнения в очереди.Время ожидания определяется как разность UpdatedAt и CreatedAt. 4. Если есть какие-то ошибки, RobotId не установится для записи из RpaProjectQueue, в тоже время не установится и дата UpdatedAt. Это является признаком отклонения поведения системы от ожидаемого. Робот, на котором произошел сбой, и сообщение об ошибке фиксируются.

БД NuGet-сервера

NuGet2 — сборка BaGet. Своя БД PostgreSQL (в Docker — ltoolsnuget), подключение — секция Database:DbConnection в конфиге NuGet2. Таблицы: Packages, PackageDependencies, PackageTypes, TargetFrameworks. Сами пакеты хранятся в файловой системе или в MinIO.

Таблицы перечислены по модели EF Core (DbSet и снимок миграций PostgreSQL). Секционированные таблицы журналов, представления и функции, которые создаются SQL-скриптами миграций, здесь не описаны — их стоит сверить по миграциям или на стенде.

Таблицы IntegrationSemaphore и IntegrationJournal объявлены сразу в нескольких контекстах (основная БД, репозиторий процессов, аналитическая БД) — уточнить, в какой базе они реально используются в каждом сценарии интеграции.

Старая статья «Компоненты системы» перечисляет те же семь баз (ltools, ltoolsidentity, ltoolslicense, ltoolslogs, ltoolsnuget, ltoolsltwrepo, ltoolsanalytic), но указывает PostgreSQL 13; Docker-шаблоны 1.26.9 используют PostgreSQL 14. БД секретов в старом списке нет.
