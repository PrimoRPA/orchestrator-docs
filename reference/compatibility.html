Какие версии Студии, Студии Linux, робота, агента и IdeaHub работают с какими версиями Оркестратора, а также ОС, СУБД и .NET. Определение LTS — на странице «Жизненный цикл версий».

Версии продуктов между собой

Матрица охватывает версии 2026 года. Студия, Robot Runner и робот одной версии считаются одним рядом, Оркестратор и агент одной версии — одной колонкой. Пара совместима, если выполнены три условия:

  1. Студия получает ресурсы Оркестратора: подключается, получает лицензию, читает и записывает ассеты и очереди, публикует проекты.
  2. Проект, опубликованный из Студии, запускается на роботе по расписанию.
  3. Оркестратор и агент понимают команды друг друга.

Ячейки проверены по исходному коду: вызовы, которые Студия реально делает, сверены с методами служб Оркестратора этой версии, параметры запуска робота — с тем, что передаёт агент. Состояние на 20.11.2026.

✔ — совместимы, ✖ — несовместимы (что именно не работает — в сноске).

Робот и Оркестратор

Робот разворачивает на машине агент Оркестратора из дистрибутива, загруженного в Оркестратор. Версия робота не обязана совпадать с версией Оркестратора. Ниже описано, какие сборки робота проверены с какими версиями Оркестратора, какой дистрибутив загружается для машин Windows и Linux и как робот запускается на машине.

Робот Windows любой версии пропускает параметры запуска, которых не знает; робот Linux пропускает параметры, которые к нему не относятся. Поэтому обновление Оркестратора не требует обновления роботов: вместе с сервером обновляются агенты (раздел «Агент»), а роботы остаются на прежнем дистрибутиве. На стенде сервер 1.26.9 выполнял проект на роботе 1.26.7.5 и с агентом 1.26.7.10, и после обновления агента до 1.26.9.

Роботы версий до 1.26.1 и работа роботов с Оркестратором 1.25.7 LTS не проверялись.

Робот, который запрашивает элементы очереди обмена данными в прежнем формате (одно значение retray или без отбора), в Оркестраторе 1.26.9 получает и повторно поставленные элементы. Проверено на стенде запросами API; какие версии робота используют прежний формат, не установлено. Подробности — на странице «Очереди обмена данными».

Какой дистрибутив загрузить

  • В Оркестратор загружается архив zip: Настройки → Система → Дистрибутивы робота → Добавить дистрибутив Робота. Файлы exe и msi из той же папки поставки предназначены для ручной установки робота и в Оркестратор не загружаются.
  • ОС, разрядность и версия дистрибутива определяются по содержимому архива. В архиве должен быть файл Primo.Robot.exe или Primo.Robot.dll. Если в архиве есть файл Primo.Robot без расширения, дистрибутив считается дистрибутивом для Linux.
  • Версия берётся из свойств файла (версия файла). Разрядность Windows-дистрибутива определяется по заголовку Primo.Robot.exe (x64 или x86); дистрибутив для Linux всегда учитывается как x64.
  • Архив без этих файлов отклоняется ответом 400 «The request couldn't be processed (Error 4).». Ограничений на версию дистрибутива при загрузке нет.
  • Если машины роботов работают и на Windows, и на Linux, загрузите дистрибутив для каждой ОС.

Дистрибутив по умолчанию назначается по разрядности, а не по ОС: один для x64 и один для x86. Дистрибутив для Linux учитывается как x64, поэтому дистрибутив Windows x64 и дистрибутив Linux занимают одно и то же место «по умолчанию».

  • Первый загруженный дистрибутив каждой разрядности становится дистрибутивом по умолчанию автоматически.
  • Назначить по умолчанию снимает отметку с прежнего дистрибутива той же разрядности, в том числе если он предназначен для другой ОС.
  • При удалении дистрибутива по умолчанию отметка переходит на другой дистрибутив той же разрядности, не обязательно той же ОС.

Если при развертывании робота дистрибутив не выбран, берётся дистрибутив по умолчанию нужной разрядности (если разрядность не указана — x64). ОС дистрибутива, выбранного явно или по умолчанию, должна совпадать с ОС машины (переключатель Linux в карточке машины). Иначе развертывание отклоняется ответом 409:

  • 1.26.9: «Linux-distributive is for Linux-worker only.» или «Windows-distributive is for Windows-worker only.»;
  • 1.26.7 LTS (проверено на 1.26.7.26) при развертывании одного робота: к тому же тексту добавлено «Check default distributive OS.».

В смешанном парке назначьте по умолчанию дистрибутив той ОС, на которой больше машин. Для машин другой ОС выбирайте дистрибутив в поле Версия дистрибутива при создании робота.

Как робот попадает на машину

  1. При развертывании WebApi назначает роботу порт и передаёт агенту команду с идентификатором дистрибутива. Порт — первый свободный на этой машине из диапазона RobotDeployment:PortMin — RobotDeployment:PortMax (по умолчанию 8000 — 9000) или заданный в поле Порт при развертывании с параметрами.
  2. Агент скачивает архив из WebApi один раз на дистрибутив и хранит его в <Agent:DataPath>/RobotDistr/<идентификатор дистрибутива>/LTools.Robot.x64.zip (или .x86.zip).
  3. Агент копирует архив в каталог робота <DeployRobot:RobotsPath>/Robot_<имя робота>_<ключ робота>/Distr/ и распаковывает в подкаталог Robot. Каталог роботов по умолчанию: Windows — C:\LTools, Linux — /opt/LTools (значение из appsettings.ProdLinux.json в архиве агента).
  4. Только на Windows: если в каталоге робота есть Primo.Robot.exe.config, агент записывает в него порт робота и отпечаток сертификата (DeployRobot:CertificateThumbprint), затем резервирует адрес https://+:<порт>/LTools.Robot/RobotService. На Linux конфигурация робота не изменяется.

Агент обращается к роботу по адресу https://<IP/DNS машины>:<порт робота>/LTools.Robot/RobotService/api/….

Версия дистрибутива фиксируется в роботе при развертывании. Повторное развертывание уже развёрнутого робота отклоняется («Робот уже развернут.»); чтобы перевести роботов на другой дистрибутив, назначьте его по умолчанию и переразверните роботов — раздел «Роботы» на странице «Порядок обновления».

Как робот запускается

Windows. Агент скачивает проект в подкаталог Project каталога робота, создаёт файл run.bat с командой start Primo.Robot.exe <параметры> и регистрирует задание Планировщика заданий «Run Robot <имя робота>_<ключ робота>» от имени RDP-пользователя робота. Задание выполняется с интерактивным входом, то есть в сеансе этого пользователя; сеанс перед запуском открывает служба RDP2 по запросу Оркестратора. Настройка сеансов — на странице «Запуск роботов и RDP-сессии».

Linux. Агент через sudo systemd-run вызывает launch-as-user.expect, который входит в систему под пользователем графического сеанса робота и выполняет сценарии из каталога робота:

  1. start-0-runner.sh — программа запуска LTools.Orchestrator.Agent.Runner поднимает виртуальный экран Xvfb с разрешением и глубиной цвета, заданными для пользователя машины; на Astra Linux 1.8 перед ней запускается dbus-launch;
  2. start-1-session.sh — графический сеанс (команда AgentCommands:Session);
  3. start-2-robot.sh — Primo.Robot <параметры>.

В каталоге ~/.config/robot/ пользователя робота допускается разместить исполняемые сценарии pre-runner.sh, pre-session.sh, pre-robot.sh и парные post-*.sh: они выполняются до и после соответствующего шага.

Параметры запуска формирует WebApi, агент передаёт их в командной строке Primo.Robot. В них входят имя и ключ робота, адрес Оркестратора (RobotDeployment:OrchBaseUrl) и службы журналов (RobotDeployment:RobotLogsBaseUrl), язык, ключ операции, редакция робота (в зашифрованном виде), учётная запись робота в Оркестраторе (orcuser и зашифрованный orcpass либо adauth), версия движка (engver), параметры шаблона развертывания (журналирование, потоки, winAuth, noOrcLogs) и проекта (RunConfig, mock). Агент добавляет путь к файлам блокировки (locksPath).

Что нужно на машине: агент той же версии, что и сервер, и подготовка по ОС — на странице «Машины роботов и агент»; для Windows — RDP-пользователь машины и служба RDP2, для Linux — пользователь графического сеанса. Требования самого робота — по инструкции робота. Если робот не стартует — «Робот не запускается».

Несколько роботов на одной машине

Дистрибутив выбирается для каждого робота при развертывании, а не для машины: версия, разрядность и ОС дистрибутива сохраняются в роботе. На одной машине допускаются роботы разных версий: у каждого свой каталог Robot_<имя>_<ключ> и свой порт. Роботы разных ОС на одной машине невозможны, так как ОС дистрибутива должна совпадать с ОС машины.

Другие проверки робота в WebApi:

  • проект запускается только на роботе с той же разрядностью, что указана в проекте: «Платформа робота не совпадает с платформой проекта.»;
  • если в проекте задан список версий дистрибутива, робот другой версии проект не запускает: «Версия дистрибутива робота не предназначена для запуска проекта.»;
  • робот редакции Desktop не создаётся: «Робот с редакцией Desktop не может быть развернут из Оркестратора.»;
  • функции, которые включаются с определённой версии робота, — в таблице «Пороги версии робота».

Attended-робот (Robot Runner)

Attended-робот агентом не разворачивается: его запускает пользователь на своей машине, и робот подключается к Оркестратору сам. В WebApi для него предусмотрены:

  • вход: POST api/Account/AttendedRobot (логин и пароль) и GET api/Account/AttendedRobotLoginNegotiate (Windows-аутентификация). Токен получает признак attended-робота и редакцию робота из запроса, по умолчанию Standard;
  • лицензия: api/Licenses/TakeAvailableAttendedRobotLicense (и /v2), KeepAliveAttendedRobot, ReleaseAttendedRobotLicense; требуется разрешение Licenses.CheckRobotLicense. Занимается лицензия робота той редакции, которая указана при входе: Enterprise, Standard или Desktop;
  • роль LimitedRobotRunner — встроенная системная роль без разрешений. Если она назначена пользователю, при входе attended-робота в токен добавляется роль LimitedRobotRunner. Проверок по этой роли в коде WebApi нет.

Агент

Агент собирается в том же решении, что и серверные службы, и получает тот же номер версии. Устанавливайте агент той же версии, что и сервер, в том числе при установке патчей LTS.

Сервер и агент разных версий работают не во всём. Оркестратор 1.26.7.18 вызывает у агента метод скачивания проекта с отслеживанием хода, которого нет в агентах 1.26.7.4 и 1.26.9. В такой паре действие Скачать проект на машину завершается ошибкой; запуск проектов по расписанию работает. Обновляйте агенты сразу после сервера: Машины роботов → Обновить выбранные. Порядок — на странице «Порядок обновления».

На время обновления сервер 1.26.9.0 работал с агентом 1.26.7.10 и роботом 1.26.7.5 на Linux: вход, лицензии и запуск проекта на роботе выполнялись.

Ограничение версии Студии — настройка, а не совместимость

Секция StudioVersionChecker в WebApi задаёт минимальную версию Студии, которой Оркестратор выдаёт лицензию. Это ограничение, которое задаёт администратор. Оно не определяет, какие версии Студии совместимы с Оркестратором.

ПараметрНазначениеПо умолчанию
StudioVersionChecker:MinimumStudioVersionМинимальная версия Студии в формате 1.23.8.4. Если не задана, проверка выключена (в журнал пишется предупреждение).не задано
StudioVersionChecker:StudioVersionExceptionBehaviorTypeПоведение Студии при отказе: 0 — закрывается без сообщения, 1 — показывает сообщение и закрывается, 2 — только показывает сообщение. Значение вне 0–2 заменяется на 1.0
  • Если версия Студии ниже порога, WebApi отвечает 409 с текстом «Версия студии устарела…» и передаёт выбранное поведение в заголовке Studio-Version-Failed-Behavior.
  • Если Студия не передала свою версию, лицензия выдаётся без проверки.
  • Порог один для Студии Windows и Студии Linux.

Если задать только MinimumStudioVersion, поведение по умолчанию — 0: устаревшая Студия закроется без сообщения пользователю.

Операционные системы

Сервер

  • Службы публикуются как self-contained под win-x64 и linux-x64: отдельная установка .NET не требуется.
  • Linux: службы оформлены как systemd-юниты (/opt/Primo/<Служба>), есть системный и пользовательский (rootless) варианты юнитов.
  • Docker-образы строятся на базе ubuntu:24.04 и Astra Linux (astra/ubi18:1.8.6); образы для Kubernetes — на astra/ubi17.

Машина робота

  • Агент выпускается для Windows и Linux.
  • На Linux команда графической сессии определяется автоматически для Astra Linux (fly-wm), CentOS (gnome-session) и РЕД ОС (mate-session). Для других дистрибутивов, в том числе Ubuntu, задайте AgentCommands:Session вручную. Для Astra Linux 1.8 агент дополнительно запускает dbus-launch.

СУБД

Поддерживаются PostgreSQL и MS SQL Server: для каждой БД в коде есть два набора миграций. MS SQL Server — только для служб на Windows Server; на Linux и в Docker — PostgreSQL.

Структурированное подключение DbConnection:Items (хост, порт, имя БД, отдельная учётная запись для миграций) WebApi читает только при DBVendor=Postgres. Для MS SQL используются строки ConnectionStrings:*Connection.

В поставочных docker-compose используются образы postgres:14 и rabbitmq:3-management.
