Интерфейс не открывается или падает WebApi

Применимо: 1.26.9WindowsLinuxDocker

Если UI4 не открывается, отвечает ошибкой или служба WebApi не стартует, проверяйте по цепочке: nginx → файлы UI → WebApi → БД и RabbitMQ. UI4 — статические файлы, которые отдаёт nginx; запросы к API идут на тот же адрес по пути /api/, и nginx проксирует их в WebApi.

Вероятные причины

  • nginx не запущен, указан неверный порт или сертификат — nginx и файлы UI.
  • WebApi не запущен: не задано окружение, нет доступа к БД или RabbitMQ при старте — WebApi не стартует или падает.
  • После перезагрузки сервера службы стартуют раньше БД или RabbitMQ — WebApi не стартует или падает.
  • Неверный location /api/ в nginx — Ошибки в UI4.
  • Linux: конфигурацию nginx.linux.conf запускает стандартная служба nginx, а не пользовательская служба Primo.Orchestrator.Nginx — nginx и файлы UI, шаг 2.
  • WebApi не может создать БД или применить миграции: нет права на создание БД, между WebApi и PostgreSQL работает пулер соединений, в PostgreSQL задано standard_conforming_strings = off, версия откачена без восстановления БД — Ошибки БД при старте WebApi.
  • Исчерпан лимит подключений PostgreSQL (max_connections) — Лимит подключений; не разрешается имя сервера БД — WebApi не стартует или падает.
  • Ошибки RabbitMQ при объявлении обменников и очередей на старте — см. RabbitMQ.

Как исправить

nginx и файлы UI: Linux

  1. nginx Оркестратора работает как пользовательская служба Primo.Orchestrator.Nginx. Системный nginx должен быть выключен, для пользователя включён linger. Проверьте: systemctl --user status Primo.Orchestrator.Nginx. active (running)
  2. Если конфигурацию из поставки запускает стандартная служба nginx, служба завершается с ошибкой о pid-файле, хотя проверка конфигурации проходит. Отключите стандартную службу и запустите пользовательскую — Установка служб: 
    sudo systemctl disable --now nginx
systemctl --user enable --now Primo.Orchestrator.Nginx
    systemctl is-active nginx — inactive, systemctl --user is-active Primo.Orchestrator.Nginx — active
  3. Проверьте конфигурацию: nginx -t -p /opt/Primo/nginx/ -c /opt/Primo/nginx/nginx.conf. Журналы nginx — в /opt/Primo/nginx/logs.
  4. Закрытый ключ сертификата должен быть доступен только владельцу: chmod 600 /opt/Primo/nginx/cert1.rsa.
  5. WebApi: служба Primo.Orchestrator.WebApi, каталог /opt/Primo/WebApi.

nginx и файлы UI: Windows

Вариант с nginx — те же действия, что выше, конфигурация nginx.win.conf.

nginx и файлы UI: Docker

Контейнер UI собирает конфигурацию nginx из шаблона через переменные NGINX_LISTEN_PORT, NGINX_APP_SERVER_HOSTNAME, NGINX_APP_SERVER_PORT и другие. TLS внутри контейнера нет. nginx отвечает на /health самостоятельно, поэтому работающий контейнер UI не означает, что WebApi доступен.

Ошибки БД при старте WebApi

При каждом старте WebApi применяет миграции к четырём БД: DbConnection:Items:Default, Identity, License, ProcessRepository (в поставке — ltools, ltoolsidentity, ltoolslicense, ltoolsltwrepo). Если БД нет, она создаётся, если есть — применяются только недостающие миграции. Создание БД и миграции выполняются под учётной записью из строки подключения (UserName). Этой учётной записи нужны право создавать БД (CREATEDB), если базы не созданы заранее, и право создавать объекты в своих БД.

  1. Найдите в журнале WebApi первую ошибку после строки «Start Primo.Orchestrator.WebApi(…)» и определите, к какой БД она относится.
  2. Если база не создаётся, создайте пустую БД вручную и назначьте владельцем учётную запись Оркестратора, затем перезапустите WebApi. Миграции применятся при старте: 
    sudo -u postgres createdb -O <пользователь БД Оркестратора> ltoolsltwrepo
    В журнале WebApi нет ошибок миграций, /health отвечает
  3. Если между WebApi и PostgreSQL работает пулер соединений (например, PgBouncer), автоматическое создание БД может завершиться ошибкой. Создайте базы заранее, как в шаге 2.
Миграции ltoolsltwrepo завершаются ошибкой, параметр standard_conforming_strings

В версиях до 1.26.7.25 миграции БД ltoolsltwrepo завершаются ошибкой, если в PostgreSQL задано standard_conforming_strings = off; удаление и повторное создание БД не помогает. Исправлено в 1.26.7.25. Проверьте значение на сервере БД:

SHOW standard_conforming_strings;
SELECT version();

Обновите WebApi до 1.26.7.25 или более поздней версии. Значение по умолчанию в PostgreSQL — on; изменять параметр на общем сервере БД без согласования с администратором БД не допускается.

Служба NuGet2: БД ltoolsnuget

NuGet2 при старте применяет миграции к своей БД (RunMigrationsAtStartup, по умолчанию true) и создаёт её, если её нет. Первая миграция подключает расширение PostgreSQL citext. Если учётной записи службы недостаточно прав для создания БД или расширения, служба завершается с «Primo.Orchestrator.NuGet has terminated abnormally.». Создайте БД заранее и подключите расширение под администратором PostgreSQL, затем запустите службу:

sudo -u postgres createdb -O <пользователь БД Оркестратора> ltoolsnuget
sudo -u postgres psql -d ltoolsnuget -c "CREATE EXTENSION IF NOT EXISTS citext;"
Откат версии: «column … already exists»

Миграции новой версии изменяют БД, а отката миграций в WebApi нет. Одно и то же изменение в разных ветках выпуска может находиться в миграциях с разными именами. Поэтому старая версия, запущенная на БД новой версии, повторно применяет уже выполненное изменение и завершается ошибкой «column … already exists». Пример: после отката с 1.26.7 на 1.25.7 — столбец InvalidCredentials таблицы Agents.

Возврат на прежнюю версию выполняется с восстановлением БД из резервной копии, созданной перед обновлением, — см. Откат обновления.

Лимит подключений к PostgreSQL

Каждая служба держит свой пул соединений на каждую строку подключения: у WebApi их четыре (Default, Identity, License, ProcessRepository), у RobotLogs — Logs, у остальных служб — свои. Размер пула — DbConnection:Items:*:MaxPoolSize (MAXPOOLSIZE в строке подключения); если он не задан, действует значение драйвера Npgsql — 100. Лимит max_connections действует на весь сервер PostgreSQL, включая другие базы и другие экземпляры Оркестратора.

  1. Сложите MaxPoolSize всех строк подключения всех служб и всех экземпляров Оркестратора на этом сервере БД и сравните с max_connections.
  2. Уменьшите MaxPoolSize до значения, рассчитанного под нагрузку, остановите лишние экземпляры Оркестратора на этом сервере БД или увеличьте max_connections в PostgreSQL. Перезапустите службы. Ошибки 53300 в журнале WebApi больше не появляются

Нестандартное размещение

UI4 собран с <base href="/"> и адресом API /api, поэтому работает только в корне сайта, не в подкаталоге. Если UI отдаётся с другого адреса, чем WebApi, перечислите адреса UI в Security:EnabledOrigins (по умолчанию пусто, CORS выключен).

Вторая копия WebApi на том же порту не запускается. Проверьте, что старый процесс завершён.
