Ошибки RabbitMQ: нет обменника или очереди

Применимо: 1.26.9WindowsLinuxDocker

Обменники и очереди RabbitMQ создаёт не администратор, а службы Оркестратора при запуске. Если нужная служба не запускалась на этом сервере RabbitMQ или RabbitMQ потерял свои данные, публикация завершается ошибкой: проекты не запускаются, события и письма теряются. На странице описано, как по тексту ошибки определить недостающий объект и восстановить его.

Симптомы

  • Не запускается ни один проект, не разворачивается робот. Агент пишет «Оркестратор вернул ошибку: StatusCode=InternalServerError». Причину показывает журнал WebApi — Что проверить.
  • В журнале WebApi предупреждение «Error publishing event [OrchEvent] to EventHub.» с одним из исключений:
    • NOT_FOUND - no exchange 'events' in vhost '/' (код 404) — Нет обменника events;
    • AlreadyClosedException: Already closed с текстом Feature `transient_nonexcl_queues` is deprecated (код 541) — Установлен RabbitMQ 4.x.
  • В журнале службы при запуске: «Ошибка при подключении к RabbitMQ» — Что проверить, шаги 2–4.
  • В консоли RabbitMQ нет очереди projects_<тенант>, хотя одноимённый обменник есть — Нет очереди projects_<тенант>.
  • Docker: после docker compose down и up в консоли RabbitMQ нет ни обменников, ни очередей Оркестратора — Пустая база RabbitMQ.
  • В консоли RabbitMQ очередь (например, dbevents2) заполнена до предела, потребителей нет — Очередь заполнена.
  • В журнале WebApi — «Failed publishing to …» с исключением MqttClientNotConnectedException — MQTT; к RabbitMQ сообщение не относится.

Вероятные причины

  • Служба, которая объявляет объект, не запускалась после очистки или пересоздания RabbitMQ (какая служба что объявляет — в таблице Кто создаёт обменники и очереди). Обменник events создаёт только States: если States выключена или ещё не стартовала, WebApi получает «no exchange 'events'» при публикации любого события, например после неудачного входа пользователя.
  • Службы подключены к разным серверам RabbitMQ или разным виртуальным хостам. Адрес задают RabbitMQ:Host (или список RabbitMQ:Hosts; при заполненных обоих используется Host) и RabbitMQ:Port, виртуальный хост — RabbitMQ:VirtualHost (если не задан, используется виртуальный хост по умолчанию /).
  • Ошибка при объявлении в момент запуска службы: служба пишет «Ошибка при подключении к RabbitMQ» и не создаёт оставшиеся объекты.
  • Установлен RabbitMQ 4.x. WebApi создаёт временные неэксклюзивные очереди (wsevents<N>, keepaliverobots<N>, assetcacheinvalidationevents<N>). В RabbitMQ 4.x такие очереди по умолчанию запрещены, сервер закрывает канал с кодом 541.
  • Docker: RabbitMQ стартовал с пустой базой после пересоздания контейнера — исправление.

Что проверить

  1. Найдите в журнале WebApi на время ошибки строки «Error publishing event» и прочитайте текст исключения: no exchange, transient_nonexcl_queues или ошибку соединения. Известно, какого объекта не хватает или почему закрыт канал
  2. Проверьте, запущены ли States, Notifications и WebApi. Найдите в начале журнала каждой службы «Ошибка при подключении к RabbitMQ». Все три службы работают, ошибки при запуске нет
  3. Откройте консоль управления RabbitMQ (порт 15672), вкладки Exchanges и Queues. Сверьте объекты с таблицей Кто создаёт обменники и очереди и виртуальный хост (столбец Virtual host) с RabbitMQ:VirtualHost служб. Обменник events и очереди projects_… есть в том виртуальном хосте, к которому подключены службы
  4. Сравните RabbitMQ:Host и RabbitMQ:Port в конфигурации всех служб. С сервера WebApi проверьте доступность именно этого адреса и порта (по умолчанию 5672), а не адреса, по которому открывалась консоль. Все службы указывают на один и тот же RabbitMQ
  5. Проверьте версию RabbitMQ: rabbitmqctl version или правый верхний угол консоли управления. Версия 3.x

Как исправить

Нет обменника events

Обменник создаёт служба States при запуске. После появления обменника WebApi требуется перезапустить: канал публикации, закрытый сервером из-за ошибки 404, автоматически не восстанавливается.

  1. Остановите службы Оркестратора.
  2. Запустите States и дождитесь в журнале строки «Запуск сервиса чтения событий оркестратора.» без ошибки RabbitMQ после неё. В консоли RabbitMQ есть обменник events типа fanout и очередь events
  3. Запустите WebApi, затем Notifications и остальные службы. В журнале WebApi нет «no exchange 'events'»

Если служба States не используется, обменник можно создать вручную в консоли RabbitMQ: Exchanges → Add a new exchange, имя events, тип fanout, Durability — Durable, Auto delete — No. Параметры должны совпадать с теми, что объявляет States: при расхождении States не запустится с этим RabbitMQ. События в такой обменник без очереди не сохраняются.

В Docker WebApi запускается раньше States (остальные службы ждут готовности web-api). Если обменника не было, после запуска всех контейнеров выполните docker compose restart web-api.

Нет очереди projects_<тенант>

Очереди и обменники проектов создаёт WebApi при запуске, сначала очередь, затем обменник, для каждого тенанта. Если обменник есть, а очереди нет, очередь удалена после запуска WebApi или при её объявлении произошла ошибка.

  1. Найдите в журнале WebApi после строки «Создание обменников и очередей в RabbitMQ для обработки очереди ожидания проектов.» ошибку «Ошибка при подключении к RabbitMQ» и текст исключения.
  2. Убедитесь, что RabbitMQ доступен, и перезапустите WebApi. Очередь projects_<тенант> появилась в консоли RabbitMQ, проекты из очереди уходят роботам

Допускается создать недостающую очередь вручную, но с теми же аргументами, что объявляет WebApi (x-max-length = 10000, durable), и привязать к обменнику projects_<тенант> с ключом маршрутизации, равным имени очереди. Перезапуск WebApi надёжнее.

Установлен RabbitMQ 4.x

В поставочных docker-compose используется образ rabbitmq:3-management, то есть ветка 3.x. С RabbitMQ 4.x WebApi не может создать временные очереди. Установите RabbitMQ ветки 3.x (3.13). Если в репозитории дистрибутива есть только 4.x (например, Ubuntu 24.04), установите пакет 3.x отдельно, из deb-пакета нужной версии. В журнале WebApi нет transient_nonexcl_queues, роботы разворачиваются

Docker: пустая база RabbitMQ после пересоздания контейнера

У службы 0rabbitmq в поставочном docker-compose не задан параметр hostname. Данные хранятся в томе rabbitmqdata (/var/lib/rabbitmq), но RabbitMQ размещает базу в каталоге с именем узла rabbit@<имя хоста>. При пересоздании контейнера Docker назначает новое случайное имя хоста, RabbitMQ запускает новый узел с пустой базой: без обменников, очередей и сообщений. Старые каталоги остаются в томе.

  1. Проверьте каталоги узлов в томе: docker compose exec 0rabbitmq ls -l /var/lib/rabbitmq/mnesia. Несколько каталогов rabbit@… — база создавалась заново при пересоздании контейнера
  2. Задайте службе 0rabbitmq постоянное имя хоста: 
        0rabbitmq:
        image: rabbitmq:3-management
        hostname: rabbitmq
        ...
  3. Выполните docker compose up -d. При первом запуске с новым именем хоста база снова создаётся пустой: дождитесь запуска всех служб и выполните docker compose restart web-api. После повторного docker compose down и up обменники и очереди сохраняются

Кто создаёт обменники и очереди

Каждая служба при запуске объявляет свои обменники и очереди. Объявление повторяется при каждом старте; существующие объекты с теми же параметрами не изменяются. Если служба не запускалась, её объектов нет, а остальные службы получают ошибку при публикации.

Обменник (тип) → очередьОбъявляетЧитает

Все объекты, кроме последней строки, создаются долговечными (durable) с ограничением длины очереди x-max-length: 10000 у очередей проектов, dbevents, dbevents2, emailevents, notificationemailevents и очередей писем; 5000 у events и очередей уведомлений. Очередь projectspriority_… дополнительно создаётся с приоритетами (x-max-priority = 3) и временем жизни сообщений; очереди projectspriority_… и deferred… по истечении времени передают сообщения в обменник projects_<тенант>. Очереди последней строки — временные (не durable, удаляются автоматически, не эксклюзивные). Имена задаются в секции RabbitMQ каждой службы; в таблице — значения по умолчанию.

Очередь заполнена, сообщения никто не читает

Очередь dbevents2 предназначена для подсистемы аналитики (служба Analytic). WebApi создаёт её всегда и копирует в неё все события Оркестратора. Если Analytic не развёрнута, у очереди нет потребителей, и она заполняется до предела x-max-length = 10000; более старые сообщения вытесняются. Это штатное поведение, на работу Оркестратора оно не влияет. Если Analytic развёрнута, а очередь не уменьшается — проверьте журнал Analytic.

То же относится к другим очередям без потребителя: в столбце Consumers консоли RabbitMQ видно, читает ли очередь какая-либо служба.

Похожее сообщение, не связанное с RabbitMQ: MQTT

В журнале WebApi при запусках роботов возможны ошибки «Failed publishing to {topic}: {message}» с исключением MQTTnet.Exceptions.MqttClientNotConnectedException. MQTT используется только для взаимодействия со службой RDP2 и настраивается секцией Mqtt (Url, Username, Password). Если секция не заполнена, сообщение не влияет на работу, но пишется с уровнем Error. Чтобы скрыть его, задайте для источника уровень выше Error:

"Serilog": {
  "MinimumLevel": {
    "Override": {
      "LTools.Orchestrator.Mqtt.Client.MqttBusClient": "Fatal"
    }
  }
}

В Docker — переменная Serilog__MinimumLevel__Override__LTools.Orchestrator.Mqtt.Client.MqttBusClient=Fatal у службы web-api. При использовании RDP2 фильтр не задавайте: он скроет и реальные ошибки связи с брокером MQTT.
