Уведомления не приходят или служба Notifications перезапускается

Применимо: 1.26.9WindowsLinuxDocker

Письма Оркестратора проходят через службы WebApi, States и Notifications и очереди RabbitMQ. На странице описано, где письмо может остановиться, почему служба Notifications завершается при отправке и какие настройки влияют на содержание писем.

Перед началомнастроена отправка почты — Почта и оповещения
Результатписьма по подпискам и из проектов доставляются, Notifications работает без перезапусков

Симптомы

  • Служба Notifications циклически перезапускается, в журнале: «Unhandled exception. MimeKit.ParseException: Unexpected ';' token at offset …».
  • Письмо из проекта на несколько адресов не доходит никому; в журнале Notifications «Не удалось отправить сообщение subject=[…] на почту {…}.» с ответом почтового сервера об отклонённом адресате.
  • Уведомления по подписке не приходят.
  • Время события в письме отличается от времени в интерфейсе на смещение часового пояса.
  • Непонятно, где задать почтовый сервер для писем, которые проект отправляет через Оркестратор.
  • Не удаётся изменить порог длины очереди проектов для уведомлений.

Как проходит письмо

Уведомление по подписке.

  1. WebApi публикует событие в обменник RabbitMQ events.
  2. States выбирает активные подписки, в которых указано это событие, применяет фильтр по сущностям, убирает повторяющиеся адреса и передаёт письмо в очередь OrchEventsResolveEvents. В журнале States: «Рассылка по оркестраторным событиям: сообщение для события [{event}] подготовлено для рассылки.»
  3. Notifications формирует письмо по шаблону и отправляет его через SMTP-сервер из секции Email.

Письмо из проекта.

  1. Робот вызывает POST api/Email/v2. Тело — form-data: поле data_dto с JSON (Email, Subject, Message, Cc, Bcc) и файлы вложений. WebApi проверяет суммарный размер вложений (Email:MaxAttachmentsLengthInMB, по умолчанию 10) и публикует письмо в обменник emailevents.
  2. Notifications помещает письмо в очередь задержки emaildefferedgeneral (EmailDefferedGeneralMilliseconds, 500 мс), откуда оно попадает в очередь отправки emailqueue.
  3. Notifications отправляет письмо одним сообщением всем адресатам. Тема письма дополняется: «<тема> - <пользователь> - <идентификатор письма>». При ошибке письмо помещается в очередь emaildefferedafterfail (EmailDefferedAfterFailMilliseconds, 1000 мс) и отправляется повторно; запись появляется на экране Настройки → Администрирование → Уведомления.

Вероятные причины

  • В поле адреса указано несколько адресов через «;» или адрес с «;» на конце.
  • Среди адресатов письма есть адрес, который отклоняет почтовый сервер.
  • Подписка не активна, в ней не выбрано событие или фильтр по сущностям не совпадает с событием.
  • Служба States не запущена или не получает события (см. Ошибки RabbitMQ).
  • Ошибка подключения или аутентификации на SMTP-сервере.

Что проверить

  1. Найдите в журнале Notifications «Unhandled exception», «Не удалось отправить сообщение» и «Сообщение на почту {…} успешно отправлено.». Известно, дошло ли письмо до SMTP-сервера
  2. Для уведомлений по подписке найдите в журнале States строку «… подготовлено для рассылки» по нужному событию. Строка есть — States передал письмо, искать в Notifications и SMTP; строки нет — проверить подписку и States
  3. Откройте Настройки → Администрирование → Подписки и проверьте у подписки адрес, флаг Подписка активна, выбранные события и Фильтр по сущностям.
  4. Для писем из проекта отправьте тестовое письмо запросом POST api/Email/v2 с учётными данными робота на один адрес. Письмо дошло — причина в проекте (адреса, вложения), не дошло — в Notifications или SMTP
  5. Откройте экран Уведомления и консоль RabbitMQ: сколько сообщений в очередях emailqueue и emaildefferedafterfail. Очереди пустые, повторных отправок нет

Как исправить

Несколько адресов в одном поле: Notifications завершается

Notifications передаёт значение поля Email почтовой библиотеке как один адрес. Строка с «;» не разбирается как адрес, исключение возникает до отправки. Для писем из проекта оно возникает в обработчике очереди emailqueue вне обработки ошибок, и процесс службы завершается; уведомление по подписке с таким адресом не отправляется. Дополнительных получателей письма из проекта передают в отдельных списках Cc и Bcc.

  1. Исправьте проект: в поле адреса — один адрес без «;», остальные адресаты — в копии.
  2. Проверьте адреса в подписках: у подписки одно поле Email на один адрес (до 500 символов, при сохранении проверяется формат: «Некорректный Email.»).
  3. Перезапустите Notifications. Служба работает, в журнале нет ParseException
  4. Если служба снова завершается при запуске, очистите в консоли RabbitMQ очереди emailqueue, emaildefferedgeneral и emaildefferedafterfail (Queues → очередь → Purge Messages). Неотправленные письма при этом удаляются.

Чтобы уведомления по подписке получали несколько человек, укажите в подписке адрес группового почтового ящика или списка рассылки и ведите состав получателей в почтовой системе.

Письмо не уходит никому, если один адрес недействителен

Письмо отправляется одним сообщением сразу всем адресатам (Email, Cc, Bcc). Если SMTP-сервер отклоняет хотя бы одного адресата, отправка не выполняется для всех. Письмо возвращается в очередь emaildefferedafterfail и отправляется повторно, пока отправка не пройдёт. Исключите недействительные адреса из списка адресатов в проекте.

Кнопка Очистить очередь на экране Уведомления удаляет только записи этого экрана (таблица NotificationEmailQueue). Письма в очередях RabbitMQ при этом остаются и продолжают отправляться. Чтобы прекратить повторы, очистите очереди emaildefferedafterfail и emailqueue в консоли RabbitMQ.

Уведомления по подписке не приходят

  • States учитывает только подписки с флагом Подписка активна, в которых выбрано событие. В UI4 при сохранении требуется хотя бы одно событие («Выберите хотя бы одно событие подписки.»).
  • Если заполнен Фильтр по сущностям, подписка срабатывает, только когда робот, проект, задание или машина из списка участвует в событии.
  • Список подписчиков States кэширует (параметр Cache:OrchSubscribers:DurationInMinutes службы States). Изменения подписки применяются после истечения кэша или перезапуска States.
  • Рассылка «Все» (прежний механизм, тип системного события помечен в коде как устаревший) отправляется только по событиям из списка RabbitMQ:AllEventsResolveList службы States. Список задаётся числовыми кодами событий (см. События и их коды); значения «все события» нет, пустой список означает, что рассылка не выполняется. В Docker-образе States по умолчанию: 201, 204, 301, 401, 501, 601, 701.

Подписку на все события для выгрузки журнала не используйте: каждое событие отправляется отдельным письмом. Для передачи событий во внешнюю систему предназначена служба LogEventsWebhook, для анализа — таблица OrchEvents (см. События и их коды).

Время в письме отличается от времени в интерфейсе

Штатное поведение. Время события (OrchTimestampUtc) передаётся в письмо в UTC. Время подготовки письма к рассылке States записывает по часам своего сервера (в Docker — по переменной TZ контейнера). Смещение Tenants:TimeOffset и Tenants:Items[].TimeOffset применяется только в WebApi при отображении в интерфейсе; в States и Notifications настройки часового пояса нет.

Где задаётся SMTP для писем из проекта

Проект передаёт в Оркестратор только содержимое письма и вложения. Отправляет письмо служба Notifications через SMTP-сервер и от адреса из своей секции Email (FromSmtp, FromSmtpPort, FromEmail, FromUserName, FromPassword). Эти параметры общие для всех писем Оркестратора, задаются в конфигурации Notifications при развёртывании; в интерфейсе их нет. Описание параметров — Почта и оповещения. Если письмо нужно отправить от имени другого почтового ящика, в проекте используется собственная отправка почты робота, а не отправка через Оркестратор.

Порог длины очереди проектов

Порог задаётся в службе States, а не в Notifications. Источник значения выбирает параметр SLAFromDb службы States:

  • SLAFromDb=false (по умолчанию) — SLA:RpaProjectQueueRise:CriticalQueueLength в конфигурации States. Измените значение и перезапустите States.
  • SLAFromDb=true — значение из БД Оркестратора. Текущие значения возвращает GET api/StatesSlaConfig, изменяет PUT api/StatesSlaConfig (оба метода требуют права на изменение настроек, Settings.Edit): 
    {
  "agentUnavailabilityFirstSec": 30,
  "agentUnavailabilityRepeatedlySec": 300,
  "rpaProjectQueueRiseCriticalQueueLength": 4,
  "rpaProjectQueueRiseRepeatedlySec": 300
}
    WebApi сохраняет значение сразу. States читает пороги один раз при запуске, поэтому после изменения перезапустите States.

В журнале States после перезапуска при SLAFromDb=true выводится строка «StatesSlaConfig: …» с новыми значениями
