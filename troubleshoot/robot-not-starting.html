Робот не запускается: запуск завис на 50 % или 75 %

Применимо: 1.26.9WindowsLinuxDocker

Запуск робота выполняется по этапам, в UI4 отображается процент последнего успешного этапа. По проценту видно, где остановился запуск: на агенте, при старте процесса робота или при получении лицензии.

ПроцентПоследний успешный этапГде искать

Агент отправляет этапы в порядке: старт, завершение старого процесса (50 %), скачивание архива (если в кэше его нет), генерация скрипта, запуск. Поэтому запуск останавливается на 50 %, если архив не скачался или не сгенерировался скрипт.

Вероятные причины

  • Нет связи агента с WebApi или WebApi с агентом.
  • Linux: агенту не хватает sudo, expect или прав на systemd-run — часто после обновления ОС.
  • Неверный пароль пользователя сессии робота.
  • Не поднялась RDP-сессия или графический сеанс, и процесс робота не стартует.
  • Нет свободной лицензии робота.
  • Процесс робота запускается и сразу завершается с ошибкой.

Что проверить

  1. Наведите указатель на процент в списке роботов и проверьте, на каком этапе ошибка. Известен этап и текст ошибки
  2. Проверьте машину в Машины роботов: колонка Доступна. С сервера WebApi выполните curl -k https://<IP/DNS>:5002/api/Worker. «Да», ответ 200 с версией агента
  3. Откройте журнал агента за время запуска. Найдите «Ошибка скачивания архива проекта с Оркестратора.», «StartRobotPipeline.CreateTaskToStartRobot - …», на Linux — «Robot … invalid credentials.» и строки с концовкой «the launch of robots is impossible». Найдена ошибка этапа
  4. На 75 % проверьте сессию: Сессия робота не поднимается. Затем лицензии в Лицензии: Нет лицензии.

Как исправить

Linux

При старте агент проверяет окружение и пишет предупреждения, если запуск невозможен: «expect command is unavailable…», «launch-as-user.expect … is missing or not executable…», «session start script is unavailable…», «sudoers does not currently permit '…'…». Установите недостающие компоненты и восстановите правило sudoers, затем перезапустите агента. Перед запуском агент проверяет пароль пользователя командой su - <user> -c /bin/true; при ошибке робот получает «Неверные учётные данные робота» — задайте верный пароль в карточке машины.

Процесс робота сразу завершается

Признаки на Linux: запуск проходит все этапы без ошибки, но результат запуска в списке роботов пустой («—»), состояние робота — «Недоступен». В разделе RPA-проекты → Запуски у такого запуска после снятия блокировки робота появляется результат «Робот освобожден по таймауту»; в Docker блокировка снимается через две минуты. До этого повторный запуск не начинается.

Связь с агентом

Адрес WebApi для агента — Orchestrator:BaseUrl в конфигурации агента, внешний адрес Оркестратора — RobotDeployment:OrchBaseUrl в WebApi. Порт и протокол агента должны совпадать с настройками в WebApi (по умолчанию HTTPS, 5002). Переменные PRIMOSIGNINGKEY, PRIMOISSUER, PRIMOAUDIENCE должны совпадать на сервере и машине робота.

Если зависание повторяется, не дожидайтесь таймаута: устраните причину на агенте и запустите заново. Кнопка Разблокировать в списке роботов снимает блокировку вручную.

Робот ещё не развернут

Проект уходит только на развернутого робота. Если Статус развертывания — «Ошибка», проверьте сообщение: «Отсутствует актуальный … дистрибутив робота.» — загрузите дистрибутив нужной ОС и разрядности; «Таймаут деплоя … мин. истек …» — агент не сообщил о завершении за RobotDeployment:TimeOutInMinutes (в классе 5, в Dockerfile 2).
