Оркестратор и БД работают медленно

Применимо: 1.26.9WindowsLinuxDocker

Чаще всего причина в БД: растут журналы, нет очистки, недостаточен пул соединений. Вторая частая причина — очередь проектов и RabbitMQ под нагрузкой.

Перед началомвключённые метрики WebApi — Мониторинг и метрики
Результатинтерфейс и запросы к БД отвечают без задержек

Симптомы

  • Таблицы в UI4 открываются долго, часть запросов завершается по таймауту.
  • Активности робота, работающие с Оркестратором (очереди, ресурсы), завершаются по таймауту.
  • Сервер БД перегружен, быстро растут БД журналов и журнал WAL.
  • В RabbitMQ растут очереди Оркестратора.
  • В журналах служб — сообщения о потерянных сообщениях («…потеряно по причине ограничения входного буфера.») или таймаутах БД — Потери сообщений.

Вероятные причины

  • Таблицы журналов не секционированы, старые данные не удаляются — Журналы.
  • Завершённые запуски не переносятся из основной БД в БД журналов — Запуски и очередь проектов.
  • Большие очереди обмена данными без автоочистки — Записи, которые не удаляются автоматически.
  • Пул соединений или таймауты команд не рассчитаны на нагрузку — строка «Пул соединений с БД» в таблице проверок.
  • Подробный уровень логирования служб в промышленной среде — строка «Уровень логирования служб» в таблице проверок.
  • Служба Analytic часто обновляет материализованные представления — Служба Analytic.
  • Триггеры «Запуск при наличии новых элементов в очереди обмена данными» с частым расписанием — Запуски и очередь проектов.
  • Одновременный старт большого числа роботов: запросы ожидают снятия блокировок таблиц — Записи LOCK TABLE.
  • В таблицах накапливаются записи, которые автоматически не удаляются — Записи, которые не удаляются автоматически.

С чего начать

  1. Включите метрики WebApi и проверьте очередь соединений к БД: db_client_connections_pending_requests. Около 0
  2. Проверьте размер таблиц БД журналов (ltoolslogs) и наличие у них секций. Таблицы секционированы, старые секции удаляются
  3. Проверьте журнал RobotLogs на «потеряно по причине ограничения входного буфера». Таких строк нет

Записи LOCK TABLE в журнале PostgreSQL для таблиц BusyRobotLicenses, Robots и RpaProjectQueue — штатная работа: WebApi и служба Licenses явно блокируют эти таблицы при выдаче и освобождении лицензий роботов, назначении роботов и обработке очереди проектов.

При одновременном старте большого числа роботов запросы ожидают снятия этих блокировок, и число занятых соединений растёт. Разнесите по времени расписания заданий, которые запускаются одновременно.

Как исправить

Журналы

  1. Секционируйте таблицы журналов по периодам и удаляйте старые секции — Обслуживание БД. Созданные секции таблиц Logs и OrchEvents видны в Настройки → Система → Журналы (только PostgreSQL).
  2. Сократите поток журнала робота. В службе RobotLogs секция RobotEventFilter: Enabled, ParsedElementClasses (какие элементы не разбирать), TextLengthLimit и ParsedMessageLengthLimit (по умолчанию 2000 символов).
  3. Если журнал нужно освободить целиком, кнопка Очистить выполняет TRUNCATE всех таблиц журналов. Данные не восстанавливаются.

Проект ожидает в очереди и при штатной работе — в журнале WebApi видна причина: «отсутствуют свободные лицензии», «отсутствуют свободные роботы…», «машина робота … перегружена». Это не неисправность, подробнее — Проект висит в очереди.

Триггер «Запуск при наличии новых элементов в очереди обмена данными» работает по расписанию: при каждом срабатывании WebApi подсчитывает в БД необработанные элементы очереди. Много таких триггеров с расписанием в несколько секунд создают постоянный поток запросов к таблице ExchangeQueueValues. Увеличьте интервал в расписании триггеров.

Если активность чтения очереди по фильтру получает HTTP 429 «Rate limit exceeded. Please try again later …», сработало ограничение ExchangeQueue:Limits:RateLimiters:PeekByFilter. Реже опрашивайте очередь из робота или увеличьте PermitLimit и Window.

Служба Analytic

Analytic обновляет материализованные представления аналитической БД по расписанию из секции Schedules:RefreshMaterializedViews: для каждого представления — cron-строка CronString и таймаут команды CommandTimeoutInSeconds (по умолчанию 600 с, 0 — без ограничения). Обновление выполняется для ключей mv_WorkersUsage и mv_RobotsUsage. Если обновление нагружает БД, переведите его на редкий запуск в нерабочее время и перезапустите Analytic:

"Schedules": {
  "RefreshMaterializedViews": {
    "mv_WorkersUsage": { "CronString": "0 0 3 * * ?" },
    "mv_RobotsUsage":  { "CronString": "0 30 3 * * ?" }
  }
}

Данные в отчётах по этим представлениям обновляются с той же периодичностью. Автоматической очистки таблиц аналитической БД в службе Analytic нет — размер БД ltoolsanalytic контролирует администратор БД.

Записи, которые не удаляются автоматически

  • Очередь проектов. Автоматически удаляются обработанные записи RpaProjectQueue старше ProjectQueue:CleaningDepth дней. Записи, удалённые из очереди вручную (заполнено поле ForceDeletedAt), остаются в таблице. Контролируйте их число и работу autovacuum по этой таблице.
  • Очереди обмена данными. Физическое удаление элементов доступно, только если в WebApi задано ExchangeQueue:AllowPhysicalRemoval = true и в карточке очереди включено «Физическое удаление». Иначе элементы удаляются логически и остаются в БД. Элементы, помеченные удалёнными до переключения очереди на физическое удаление, остаются в таблице. Освобождение места после удаления выполняет СУБД (autovacuum).
  • Перенесённые запуски. Запуски, перенесённые в БД журналов (RpaProjectLaunch:EnableLogsTransfer), из таблицы RpaProjectLaunches в ltoolslogs автоматически не удаляются.

Параметры фоновой очистки — Обслуживание БД.

Потери сообщений

Если БД журналов не успевает, RobotLogs отбрасывает записи: «Сообщение … потеряно по причине ограничения входного буфера.» Буферы: InputBufferRobotLogs, InputBufferOrchEvents, InputBufferRobotStatuses, InputBufferAttendedRobotLogs — MaxQueueLength (в классе 50000, в Dockerfile 200000). Увеличение буфера оправдано только вместе с ускорением БД.

Очереди RabbitMQ Оркестратора объявлены с ограничением длины (например, dbevents — 10000) без x-overflow: при переполнении RabbitMQ без предупреждения удаляет самые старые сообщения.
