Оркестратор и БД работают медленно

Применимо: 1.26.9WindowsLinuxDocker

Чаще всего тормозит БД: растут журналы, нет очистки, не хватает пула соединений. Вторая частая причина — очередь проектов и RabbitMQ под нагрузкой.

Симптомы

  • Таблицы в UI4 открываются долго, часть запросов падает по таймауту.
  • Активности робота, работающие с Оркестратором (очереди, ресурсы), падают по таймауту.
  • Сервер БД перегружен, быстро растут БД журналов и журнал WAL.
  • В RabbitMQ растут очереди Оркестратора.
  • В журналах служб — сообщения о потерянных сообщениях или таймаутах БД.

Вероятные причины

  • Таблицы журналов не секционированы, старые данные не удаляются.
  • Завершённые запуски не переносятся из основной БД в БД журналов.
  • Большие очереди обмена данными без автоочистки.
  • Пул соединений или таймауты команд не рассчитаны на нагрузку.
  • Подробный уровень логирования служб в проде.

С чего начать

  1. Включите метрики WebApi и посмотрите очередь соединений к БД: db_client_connections_pending_requests. Около 0
  2. Посмотрите размер таблиц БД журналов (ltoolslogs) и есть ли у них секции. Таблицы секционированы, старые секции удаляются
  3. Проверьте журнал RobotLogs на «потеряно по причине ограничения входного буфера». Таких строк нет

Как исправить

Журналы

  1. Секционируйте таблицы журналов по периодам и удаляйте старые секции — Обслуживание БД. Созданные секции таблиц Logs и OrchEvents видны в Настройки → Система → Журналы (только PostgreSQL).
  2. Сократите поток журнала робота. В службе RobotLogs секция RobotEventFilter: Enabled, ParsedElementClasses (какие элементы не разбирать), TextLengthLimit и ParsedMessageLengthLimit (по умолчанию 2000 символов).
  3. Если журнал нужно освободить целиком, кнопка Очистить выполняет TRUNCATE всех таблиц журналов. Данные не восстановить.

Проект в очереди ждёт и при нормальной работе — в журнале WebApi видна причина: «отсутствуют свободные лицензии», «отсутствуют свободные роботы…», «машина робота … перегружена». Это не неисправность, подробнее — Проект висит в очереди.

Если активность чтения очереди по фильтру получает HTTP 429 «Rate limit exceeded. Please try again later …», сработало ограничение ExchangeQueue:Limits:RateLimiters:PeekByFilter. Реже опрашивайте очередь из робота или поднимите PermitLimit и Window.

Потери сообщений

Если БД журналов не успевает, RobotLogs отбрасывает записи: «Сообщение … потеряно по причине ограничения входного буфера.» Буферы: InputBufferRobotLogs, InputBufferOrchEvents, InputBufferRobotStatuses, InputBufferAttendedRobotLogs — MaxQueueLength (в классе 50000, в Dockerfile 200000). Увеличивать буфер имеет смысл только вместе с ускорением БД. Очереди RabbitMQ Оркестратора объявлены с ограничением длины (например, dbevents — 10000) без x-overflow: при переполнении RabbitMQ молча удаляет самые старые сообщения.

Скриншот: «Настройки → Система → Журналы», таблица секций.

Расхождение: в старых доках описан SQL для секционирования, в коде его нет. Таблица секций в UI читает только БД с именем ltoolslogs. Удаление секции из UI4 в 1.26.9, вероятно, не работает: обработчик закомментирован.

Получение лицензии роботом блокирует таблицу BusyRobotLicenses целиком (LOCK TABLE / TABLOCKX). При массовом старте роботов это возможная точка ожидания — проверить на нагрузке.
