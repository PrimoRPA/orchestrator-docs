Очередь обмена данными работает не так, как ожидается

Применимо: 1.26.9WindowsLinuxDocker

Элементы очереди обмена данными выдаются роботу не по порядку, остаются в статусе «Выполняется», не меняют статус после чтения через API или не добавляются из-за натурального ключа. На странице описаны причины по коду WebApi и способы исправления. Повторная постановка элементов после ошибки описана отдельно — см. Очереди: повторная постановка элементов.

Перед началомдоступ к журналу WebApi и к файлу конфигурации WebApi — Журналы служб
Результатэлементы очереди выдаются и обрабатываются в ожидаемом порядке и статусе

Симптомы

  • При частом чтении большой очереди по FIFO часть элементов выдаётся вне порядка: элементы, добавленные позже, обрабатываются раньше оставшихся старых.
  • Элементы остались в статусе «Выполняется»: робот извлёк их и не завершил обработку.
  • Метод GET /api/ExchangeQueues/v2/read/{queueName}/{key} возвращает элемент, но статус остаётся «Новое». Последующий PUT /api/ExchangeQueues/changestatus/{queueName}/{key} возвращает 409 «Изменение статуса возможно только у прочитанного элемента.»
  • Добавление элемента возвращает 409 «Длина NaturalKey не может быть больше 200.»

Вероятные причины

  • Работает буфер предвыборки. В скоростном режиме WebApi резервирует часть очереди в памяти узла. Строгий порядок FIFO в этом режиме не гарантируется.
  • Обработка элемента не завершена. Статус «Выполняется» означает, что элемент извлечён или прочитан с блокировкой, а итоговый статус не установлен. По умолчанию такие элементы не возвращаются в очередь автоматически.
  • Элемент прочитан без блокировки. Чтение по ключу без параметра lockId — только просмотр.
  • Натуральный ключ длиннее 200 символов.

Что проверить

  1. Откройте файл конфигурации WebApi и найдите в секции ExchangeQueue параметры PrefetchDepth и SpeedModeInterval. Учитывайте переменные окружения: в Docker-образах WebApi заданы ExchangeQueue__PrefetchDepth=500 и ExchangeQueue__SpeedModeInterval=1500. Известно, включена ли предвыборка (значение больше 0)
  2. В Роботы → Очереди обмена данными → Элементы очереди задайте фильтр Статусы = «Выполняется». Сверьте время извлечения с журналом робота. Известно, какие элементы не завершены и каким роботом они взяты
  3. Для вызовов API проверьте, передаётся ли в запросе чтения параметр lockId и совпадает ли robotName в запросах чтения и смены статуса. Чтение выполняется с блокировкой тем же роботом
  4. Проверьте длину натурального ключа, который формирует процесс, и тип уникальности ключа в форме очереди. Ключ не длиннее 200 символов

Как исправить

Элементы выдаются не по порядку

Предвыборка включается параметром ExchangeQueue:PrefetchDepth — числом элементов, которые узел WebApi резервирует за раз. В классе настроек значение по умолчанию 0 (предвыборка выключена), в Docker-образах — 500.

Предвыборка работает только в скоростном режиме. Режим включается, если два запроса на извлечение по FIFO к одному узлу WebApi пришли с интервалом не больше ExchangeQueue:SpeedModeInterval миллисекунд (по умолчанию 500, в Docker-образах 1500). Интервал учитывается по всем запросам извлечения к узлу, а не по отдельной очереди или роботу. В скоростном режиме узел помечает до PrefetchDepth элементов как зарезервированные и выдаёт их из памяти; обычное извлечение такие элементы пропускает и берёт следующие. Невыданные элементы возвращаются в очередь при сбросе буфера, раз в ExchangeQueue:PrefetchBufferResetInterval миллисекунд (по умолчанию 2000). Элементы, зарезервированные остановившимся узлом, возвращаются через 10 минут.

Порядок FIFO нарушается и на одном узле: когда скоростной режим выключается, обычное извлечение выдаёт элементы, стоящие в очереди после зарезервированных. При нескольких узлах WebApi у каждого узла свой буфер.

Если процессу нужен строгий порядок:

  1. Задайте в WebApi "ExchangeQueue": { "PrefetchDepth": 0 } (в Docker — переменная ExchangeQueue__PrefetchDepth=0).
  2. Перезапустите WebApi на всех узлах. Элементы извлекаются в порядке приоритета и времени добавления

Без предвыборки каждое извлечение выполняется отдельным запросом к БД. При высокой интенсивности чтения это снижает производительность очередей. Альтернатива — уменьшить SpeedModeInterval, чтобы скоростной режим включался реже; порядок в этом случае по-прежнему не гарантируется.

Элементы остались в статусе «Выполняется»

Функции массовой смены статуса в UI4 нет. Действие Повторить в меню строки сбрасывает один элемент: снимает отметку о чтении и статус, обнуляет счётчик повторов и ставит новое время добавления. Для группы элементов используйте клонирование:

  1. В Элементы очереди задайте фильтр Статусы = «Выполняется» и отметьте нужные строки.
  2. Нажмите Клонировать. Появились копии со статусом «Новое»
  3. Не снимая отметки с исходных строк, нажмите Удалить. Исходные элементы в статусе «Удалено»

Копия получает новый идентификатор и нулевой счётчик повторов. Значение, метаданные, теги, приоритет и даты доступности копируются. Натуральный ключ копируется только в очереди без типа уникальности ключа; при включённой уникальности у копии ключа нет. Элемент, который является корнем цепочки повторов, при удалении пропускается.

Автоматическая обработка зависших элементов включается параметром ExchangeQueue:EnabledInProgressTimeout=true (по умолчанию false). Тогда в форме очереди появляется поле Таймаут для элемента очереди (сек.). Элемент, который находится в статусе «Выполняется» дольше таймаута, удаляется с причиной «таймаут», а не возвращается в очередь. Проверяются только элементы, извлечённые после последнего запуска WebApi.

Статус не меняется после чтения через API

Чтение по ключу без lockId возвращает элемент, но не блокирует его и не переводит в статус «Выполняется». Изменить статус можно только у прочитанного элемента.

  1. Читайте с блокировкой: GET /api/ExchangeQueues/v2/read/{queueName}/{key}?robotName={robot}&lockId={guid}, где lockId — новый GUID, который формирует вызывающая сторона. Элемент в статусе «Выполняется»
  2. Вызовите PUT /api/ExchangeQueues/changestatus/{queueName}/{key}?robotName={robot} от имени того же робота. Элемент получил итоговый статус

Натуральный ключ длиннее 200 символов

Поле натурального ключа ограничено 200 символами. Если в очереди задан Тип уникальности натурального ключа, WebApi проверяет длину при добавлении и изменении элемента и возвращает 409 «Длина NaturalKey не может быть больше 200.» Сократите ключ в процессе, например замените длинную строку её хешем.
